# Scenephonie MVP 尋路圖

Label: `wayfinder:map`

## Destination

一份**可直接開工的 MVP 規格書** — 功能邊界、資料模型、關鍵技術選型（區塊編輯器、儲存模型、PDF 匯出）全部寫定，交接後就能開始實作。

地圖走完的判準：沒有任何「還得先想清楚才敢動手」的問題殘留。

## Notes

### 領域與定位

台灣影視編劇工具。給**真實編劇**使用（含作者自己與身邊編劇朋友），獨立開發、無硬性期限、不背商業包袱。作者有編劇經驗與影視產業背景，是領域內行人 — domain 問題可以直接問他，不必事事外求。

### 產品的真正痛點

不是「結構化很潮」，而是：**大家用 Word 寫劇本，所以格式就是內容的一部分**。三角形要不要加、metadata 用簡表還是行內，全都直接刻在文字裡，換格式等於重排全文。台灣接案者格式各異，根因在此。

內容結構化之後，格式與內容脫鉤，各種格式退化成**渲染樣式**。這是本產品的核心賭注。

### 常設原則：一條路走通，但不堵死岔路

v1 只做一種，架構預留擴充。這個模式在本效力中反覆出現（場次表只做第一層、輸出只做一種格式），是刻意的。

### 硬性架構約束

每張票券的決策都不得違反下列三條：

1. **場次是穩定錨點。** 每個場次有永久 id，重新排序、插入、刪除都不破壞外部引用。所有下游文件（場次表、分鏡、行程）掛在 id 上，而非「第 12 場」這種會變動的序號。
2. **資料模型不含呈現性資訊。** 三角形、粗體、縮排等屬於輸出模板，不進資料模型。
3. **不得堵死協作。** v1 不做同步層，但資料模型不能設計成「之後加不上協作」。

### 核心模型直覺

**場次是劇本的核心實體，場次表是它的投影。**

**但分場大綱不是投影。** 它以**場景**（敘事上的事件／情境）為單位另外撰寫，在劇本之前完成，粒度與場次不同 —— 一個場景可橫跨多個場次。它是獨立的創作層，不是視圖。

> ⚠️ 2026-08-18 修正。此處原記為「劇本／分場大綱／場次表都只是場次的不同投影」，並據此推論「分場大綱幾乎免費」。**分場大綱那半是錯的**，作者依業界經驗更正。詳見 `CONTEXT.md` 的「場景」與「分場大綱」詞條。

若要把分場大綱納入模型，正確形狀是 **場景 1:N 場次**（場次可歸屬到某個場景）。這也正好解釋業界「分場大綱 40 場、劇本卻 130 場」的現象 —— 不是有人算錯，是兩者計數單位不同。是否納入 v1 **待決**。

### MVP 範圍（已定，不再重議）

**進 v1：**

- 區塊化編輯。建立場次走 **`/next`「新增下一場」**（也可用 ⌘+Enter 或場次腳部按鈕）；切換區塊型別走 Tab。
- 區塊型別共三種：**動作、對白、插入畫面**。三角形其餘 6 種語意併入動作。
  - **「插入鏡頭」於 2026-08-21 更名為「插入畫面」**，只裝單一畫面描述、不產生新場次。防線從「嚴格限定單一鏡頭」改寫成**不得長出運鏡、景別等欄位** —— 那條線本身沒變（長出欄位就是文字分鏡，已排除在外），只是換一種守法。
  - **對白帶「發聲方式」**（一般／V.O./O.S.），併進人物欄的自動補全選單，不另做 UI。**不可據此推導登場人物**。
- 正式場次編號永遠是 **1..N**，**使用者手打的字母尾綴不存在**（2026-08-20）：它是繞過「重新編號會讓下游表單失效」的 workaround，而那個洞正是約束 1 要填的；原型證實它是假保護（`S5A` 一被搬移就變成 `S2A`）。「這一版已經交出去了」屬版本鎖定，歸票券 07。
- **場次序列有階層，深度固定兩層**（主場次 → 子場次，子場次不能再有子場次；蒙太奇水平展開）—— 2026-08-21 拉回 v1，撤銷「插入戲｜Out of scope」。子場次**會**出現在場次表上（額外的場景需求必須讓製片知道）。子場次編號是**從父子關係推導**的顯示值，因此不說謊 —— 子場次跟著父場次一起搬。細節歸票券 09。
- **草稿場次**：`是草稿 = 手動標記 或 metadata 不完整`，不參與正式編號（標籤 `S11[D1]`，錨定前一場），不進 PDF 與場次表，匯出前防呆。見票券 11。
- **拖曳排序**（場次可拖，區塊可跨場次拖）—— 2026-08-20 從 Out of scope 拉回。規格書必須連成本一起寫：得繞過 `isolating`、得處理「搬走最後一個區塊」後的空場次、得跟 ProseMirror 的原生拖放搶事件。
- **文件只由場次組成**（`scene+`），場次之外沒有可編輯空間。代價是匯入既有劇本沒有落地區 —— 匯入已排除在 v1 外。<br><sub>⚠️ 場次**內部**的 content 表達方式會因子場次而改（`sceneBlock+` 要變成什麼），屬票券 09；文件收成 `scene+` 這條不變。</sub>
- 場次 metadata：場次號、日／夜／晨／昏、內／外、地點、登場人物
- **人物與地點都是實體**，非字串（地點於 2026-08-21 升格）。場次指向的是 `{ 實體 id, 這一場顯示的名字 }` —— 漸進揭露（「未知大樓房間」後來揭露為「海豚公寓房間」）不能被正規化掉。細節歸票券 10。
- **劇情文字裡的人物／地點行內引用**，形狀是 `{ id, 顯示文字 }`：文字是權威的渲染來源，id 只是額外連結，斷了也只是少一條連結、PDF 照印。改名不自動代換全文。
- **場次引用（`@S5`）反過來必須連動** —— 場次號不是人寫的字，是算出來的顯示值。附快速參考彈窗。
- **分場大綱做成一份自由文字文件**，不與場次關聯、不引入場景實體。呼應它在業界本來就沒有硬性格式的性質。
- **場次上沒有摘要欄位。** 編劇通常不逐場填寫，強迫他們填等於為了下游表單好看而增加寫作負擔，與「不打斷心流」的主張相反。順場表的「劇情概要」欄在 v1 沒有資料來源。

  <sub>（以上兩項於 2026-08-18 取代原本的「場次 summary 欄位 + 分場大綱視圖」。原方案建立在「分場大綱是場次摘要的投影」這個已證實錯誤的前提上。）</sub>
- PDF 匯出，格式參照**文化部劇本獎範例**，水準線＝「拿去參賽會被接受」，不追求排版精美
- **場次表**（第一層投影：純從劇本推導，零新增資訊）
- 唯讀分享連結（免註冊可看劇本與場次表）
- 專案與劇本拆成兩個實體，v1 為 1:1（單部電影）

**技術棧（初步，非鎖定）：** Next.js / TypeScript / PostgreSQL / Drizzle ORM。**編輯器確定用 Tiptap**（原型已驗證，見票券 03）。

## Decisions so far

<!-- 一行一張已關閉票券：足以判斷相關性，細節去票券裡看 -->

- [台灣劇本格式規範對齊](./issues/01-taiwan-screenplay-format-spec.md) — 文化部劇本獎格式**實質等同**優良劇本獎格式（場次標題無人物欄位、無 △ 符號、對白有兩種可接受變體、無簡表），北藝大是獨立的另一套且唯一給出完整頁面設定數字；三份範本皆未觸及插入場次編號。
- [PDF 匯出技術方案](./issues/05-pdf-export-tech.md) — 首選 **Puppeteer/Playwright + `@sparticuz/chromium`**（CJK 精度最高、換格式＝換 CSS 模板）；「Vercel 50 MB 卡死 Puppeteer」的說法**已過時**，現行為 250 MB，中文字型在 Vercel／Lambda **不構成阻礙**；但**排除 Cloudflare Workers 純執行模式**（10 MiB），此技術路徑反向約束了部署平台選擇。
- [插入戲與插入鏡頭的表達慣例](./issues/08-inserted-scenes-and-shots.md) — 台灣端經查證是**空白**（S5A 僅作者單一來源）；美式軟體三方收斂於**字母尾綴**（`12A`）故建議沿用，且因本專案已有 id／場次號分離，**不需要 Final Draft 的「鎖定」機制**；插入鏡頭應**獨立成區塊型別但不產生新場次**（Final Draft 與 Scrivener 皆如此切分），三角形其餘 6 種語意仍併入動作。
  <sub>⚠️ 兩半都已被後續推翻。字母尾綴那半：2026-08-20 插入戲移出 v1。插入鏡頭那半：2026-08-21 更名為「插入畫面」並縮回「單一畫面描述」，長插入改走**子場次**（票券 09）；「獨立成區塊型別但不產生新場次」這個切分仍然有效。</sub>
- [區塊編輯器選型與 /scene 輸入體驗](./issues/03-editor-prototype.md) — **Tiptap 通過**，node schema 表達力沒問題；真正的成本是**每個自訂互動都要跟一層預設行為協商**（六個 bug 全屬同一家族，已逐條記錄）。選定**變體 A · 內嵌簡表**；建立場次改為 `/next`「新增下一場」；⌘+A 依結構逐層擴選。**場次號走 decoration，不進文件也不進資料庫** —— 它從來不是 key，只在渲染那一刻才有意義。中文 IME 不是架構障礙。三項範圍變更：拖曳排序拉回 v1、插入戲移出 v1、匯入排除在 v1 外。
- [草稿場次](./issues/11-draft-scenes.md) — 草稿**不是要「轉換」的狀態，是推導出來的**（`手動標記 或 metadata 不完整`），因此沒有「自動轉換」這個會在你背後改文件的動作；不參與正式編號，標籤 `S11[D1]` **錨定前一場**（錨定後一場會與真正的 `S12` 撞號）；不進 PDF 與場次表；匯出前列出將被略過的草稿（附首行摘錄、可多選全選抑制），但**即使全部抑制仍顯示「本次略過 N 場」** —— 靜默少印是投獎者最糟的失敗模式。
- [場次表與拍攝表單的真實欄位](./issues/02-scene-breakdown-fields.md) — 順場表 14 欄已拆解分層（第一層僅場次號／內外／日夜／地點／登場人物／摘要）；「男一～女三」欄填的是**服裝代號**而非出席勾選；業界表單**清一色以會變動的場次號互相參照、無永久 id**，故「場次是穩定錨點」在業界無範本可循，是我們要自建的機制。

## Not yet specified

在範圍內，但還不夠銳利到能開票。前線推進後會畢業成票券。

- **對白排版變體** — 文化部劇本獎格式對「行內式」與「置中分行式」兩種對白寫法均可接受，未強制擇一。v1 要選哪一種？要不要兩種都支援讓使用者選？預期在規格書定稿時決定，除非它意外變複雜。
- **新手引導** — 「場次之外不能打字」對不熟這個軟體的人需要習慣，作者認為要想辦法引導。Tab 切換區塊型別同理：該判斷只來自一位熟悉網頁操作的編劇，未在其他使用者身上驗證。形式（首次導覽？空狀態提示？）還不夠銳利到能開票。
- **唯讀分享連結的機制** — URL 形式、是否可撤銷、要不要有效期。
- **認證方案** — 自建 vs 第三方服務。淺，但 v1 需要。
- **部署與資料庫託管** — 平台選擇。**已有一個硬邊界條件**：PDF 匯出的首選方案（Puppeteer + Chromium）在 Vercel／AWS Lambda 可行（250 MB 空間足夠），但**在 Cloudflare Workers 純執行模式不可行**（10 MiB 上限）。若日後傾向 Cloudflare，PDF 匯出須拆成獨立子服務或改用其 Browser Rendering API（未實測）。
- **專案的擁有者概念** — 即使 v1 單人，資料模型要不要現在就有 owner 欄位（關係到約束 3）。

## Out of scope

已意識地排除在**本效力**之外。不會畢業；除非重畫目的地，否則不再回來。

- **即時協作與離線編輯** — v1 不做同步層。CRDT／local-first 會讓編輯器選型與後端複雜度翻倍，是獨立開發者最容易翻船的坑。（但受約束 3 保護）
- **第二層標註**（道具、服裝、預估頁數、拍攝地點）— 在還沒有真實劇本資料前訂欄位是在猜。
- **第三層新文件**（文字分鏡、拍攝行程）— 另一個階層、另一群使用者、另一個產品；拍攝行程本質是排程求解，市場上已有 Movie Magic、StudioBinder。這是長期護城河，但不是 v1。
- **多角色帳號與權限** — 唯讀分享連結先驗證「劇組是否真的需要這些資訊」。
- **多格式輸出** — v1 只做文化部劇本獎格式；架構預留參數化。
- **影集多集支援** — 專案與劇本已拆開，之後 1:1 放寬為 1:N 即可。
- **匯入既有劇本** — 文件收成 `scene+` 之後，貼上的散文沒有落地區。而「就算是已經結構化的文字，變因也很多」（作者判斷）：Word 劇本的場次標題有幾十種寫法，這是獨立的解析問題，塞進 v1 只會拖垮它。
- **使用者手打的字母尾綴編號** — 見 MVP 範圍的說明。殘留的真實情境（劇本已交付後改稿）是版本鎖定問題，歸票券 07。
  <sub>⚠️ 2026-08-21：本條原為「**插入戲與**字母尾綴編號」，插入戲那半已**撤銷**並拉回 v1，改以父子場次表達（票券 09）。父子關係沒有 `S5A` 「搬移就說謊」的毛病，因為子場次跟著父場次一起搬 —— 這是當初否決它的唯一理由。被排除的只剩「使用者手打的尾綴」。</sub>
- **其餘次要功能** — 便利貼／參考資料、AI 寫作建議、協作評論、劇本資料儀表板。（**區塊拖拉排序已於 2026-08-20 拉回 v1**。）
