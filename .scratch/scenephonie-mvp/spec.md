## 1. 定位與賭注

台灣影視編劇工具，給真實編劇使用。獨立開發、無硬性期限、不背商業包袱。

**痛點不是「結構化很潮」**，而是：大家用 Word 寫劇本，所以**格式就是內容的一部分**。三角形要不要加、metadata 用簡表還是行內，全都直接刻在文字裡，換一種格式等於重排全文。台灣接案者格式各異，根因在此。

**賭注**：內容結構化之後，格式與內容脫鉤，各種格式退化成**渲染樣式**。

**常設原則：一條路走通，但不堵死岔路。** v1 只做一種，架構預留擴充。這個模式在本規格裡反覆出現（場次表只做第一層、輸出只做一種格式、專案只做一種類型），是刻意的。

## 2. 三條硬性架構約束

規格中任何一條規則都不得違反下列三條。第 12 節逐條說明它們如何被滿足。

1. **場次是穩定錨點。** 每個場次有永久 id，重新排序、插入、刪除都不破壞外部引用。所有下游文件掛在 id 上，而非「第 12 場」這種會變動的序號。
2. **資料模型不含呈現性資訊。** 三角形、粗體、縮排、「以下對剪」、「回到」都屬於輸出模板，不進資料模型。
3. **不得堵死協作。** v1 不做同步層，但資料模型不能設計成「之後加不上協作」。

不會在本效力中回來。要做就是重畫目的地、開新的效力。

| 排除項 | 理由 |

| **重疊群組**（一個場次屬於多個群組） | 重疊的區間不是樹，編輯器文件模型嚴格是樹。升級路徑已保留，見 [ADR-0006](../../docs/adr/0006-continuous-action-as-continuation-subscenes.md) |

| **第二層標註**（道具／服裝／預估頁數／拍攝地點） | 沒有真實劇本資料前訂欄位是在猜 |
| **第三層新文件**（文字分鏡、拍攝行程） | 另一個階層、另一群使用者、另一個產品 |
| **多角色帳號與權限** | 先用唯讀分享連結驗證劇組是否真的需要這些資訊 |
| **多格式輸出** | v1 只做 GHSA 格式；架構預留參數化（§9.8） |
| **影集多集支援** | v1 只做單一劇本專案。升級路徑＝新增一種專案類型，見 [ADR-0009](../../docs/adr/0009-documents-hang-on-the-creative-unit-they-describe.md) |
| **匯入既有劇本** | 文件收成場次序列後，貼上的散文沒有落地區；Word 劇本的場次標題有幾十種寫法，是獨立的解析問題 |
| **使用者手打的字母尾綴編號**（`S5A`） | 假保護 —— 一搬移就變成 `S2A`。它在業界成立是因為底下有顏色稿的鎖定層，我們沒有那一層 |
| **人物關係圖** | GHSA 明文禁止圖片；且它是一個編輯器不是一個欄位。⚠️ 但**歸迷霧不歸永久排除** —— 消費者是編劇與劇組而非評審 |
| **劇情文字裡的人物／地點行內引用** | 沒有 v1 消費者：它答的是「被提及」，而登場人物的判準是**入鏡** |
| **版本鎖定／顏色稿** | 解的是紙本流通問題，我們有共同的資料來源 |
| **投稿攤平**（把子場次攤平成連續 1..N） | 已複審維持（[13](./issues/13-inserted-scene-conventions-in-practice.md)）：攤平自己會製造新的說謊面。岔路不封 —— 加回來是一個推導函式加一個匯出選項 |
| **便利貼、AI 寫作建議、協作評論、資料儀表板** | 次要功能 |

## 4. 領域模型

### 4.1 全景

```
專案 (project)                     ← 類型：單一劇本專案（v1 唯一）
 ├── 劇本 (screenplay)  1:1        ← doc：一棵場次樹
 │    └── documents(kind=分場大綱)
 ├── 人物 (character)   1:N        ← append-only，存在＝被引用
 ├── 地點 (location)    1:N        ← 同上
 ├── documents(kind=交件大綱)      ← 描述整部作品 → 掛專案
 ├── documents(kind=角色設定表)    ← 同上
 ├── 交付 (delivery)               ← append-only，唯一刻意不可變
 └── 分享 (share)                  ← 獨立 identity 與生命週期
```

**文件掛載於它所描述的創作單位**（[ADR-0009](../../docs/adr/0009-documents-hang-on-the-creative-unit-they-describe.md)）：描述整部作品 → 掛專案；描述單一劇本 → 掛劇本。判準建立在**關係**上而非**名稱**上，因為文件名稱是可變的呈現值。這是「可變的顯示值不承載身分」在本專案的第二次出現，第一次是場次號。

### 4.2 專案與劇本

**專案 = 一部作品。** 有類型：

- **單一劇本專案** —— 一個專案一個劇本（電影、短影片、微電影、廣告）。**v1 只做這一種。**
- **系列劇本專案** —— 不在 v1 範圍內。

⚠️ **1:1 不是待放寬的限制，是「單一劇本專案」這個類型的定義。** 升級路徑是**新增一種類型**（加東西），不是把 1:1 鬆綁成 1:N。

**v1 不提供類型選擇、不做 UI** —— 只有一種類型時給選就是說謊。欄位存不存在是實作細節（單一值列舉日後補一欄帶預設值是廉價遷移）。

**專案的 meta 欄位**（[20](./issues/20-submission-docs-product-shape.md)）—— 匯出交件 PDF 時的前置頁來源：

| 預設欄位 | 預設是否進 PDF |
|---|---|
| 片名 | 開 |
| 劇情大綱（可改名為「故事大綱」） | 開 |
| 人物介紹 | 開 |
| **編劇姓名** | **⚠️ 關** —— GHSA 與 TFC 都明文不得署名。這是唯一一個預設值與直覺相反的欄位 |
| 分場大綱 | 關（兩個比賽都不要它） |

全部**可改名、可開關、可排序**，編劇可自由新增欄位。

> **界線（必須寫下，否則會與[票券 15](./issues/15-multi-spacetime-scenes.md) 否決「通用備註欄」前後不一）**：
> 自訂欄位**只能裝文件層級的散文，不得裝場次層級的資料**。否則會有人拿它寫「第 12 場要補拍」——
> 場次的東西必須留在場次上，才進得了場次表與交付。
> 通用備註欄被否決的理由是「沒有消費者」；這裡每個欄位都直接對應一份要繳的東西，消費者是 PDF 的前置頁，而且只有這一個。

**「劇本內文」不是欄位、不進這個清單** —— 它是那份 PDF 的主體。前置欄位可自由排序，**內文永遠押尾、永遠在**。

**否決「匯出時選投哪個獎」**：那等於我們替編劇讀簡章，讀錯的代價是件被退，而我們扛不起也驗證不了。簡章確實會變（GHSA 條款編號 46 屆第八款 → 48 屆第十款、浮水印文字每屆不同）。

### 4.3 場次

**定義：由時空的連續性界定** —— 時間或空間一變，就是新的場次。metadata 不是任意挑的欄位，而正是場次的**身分判準**。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `sceneId` | string | `sc_` 前綴 nanoid，全域唯一，**使用者永遠看不到**（[ADR-0002](../../docs/adr/0002-scene-id-and-derived-scene-numbers.md)） |
| `時間` | `日｜夜｜晨｜昏｜null` | 業界順場表稱「光」 |
| `內外` | `內景｜外景｜內外景｜雜景｜null` | 業界順場表稱「景」 |
| `地點` | `{ locationId, 顯示名 }` 單值 ｜ **陣列（僅雜景）** ｜ null | 見下方雜景逃生口 |
| `登場人物` | `{ characterId, 顯示名 }[]` | 判準是**入鏡**，不是有沒有台詞 |
| `群演` | `{ extraId, 描述, 人數 }[]` | 場次限定實體，id 只在該場次內有意義 |
| `manualDraft` | boolean | 手動標記為草稿 |
| `dismissedCharacterIds` | string[] | 登場人物提示中選了「不新增 —— 他不入鏡」的人物 |

**場次號不是欄位。** 它是渲染那一刻推導出來的顯示值，不進文件也不進資料庫（§5.4）。

#### 場次身分只在下列五個時刻被鑄造

1. 建立場次（`/next`、⌘+Enter、場次腳部按鈕）
2. 建立子場次（`/insert`、`/continue-to`）
3. 建立群組成員（「對剪到…」第二步選「建立新的一場」）
4. 複製出一份副本（碰撞修復）
5. 跨劇本貼上

**其餘一切都保住身分**：拖曳、剪下貼上、升級降級、⌘Z。這是約束 1 的可執行版本。

#### metadata 一律單值 —— 唯一的逃生口是雜景

**雜景**（短時間內快速跳接的多地點畫面）是 `內外` 欄位的第四個值，不是地點的值。它是**場次定義唯一的逃生口**：

- **不要求編劇拆開。** 台灣現行寫法就是一句散文（「他在巷口、警局、商圈到處問人」），沒有片段層級的地點與登場人物 —— 要求拆開不是把既有寫法結構化，而是要求編劇多做事。
- 既然承認它橫跨多地，**它的地點欄可多值、也可留空**。
- **草稿防呆對「內外＝雜景 ＋ 地點留空」放行** —— 「完整」的定義隨內外的值改變。
- 地點留空時，場次表的地點欄印**推導文字**「參照敘述」（不建垃圾實體）。
- 編劇想嚴謹時可自願升級成**場次群組**，那時它變回 N 個各自單值的場次。**給選項，不給功課。**

#### ❌ 不做通用備註欄

沒有消費者（場次 metadata 只有場次表與 PDF 場次標題兩個消費者），而且自由文字欄是結構化的漏水口。

#### ❌ 場次上沒有摘要欄位

順場表的「劇情概要」多由製表者撰寫，且編劇通常不逐場填寫。強迫他填等於為了下游表單好看而增加寫作負擔，與「不打斷心流」直接相反。**順場表的劇情概要欄在 v1 沒有資料來源。**

### 4.4 子場次

附屬於某個**主場次**的場次。有自己完整的 metadata 與自己的永久 id，因此依定義就是場次。

⚠️ **「附屬」是結構詞，不是敘事詞。** 它只表示「這段戲從主場次開始」，**不表示**敘事上比較次要，也不表示它的地點在主場次的地點裡面（地點實體之間沒有包含關係）。

**種類**（編劇的宣告，系統不代填）：

| 種類 | 意思 | 入口 |
|---|---|---|
| **插入** | 另一段時空的戲（閃回、閃進、夢境） | `/insert`「插入戲」 |
| **接續** | 連續動作走進另一個空間，中間沒有時間間隔 | `/continue-to`「接續到…」 |

**兩種只有語意分岔，結構完全共用。** 底下所有規則對兩者一律適用：

- **深度固定兩層** —— 子場次不能再有子場次。由 schema 的內容規則直接保證，不是執行期檢查。
- **metadata 完全不繼承主場次。** 預填等於預設一個依定義不可能成立的狀態，而且**會騙過草稿防呆** —— 一場沒改過的子場次會安靜地告訴製片「這場跟前一場同時同地」，那是最糟的錯，因為沒有任何線索。
  省打字走**明確套用**：`/insert`／`/continue-to` 的第二步可選一個既有場次，套用它的**內外／時間／地點**三欄（地點是實體引用，因此兩場在場次表自動聚合），**不套用登場人物**。套用是**複製，不是連動**。清單第一項是「不沿用，留空」。
- **會進場次表**，自佔一列，緊接主場次之後，縮排僅作視覺次級。判準：場次 metadata 只有兩個消費者（場次表與 PDF 場次標題），子場次若不進場次表，它的 metadata 就沒有任何人看得到。**「有 metadata」與「進場次表」必須同進同退。**
- **刪除主場次一併刪除子場次。** 配套是兩個不彈對話框的做法：`SceneMenu` 的刪除項標籤寫明數量（「刪除本場（含 2 個子場次）」）、⌘Z 一步完整還原（子樹是一個節點，`sceneId` 一起回來）。
- **不做降級**（子場次 → 插入畫面）：會消滅永久錨點、裝不下（`sceneBlock+` 塞不進 `inline*`）、而且有現成替代品（⌘Z 或刪掉重打）。

**編號 `5.1`**（點號）—— 推導的顯示值。用點號而非連字號，是因為連字號是**鏡號**的慣例（`5-1` ＝ 第 5 場第 1 鏡），點號把那個位子空出來（子場次的第 3 鏡是 `5.1-3`）。⚠️ 備案 `S5之1` **已撤下** —— 它撞鏡號（[13](./issues/13-inserted-scene-conventions-in-practice.md)）。

**折返**（走出去又回到主場次）是免費的：主場次的內容可以是區塊 → 子場次 → 再回到區塊，所以主場次在場次表上仍然只有一列。

### 4.5 場次群組與片段

**群組 = N 個平行的成員場次 ＋ 一串有序的片段**，每個片段標記它屬於哪一個成員。用來表達**交叉場次**（對剪）。

- **成員場次就是普通的場次** —— 各自完整的單值 metadata、各自的永久 id、各自一個**頂層場次號**（`26`、`27`、`28`），場次表各自一列。
- **群組本身不佔場次號、不進場次表。** 「這幾場是一組對剪」是**敘事**事實不是**製作**事實，製片排通告要的正是把它們拆開。
- **成員場次沒有自己的內容** —— 內容在片段裡。這是這個形狀誠實的代價，也正好對應現實：**成員場次是拍攝的單位，片段是閱讀的單位**。
- **存在的理由只有一個：保住交錯**（更準確地說，是**閱讀的單位和拍攝的單位對不起來時的片段歸屬**）。片段的先後順序是推導不出來的真資訊。凡是不交錯的情境都不該用群組 —— 那會讓群組退化成「讓標題看起來合在一起」，也就是把呈現性資訊放進資料模型。
- **成員可以有自己的子場次。** 群組不能巢狀，一個場次不能同時屬於兩個群組。**階層裝得進平行裡面，平行裝不進平行裡面。**
- **「以下對剪」四個字不進資料模型**，是模板產物。

**手勢分兩種**（重手勢建立、輕手勢切換）：

| 手勢 | 動作 | 頻率 |
|---|---|---|
| `/` →「**對剪到…**」 | 建立群組（第二步沿用子場次那個「選既有場次或建立新的一場」） | 一段戲一次 |
| **`⌘+1`／`⌘+2`／`⌘+3`** | 切換游標所在片段的歸屬，**直接定址** | 一段戲五到十次 |

**不用循環鍵** —— 三地對剪也算常見，循環要編劇記住順序。`⌘+4` 在只有三個成員時是**無效鍵**，永遠不會憑空建立場次。`/next` 與 `Tab` 語意不變：群組裡按 `/next` 是「結束群組、建立下一個場次」，不是新增第四個成員。

⚠️ **「同時發生」不是交叉場次的定義**，所以「metadata 完全不繼承」完整適用。

### 4.6 區塊

三種型別，涵蓋台灣三角形原本的 9 種語意（其餘 6 種併入動作）：

| 型別 | 內容 | 說明 |
|---|---|---|
| **動作** | inline text | 描述人物行為與環境 |
| **對白** | `{ 人物引用, 發聲方式, inline text }` | 見下 |
| **插入畫面** | inline text | 單一畫面描述，**不產生新場次** |

**對白的人物欄，合法目標是「人物」或「本場次的群演」。** 分界規則：

> **一個人說話 → 人物**（即使名字只是「路人甲」）。**一群人齊聲說 → 群演。**

（原規則「一旦有對白就升格為人物」在集體發聲上會壞掉 —— 人數無處可放。新規則的判準跟著**通告**走。）

**發聲方式**：`一般｜V.O.｜O.S.`，併進人物欄的自動補全選單，不另做 UI。輸出時渲染為 `小明（V.O.）`。

⚠️ **不可據此推導登場人物**（判準是入鏡），**但可據此提示** —— 見 §4.7。

**插入畫面有兩條並存的防線，方向不同**：

1. **與本場次同一個時空。** 時空一變就走**子場次** —— 換了時間或地點，製片就得知道那個畫面要另外在什麼時候什麼地方拍。這條是**判準級**的，直接來自場次的定義。
2. **不得長出運鏡、景別等欄位** —— 一旦長出來就是文字分鏡，那在範圍外。

第 1 條比「嚴格限定單一鏡頭」好，因為後者是量的模糊判斷（幾個鏡頭算多？），前者是編劇本來就會做的判斷（這個畫面在哪裡拍？）。

**這條界線靠兩個近乎零成本的位置去教，不做常駐提示**：

- `/` 選單的兩行對照（該處本來就有 hint 行）：
  - 插入畫面 —— 同一個時空的單一畫面，不另立場次
  - 插入戲 —— 換了時空的一小段戲，會進場次表（編號 5.1）
- 區塊自己的標籤上，游標進入時長出逃生口，列**兩個目的地**：「換了時空？改成**插入戲** ／ 改成**接續**」。用詞刻意與 `/` 選單相同；**不預設變成插入戲**，那會在編劇背後決定 `種類`。

**無粗體／斜體／刪除線** —— StarterKit 相關 mark 全關，落實約束 2。

**括號提示**（`啊（抓一抓頭），我知道了`）不做特別處理，就是對白裡的普通文字。

### 4.7 人物、地點、群演

#### 存在 ＝ 被引用（[ADR-0005](../../docs/adr/0005-entities-exist-by-reference.md)）

實體表是 **append-only 的名字目錄**。一筆實體「存在」＝至少有一個引用指向它。引用有三個來源：場次 metadata、對白人物欄、角色設定表。

這一句話讓三個問題**一起消失**而非各自被解決：

- **孤兒不出現在任何地方、v1 永不清理** → ⌘Z 留下的孤兒不必處理，文件與實體表的 undo 一致性問題**消失**而非被解決。
- **「刪除實體」這個動作不存在** —— 編劇只能拿掉引用。
- **合併別名不必真的刪掉舊 id。**

#### 欄位極簡

| | 欄位 |
|---|---|
| **人物** | `id`（`ch_` nanoid）、專案 id、**名字**、**描述** |
| **地點** | `id`（`lo_` nanoid）、專案 id、**名字** |

**地點沒有描述欄位** —— 沒有任何比賽要求地點介紹。這是兩者唯一的不對稱，而且是有理由的不對稱。

人物的**描述**就是人物介紹的內文，消費者是 PDF 的人物介紹頁。性別、年齡不做成欄位（人物介紹沒有規定格式，做成欄位是憑空發明約束）；「主要人物」不是旗標，就是有沒有被角色設定表收錄。

**兩者都屬於專案，不屬於劇本** —— 影集那天人物跨集有身分連續性。

#### 引用形狀與漸進揭露

場次與對白指向的是 **`{ 實體 id, 這一場顯示的名字 }`**。**漸進揭露是敘事手段，不能被正規化掉**：編劇先寫「未知大樓房間」，後段才揭露它是「海豚公寓房間」。

- **別名不存在實體上** —— 就是各引用上的顯示名。
- **名字是真欄位不是推導值**（初值＝第一次建立時打的字，可改）—— 推導在漸進揭露下算不出編劇心裡的真名。
- **地點實體之間沒有包含關係。** 公寓 ⊃ 客廳 這種樹不做：沒有 v1 消費者、要人另外填、而且沒有底（公寓 ⊃ 客廳 ⊃ 沙發？）。

**地點的身分判準是「美術上要不要分開處理」** —— 不是名字，也不是地理位置。同一個房間的「二十年前」與「現在」是**兩個**地點實體（美術要陳設兩次）；「未知大樓房間」與「海豚公寓房間」是**同一個**實體的兩個顯示名（陳設只有一套）。這兩個案例方向相反，正好界定了這條判準。

#### 自動補全選單：三列

```
📍 海豚公寓房間（12 場）
＋ 建立新實體「未知大樓房間」
🔗 作為既有實體的另一個名字…
```

- **打字當下不問任何問題** —— 系統不可能懷疑「海豚公寓房間」就是「未知大樓房間」，積極合併相似名會把兩套陳設併成一套。
- **但第三列讓編劇主動說出口** —— 他寫的當下就知道。第二步把改名也吸收進同一個流程（`只當這一場的名字` ／ `同時把實體改名`）。
- **新建 chip 與命中 chip 視覺可辨**（`＋` vs `📍`）。
- **注音組字期間選單完全不動作。**
- 事後補救走 chip 選單的「這其實是…」（重寫引用、要自己的確認、⌘Z 不管它）。

#### 登場人物的提示（不是推導）

> 觸發條件：某人物在本場有**一般**發聲方式的對白，且不在本場的登場人物欄。

標了 V.O./O.S. 的**絕不提示**（編劇已明確宣告那個人不入鏡）。反方向（在登場人物欄但沒台詞）也不提示。

提示是一個**可忽略的選單**：`＋ 新增為登場人物` ／ `✕ 不新增 —— 他不入鏡`。

**ESC 與「不新增」語意刻意分開**：ESC 是「現在別煩我」，不記錄任何判斷、下次還會提示；「不新增」是明確判斷，存進 `dismissedCharacterIds`，這一場的這個人不再提示。**推導替編劇做決定，提示只指出落差。**

匯出前的清單把它列為**提醒但不阻擋**，與草稿分開 —— 草稿是確定要被略過的，這裡則可能是正確狀態，拿去攔匯出是製造假警報。

#### 群演

「描述 ＋ 人數」的**清單**（可多組：`咖啡廳客人 x8、服務生 x2`），掛在場次上。

**不是人物**，因為它缺乏跨場次的身分連續性（第 3 場的路人與第 7 場的路人不是同一批人）。若塞進人物，「這個人物出現在哪幾場」就會失去意義。

- **進場次表第一層**（唯一的消費者），**不進 PDF**。
- **入口不走 `/` 選單**（否決 `/extra`、`/crowd`）—— 群演是 metadata 欄位而非區塊，放進 `/` 會讓它的語意從「建立東西」擴成「建立東西＋編輯 metadata」。入口是**簡表的群演欄** ＋ **對白人物欄的自動補全**（可在那裡直接新建一筆，解掉「寫對白寫到一半要跳去簡表」的心流問題）。
- 描述可跨場次自動補全，但**只補字串、不建立連結** —— 不做「這是同一批人」的假承諾。
- **「臨演」與「群眾演員」不拆**（劇本這一層沒有資訊可以區分）；**「特約」不是群演** —— 那是有台詞的小角色，已被「人物」吸收。

#### 多值欄位的輸入規則（同時適用地點欄與登場人物欄）

> **標點（`、` `，` `,` `；` `;`）是分隔符；全形半形空白一律視為名字的一部分。**

空白全排除是因為中文列舉本來就用頓號，而**注音的空白鍵是選字鍵、Enter 是送出鍵**，兩者在組字期間都被 IME 吃掉 —— 把分隔綁在那種鍵上正是[票券 03](./issues/03-editor-prototype.md) 那個 bug 家族。

**即時切成 chip**（地點是實體，編劇必須立刻看到是命中既有實體還是新建），Backspace 還原成可編輯文字，貼上用同一規則解析。

### 4.8 草稿場次

```
是草稿 = 使用者手動標記為草稿  或  metadata 不完整
```

**是推導出來的狀態，不是要手動「轉換」的狀態** —— 因此沒有任何時刻有東西在編劇背後改他的文件。欄位填完它自己就變回正式場次。資料模型只多一個 `manualDraft` 布林值，**不存狀態機**。

- **不參與正式場次編號**，另有推導標籤 `S11[D1]`、`S11[D2]`，**錨定前一場**（錨定後一場會與真正的 `S12` 撞號）。排在全劇第一場之前 → `[D1]`。
- **不進 PDF，不進場次表。**
- **父場次是草稿 → 子場次一律是草稿**；子場次可以單獨是草稿而父場次不是。
- 「不再提醒」記的必須是 `sceneId`，標籤只負責讓人在彈窗裡看懂是哪一場。
- 草稿與正式場次在編輯器中要有視覺區隔。

**「metadata 不完整」的判定隨 `內外` 的值改變**：`內外＝雜景` 時地點欄留空**合法**（§4.3）。

**三條會讓場次自動成為草稿的不變式**（零新機制，全部接到這條規則上）：

- 同一群組的成員之間 metadata 完全相同
- 子場次的 metadata 與主場次完全相同
- metadata 有空欄（雜景的地點欄除外）

### 4.9 交付與分享

#### 交付 = 一則承諾

> 「這份內容，在你之後改稿時仍保持不變。」

**判準是承諾而非通道**（不變式 D，§11）。它凍結的是該次承諾的**內容與語意推導值**（場次號），不是像素。

**存的是推導的結果，不是推導的輸入** —— 因為編號演算法還會改，若存輸入（當時的場次樹）日後重跑會算出不同的號碼，等於讓程式碼回頭改寫歷史。交付的全部價值就在於它與紙上那個字永遠一致。

**交付是事件不是狀態**：同一份劇本重複匯出＝兩筆交付，不去重。**「產物尚未成功產生」是一個合法狀態**，不是待清理的異常 —— 不為它設狀態機旗標，使用者重試即是重新渲染同一筆。

#### 分享 = 一次具有獨立 identity 與生命週期的對外分享關係

**劇本是它的欄位，不是它的身分。** 論證是結構性的：**凍結連結在劇本身分下沒有位置可站** —— 它指的不是劇本的現在，而是劇本的某個過去。

兩種分享對應兩種**意圖，而不是一個開關**：

| | 是什麼 | 怎麼產生 |
|---|---|---|
| **即時分享** | 給人看最新稿 | 分享面板上唯一的東西 |
| **凍結分享** | 一筆交付的公開把手（＝我在交稿） | **匯出 PDF 的副產品** |

**否決 toggle**：Figma 把凍結藏進版本歷史、被抱怨十年，是現成的失敗案例。凡是要使用者理解「活 vs 凍結」這組詞才能正確分享的設計，都會退化成那個樣子。使用者表達意圖的方式是他本來就懂的「我在交稿 vs 我在給人看」。

**劇本與場次表是同一個 share 的兩個視圖**（頁內切換），不是兩條連結。

**v1 的分享零配置** —— 視圖組合固定、沒有標題、沒有密碼。選這個 identity 是為了讓凍結有地方站，不是為了長出開關。

**紅線**：沒有版本列表、沒有比較、沒有還原。一次交付＝一條連結，如此而已。

## 5. 編輯器 schema

**這一節是 [ADR-0007](../../docs/adr/0007-document-as-single-authority.md) 說的「唯一權威」的具體形狀。**

### 5.1 節點表

```
doc          := (scene | sceneGroup)+
scene        := (sceneBlock | subscene)+           isolating, defining
subscene     := sceneBlock+                        isolating, defining
sceneGroup   := groupMember+ groupFragment+
groupMember  := （無內容）                          atom
groupFragment:= (sceneBlock | subscene)+

sceneBlock   := action | dialogue | insertShot
action       := inline*
dialogue     := inline*                            （人物與發聲方式在 attrs）
insertShot   := inline*
```

| 節點 | attrs |
|---|---|
| `scene` | `sceneId`, `時間`, `內外`, `地點`, `登場人物`, `群演`, `manualDraft`, `dismissedCharacterIds` |
| `subscene` | 同 `scene` ＋ **`種類`**（`插入｜接續`） |
| `sceneGroup` | **`groupId`** |
| `groupMember` | 同 `scene` 的全部 metadata attrs（含 `sceneId`） |
| `groupFragment` | `memberId`（指向同群組某個 `groupMember` 的 `sceneId`） |
| `dialogue` | `人物`（`{ id, 顯示名 }`）、`發聲方式` |

**schema 直接保證的三件事**（不是執行期檢查）：

1. **深度固定兩層** —— `subscene` 的內容規則不含 `subscene`。
2. **群組不能巢狀** —— `groupFragment` 的內容規則不含 `sceneGroup`。
3. **一個場次不能同時屬於兩個群組** —— `groupMember` 住在唯一一個 `sceneGroup` 節點裡，樹結構本身保證。

**場次之外沒有可編輯的空間。** 所有可編輯內容都在 `sceneBlock` 裡，而 `sceneBlock` 只出現在 `scene`／`subscene`／`groupFragment` 底下。代價是匯入既有劇本沒有落地區 —— 匯入已排除在 v1 外。

> ⚠️ 文件頂層從 `scene+` 放寬為 `(scene | sceneGroup)+`。這不是鬆綁「文件只由場次組成」，
> 因為 `sceneGroup` 只是一群場次的容器，沒有自己的可編輯空間。

### 5.2 群組的形狀 —— 本規格書新裁決

[票券 04](./issues/04-screenplay-storage-model.md) Q5(e) 把兩個問題留給本文：**群組在 schema 裡是不是節點？需不需要 id？**

**裁決：是節點，且有 id（`gr_` 前綴 nanoid，使用者永遠看不到）。**

**為什麼是節點而非旗標**（例如在成員場次與片段上各掛一個 `groupId` attr、平坦排在頂層）：那是 [ADR-0003](../../docs/adr/0003-inserted-scenes-as-subscenes.md) 已經否決過的「平坦 ＋ 旗標」家族第三次出現。做成節點時，「群組不能巢狀」與「一個場次不能屬於兩個群組」由樹結構免費保證；做成旗標時，兩者都退化成執行期檢查，而且文件狀態本身能說謊（一個 `groupId` 指向不存在群組的場次）。

**為什麼成員是另一種節點而非 `scene`**：成員場次**沒有自己的內容**（[ADR-0004](../../docs/adr/0004-scene-groups-for-intercut.md) 明訂，內容在片段裡）。這是真實的結構差異，不是同一個東西的兩種寫法 —— 用同一個 `scene` 節點就得把它的內容規則放寬成可為空，那會讓**所有**場次都能是空的。`projectScenes()` 對 `groupMember` 與 `scene` 一視同仁（同樣的 metadata、同樣進場次表、同樣佔一個頂層場次號）。

**為什麼群組要 id，而片段不要**：

- **片段不要 id** 是 [ADR-0006](../../docs/adr/0006-continuous-action-as-continuation-subscenes.md) 保護規則 3 明文禁止的，理由是「插入子場次把一個片段切成兩半」會製造一個沒人需要回答的繼承問題。**片段會被切開，群組不會。**
- **群組要 id**，因為 command 層要定址它而不能用位置（§6.3 的准入判準：以 id 定址，不以位置定址）。`assignFragmentToMember(groupId, fragmentIndex, memberId)` 裡的 `fragmentIndex` 是呼叫當下由編輯器從游標算出的**傳遞參數**，不被任何東西儲存 —— 那不違反保護規則 3，規則禁的是**持久化的引用**。

**去重規則一體適用**：`groupId` 與 `sceneId` 走同一套（§6.5）。

**片段的正規化**：相鄰兩個片段若歸屬同一個成員，`appendTransaction` 合併成一個（標 `addToHistory: false`）。理由與去重相同 —— 那個區別在模型裡沒有意義，而 ADR-0006 寫下的重疊群組遷移路徑假設片段是極大的。

### 5.3 attr 的 null 鐵律

> **任何可能裝 `null` 的 attr，schema 預設值必須也是 `null`。**

這條不是風格，是 [票券 19](./issues/19-yjs-migration-spike.md) 的探針實測結果：**`y-prosemirror` 不儲存 null attr**，回程一律由 schema 預設值填補。`default: '一般'` 的欄位裝 `null`，往返後**靜默變成 `'一般'`** —— 遷移不會報錯，只會改掉編劇的稿。

**v1 的具體裁決**：

| attr | 裁決 |
|---|---|
| `時間`、`內外`、`地點`、`登場人物` | **可為 null，`default: null`**（空 metadata → 自動草稿，這是防呆的地基） |
| **`發聲方式`** | **不允許 null**。三值列舉，`default: '一般'`。⚠️ 這是[票券 19](./issues/19-yjs-migration-spike.md) 點名的受害候選 —— 「要嘛預設 null、要嘛不允許 null，不要兩者兼有」 |
| **`種類`** | **不允許 null**，無預設，建立時必填（它是編劇按下哪個入口的宣告，系統不代填） |
| `manualDraft` | 不允許 null，`default: false` |

### 5.4 場次號：decoration，不進文件也不進資料庫

`projectScenes(doc)` 是**純函式**，瀏覽器與 Node 都能跑。場次表、PDF 匯出、唯讀分享各自呼叫它；編輯器也一樣，只是得透過 ProseMirror decoration 才能讓 node view 知道該重繪。

**決定性理由**：場次號在系統裡**從來不是 key** —— 約束 1 說下游一律掛 `sceneId`，沒有任何查詢用場次號 join。它只在渲染的那一刻才有意義，所以就該在渲染時才算。存成 node attribute（衍生快取）會讓 PDF 匯出必須選擇「相不相信這個欄位」：相信則可能印出錯的場次號（而水準線是「拿去參賽會被接受」），不信則該欄位只剩說謊的能力。

**推導規則**：

```
正式場次（非草稿）依文件順序編 1..N
  ├── scene       → "12"
  ├── groupMember → "26" / "27" / "28"   （各佔頂層號，群組不佔號）
  └── subscene    → "5.1"                （父場次號 + 點號 + 該父場次底下第幾個子場次）
草稿場次跳過，另編 "S11[D1]"（錨定前一個正式場次）
```

**約束 1 在本規格中以同一形狀出現三次**：場次號、子場次號、草稿標籤都是推導值，都不進資料庫。

### 5.5 schema 必須 isomorphic

**node spec 與 node view 分家。** schema 那半是獨立模組，不含任何瀏覽器相依 —— 它要在 Node 裡跑（PDF 匯出、場次表推導、伺服器端 command），也要在日後給 `y-prosemirror` 吃同一份。[票券 19](./issues/19-yjs-migration-spike.md) 已實地檢驗通過。

## 6. 儲存模型

**一句話：doc 是唯一權威，寫入只走 domain command 層。** 見 [ADR-0007](../../docs/adr/0007-document-as-single-authority.md)。

### 6.1 邊界一覽

```
canonical document   = ProseMirror JSON
storage              = jsonb
schema version       = doc_schema_version
concurrency          = doc_seq
write boundary       = commands
read boundary        = projection
migration            = schema migration
backup               = append-only before-image（recovery，不是版本歷史）
future collaboration = Yjs（票券 19 已驗證可行）
```

### 6.2 資料表

關聯式表只裝**本來就不在 doc 裡的東西**。它們是衍生的或獨立的，永遠不是 doc 內容的第二份副本。

| 表 | 欄位 | 備註 |
|---|---|---|
| `projects` | `id`, `type`（單一劇本專案）, `title`, meta 欄位 | v1 只有一種 type |
| `screenplays` | `id`, `project_id`, `doc jsonb`, `doc_schema_version`, `doc_seq` | **一個劇本一列** |
| `characters` | `id`（`ch_`）, `project_id`, `name`, `description` | append-only |
| `locations` | `id`（`lo_`）, `project_id`, `name` | append-only，**無描述欄** |
| `documents` | `id`, **`project_id`（必填）**, **`screenplay_id`（可為 null）**, `kind`, `body jsonb`, `doc_schema_version`, `doc_seq` | 見不變式 F |
| `deliveries` | `id`, `screenplay_id`, `created_at`, `payload jsonb` | append-only、**唯一刻意不可變**、**無** `doc_seq`／`doc_schema_version` |
| `share_links` | `id`, `screenplay_id`, `delivery_id`（null ＝ 即時分享）, `token`, `created_at`, `revoked_at` | token **opaque 且不可枚舉** |
| `screenplay_backups` | `id`, `screenplay_id`, `doc jsonb`, `created_at` | append-only before-image、**無 UI** |

**⚠️ 資料庫沒有 `scenes` 表。** 理由同「存在＝被引用」：場次「存在」就是它在那棵樹上。登記簿等於第二份權威，而它唯一的好處（外鍵完整性）在 v1 沒有消費者。

**這同時回答了「id 如何在編輯器與資料庫之間保持一致」：不必保持一致，因為資料庫沒有要跟著同步的副本。** 唯一的一致性要求是**同一份 doc 內 id 不得重複**（§6.5）。

**`documents` 的 `kind` 與層級**（不變式 F：`kind` 固定其合法層級，不由使用者決定）：

| `kind` | 層級 | 說明 |
|---|---|---|
| `交件大綱` | **專案** | 可多份，各自命名，附字數計數器 |
| `角色設定表` | **專案** | 有序的人物引用清單，`body` 是極簡 PM doc（每個節點一筆人物引用） |
| `分場大綱` | **劇本** | 自由文字，不與場次關聯 |

每個 `kind` 有**自己的 node schema 與自己的遷移鏈**，所以那一列的 `doc_schema_version` 是**該 kind 的版本**，不是一個全域數字。

> **⚠️ 角色設定表選 PM doc 是有效期條件的，不是永久不變量。**
> 成立的前提是它的職責僅止於「有序人物引用清單 ＋ PDF 排版來源」。
> 若它演化為具有篩選／分類／群組／搜尋能力的 **entity browser**，就應重新評估它是 document 還是 **projection/view**。
> 觸發點可指名：地圖 Not yet specified 的「按實體聚合的地點／人物清單視圖」畢業之時。

**為什麼角色設定表選 PM doc 而非關聯表 `(screenplay_id, character_id, order)`**：關聯表的誘惑是可以掛真外鍵，但那個外鍵**沒有消費者**（人物 append-only、永不刪除），而代價是**引用會有第二種住所** —— 「存在＝被引用」的判定得同時掃 doc 又掃表，§6.6 的規則也要長出第二套實作。收進 doc 後，**引用只有一種住所**，而且拖曳排序、⌘Z、command 層、projection 全部免費復用。

**為什麼交件大綱與角色設定表掛專案而非劇本**：它們描述的創作單位是**整部作品**。v1 沒有可觀測變化（1:1 之下兩層等價），這條買的是影集那天接得上。

### 6.3 寫入邊界：domain command

```
domain command（意圖） → ProseMirror Step（機械變更／日後的傳輸單位） → doc（唯一權威、唯一被持久化）
```

**command 是程式碼，不是資料。** isomorphic TS 模組、純函式、吃 doc 吐新 doc。**否決「command 是可序列化的訊息、可寫 log、可重播」** —— 那會製造第二個權威（log 與 doc 誰是真相），不知不覺走進 event sourcing；而它想要的東西 ProseMirror 已經給了：**`Step`**。

**真正的獲利不是「多入口」**（v1 只有一個寫入入口）**，而是給不變式一個家 —— 且是在瀏覽器外可單元測試的家。**

**准入判準**（免得長成「每個 Tiptap command 包一層」的空殼）：

> 一個 domain command 要能進來，必須至少滿足其一：**它強制執行了一條不變式**，或**它以 `sceneId`／實體 id 定址（而非以位置定址）**。兩者皆非的留在編輯器裡當一般 Tiptap command。

**edge boundary 規則**：

> **UI 與 application 層不得直接依賴編輯器的實作細節** —— 包含 transaction、mutation、`history`、以及以**位置**定址的任何東西。**凡具備 domain 或 application 意義的操作，一律透過 command abstraction 執行。**

⚠️ 這條**不是**「不准用 ProseMirror」。**編輯器套件內部**照常直接用 PM API（node view 怎麼畫簡表、`Tab` 怎麼排環、拖曳落點判定、注音組字期間選單不動作）。規則管的是**跨出編輯器邊界**的線：頁面、伺服器、日後的 API、日後可編輯的場次表。**編輯器對外只曝露兩樣東西 —— commands（寫）與 projection（讀）。**

**意圖 vs 手勢的分界**（這條線一鬆，command 層就會被 UI 細節污染而測不動）：

| 手勢（留在編輯器） | 意圖（就是 command） |
|---|---|
| `Tab` 怎麼排環 | `setBlockType(blockId, type)` |
| `/` 選單怎麼過濾、IME 組字期間不動作 | `insertSubscene(parentId, kind, meta)` |
| `⌘+1/2/3` 直接定址、`⌘+4` 是無效鍵 | `assignFragmentToMember(groupId, fragmentIndex, memberId)` |
| 拖曳時哪些位置不畫落點線 | `moveScene(sceneId, target)` —— **它自己也要拒絕非法目標** |
| 自動補全選單三列怎麼排 | `createLocation(name)` / `renameLocation(id, name)` |

最後一列是**縱深不是重複**：落點線是 UI 的預防，command 的拒絕是模型的保證；UI 只擋得住滑鼠，擋不住伺服器端呼叫或日後的 API。

**伺服器端可執行**：ProseMirror 是純 TS，`EditorState`／schema／transaction／command 在 Node 裡都跑得動；瀏覽器專屬的只有 `EditorView` 與 node view。

### 6.4 讀取邊界：projection

**場次表不建投影表**，在讀取當下由純函式推導：

```ts
projectSceneTable(doc): { rows: SceneTableRow[], missingRefs: MissingRef[] }
```

**這個簽名裡沒有 doc 以外的輸入，型別本身在強制「場次表是零新增資訊的投影」** —— 有人想加一欄製作端另填的東西時會發現簽名裝不下，比文件裡的一句話有力。

PDF、場次表、匯出前草稿清單**共用同一次走訪**（場次號、草稿判定、群組成員展開），不會長出兩套會分歧的實作。

**成本**：130 場的 doc 幾百 KB，撈 jsonb ＋ `Node.fromJSON` ＋ 走一遍樹是**十毫秒等級**；而 PDF 匯出與分享連結本來就要撈整份 doc。投影表買到的很少，要付的是**推導漂移**（何時重算、失敗怎麼辦、怎麼發現與 doc 不一致）。

**投影表日後要加是免費的**：它就是這個函式輸出的**快取**，key 是 `doc_seq`，要重建就 `DROP` 再跑一次。而**那張表可以有真外鍵**，因為它是衍生的、可重建的。

⚠️ **快取與快照方向相反**：快取要跟上 doc，**交付與凍結分享連結是快照 —— 刻意不可變、抵抗 doc**。

### 6.5 場次 id 的產生與去重

`sceneId`（與 `groupId`）**由編輯器端產生並存在節點的 attr 上**。

**兩個機制分屬兩個層次，各自只做一件事**：

| 層次 | 機制 | 職責 | 它知道什麼 |
|---|---|---|---|
| **剪貼簿邊界** | `transformCopied` / `transformPasted` | **語意判斷**：這次貼上是延續既有身分，還是建立新身分 | 來源劇本、目的劇本 |
| **文件不變式** | `appendTransaction` | **結構修復**：同一份 doc 內不得有重複 id | 只有這棵樹，不需要 provenance |

**`appendTransaction` 因此永遠不必知道來源**，它是**最後一道防線**，對任何來源都成立（剪貼簿、程式化插入、日後的匯入、我們自己的 bug）。

**去重規則**：

> 只在偵測到重複時動作，改的一律是**本次 transaction 新插入的那個節點**（step 資訊拿得到）。無法判定時的後備規則是**文件順序在前者保留**。

**碰撞本身就是判別器，不必猜使用者意圖**：剪下時原節點離開文件 → 貼上不碰撞 → 去重不觸發 → **id 天然保住**（約束 1）；複製時原節點還在 → 貼上必碰撞 → 去重觸發 → **id 換新**。

**跨劇本貼上 ＝ 鑄造新身分。** 一份劇本的場次，身分只在那份劇本裡有意義。作法是在剪貼簿內容上蓋一個來源劇本的印記，**來源劇本 ≠ 目前劇本時一律重新產生 id**。全域唯一是實作結果，不是要去維護的規則。

**去重的 transaction 標 `addToHistory: false`** —— 否則複製貼上 → 去重改 id → ⌘Z → 退回到重複 id 的狀態。它不是使用者的動作，是模型的修復。

**適用範圍**：`scene`、`subscene`、`groupMember`、`sceneGroup` 完全相同處理。**群演不去重** —— 它是場次限定實體、id 只在該場次內有意義，跟著場次被複製過去是**正確的**。

### 6.6 引用完整性：寫入嚴格，讀取容忍

> **⚠️ 這兩半必須並排讀。單獨拿走任何一半，後人都會把另一半當成 bug 去「修」。**

| 路徑 | 規則 |
|---|---|
| **寫入** | 所有 domain command **必須拒絕**建立對不存在實體的引用。建立實體時，**先建立實體、再寫入 doc**。 |
| **讀取** | doc **必須允許**引用不存在的實體。懸空引用不影響渲染 —— **顯示名是渲染權威（fallback 來源）**，PDF 照印、場次表照印，只是少一條可聚合的連結。 |

這確保的是 **command-level referential integrity，不是真的 FK**，所以**系統不能保證懸空引用不會發生**。

**「先建立實體、再寫入 doc」不只是建議順序，它是上一條能成立的前提** —— 檢查對象是實體表，反過來的話每一次建立新人物的 command 都會被自己的不變式擋下。

**為什麼有人會想「修」**：有人會想在 projection 裡擋掉懸空引用 —— 那會讓 PDF 少印一個地點，是投獎者最糟的失敗模式；也有人會想讓 command 放行以求彈性 —— 那會讓日後要加聚合投影表時，doc 裡已經累積了髒引用。

**❌ 否決「載入時用顯示名自癒補一筆」**：(1) 它是**讀取路徑的寫入**（外人打開唯讀分享連結時寫我們的資料庫）；(2) 補出來的名字**是錯的** —— 漸進揭露下前 8 場的顯示名是「未知大樓房間」，自癒會把假名鑄成正式名字，而製片要知道去哪裡拍。**用一筆說謊的資料換掉一個誠實的缺口，是虧的。**

**引用缺失只做診斷**：`projectSceneTable` 額外回傳 `missingRefs`。

> **`missingRefs` 是 projection 的診斷輸出（diagnostic output），不是業務輸出。**
> 不參與渲染、不被持久化、消費者的業務邏輯不得讀它。

伺服器端解析 doc 時輸出一筆結構化日誌，**不對編劇曝露**（對他沒有可行動的資訊，顯示名照印，沒有任何東西被少印 —— 跳警告只是假警報）。真的出事時（資料庫還原）看伺服器日誌，讀者是我們不是編劇。

### 6.7 並行、遷移、備份

| 欄位 | 是什麼 | 什麼時候變 |
|---|---|---|
| `doc_schema_version`（integer） | 這份 doc 用哪一版 node schema 寫的 | **部署時**（我們改了 schema） |
| `doc_seq`（bigint） | 並行控制 token | **每次成功改變 canonical document state** |

一個隨程式碼走、一個隨資料走。**命名刻意避開「版本／版次／revision／鎖定」**，因為版本鎖定是已否決的功能：

> `doc_seq` 是每一次**成功改變 canonical document state** 的 optimistic concurrency token。它不是自動存檔次數、不是版次、不是任何產品概念。不對使用者曝露，與交付無關。

**`doc_schema_version` 存成欄位，不存在 doc JSON 裡** —— 查得到「還有幾份停在舊版」、載入前就知道要不要遷移、避免兩個權威。

**遷移採 lazy，且永遠在記憶體中發生；寫回只發生在本來就會寫的路徑**（使用者存檔、伺服器端 command），**讀取路徑一律不寫回** —— 否則 PDF 匯出／場次表／分享連結都會觸發資料庫寫入，且會製造兩個 client 同時載入舊 schema 互相覆蓋的 race。代價是「只被讀從不被編輯」的 doc 永遠停在舊版 —— 但遷移鏈無論如何都得留著，所以不算代價。

**原子性規則**：**schema migration、doc 更新、`doc_seq` 遞增是同一個原子操作**，並沿用 `doc_seq` 的並行檢查。

#### 自動備份

**風險是有牙齒的**：⌘Z 只活在瀏覽器分頁裡，分頁一關就沒了。編劇失去的不是一個功能，是三個月的稿。

- 寫入的是 **before-image**（被這次存檔覆蓋掉的那一份 doc，成本幾乎為零 —— 它本來就在手上）。
- **無查閱 UI，v1 全部保留。** 加 UI 就是把保險變成功能，會立刻拖出「怎麼比較差異」「怎麼命名」「能不能只還原一半」一整串，而版本鎖定已被否決。要救稿時從 `psql` 手動撈。
- **它是 recovery 機制，不是版本歷史功能。**
- **原子性**：凡依 backup policy 判定需要建立備份的那次存檔，**備份與 canonical document update 必須是同一個 atomic state transition**。
- **觸發判準是伺服器端的純時間判定，不由 client 宣告**（client 會開兩個分頁、會離線、會當掉；更糟的是**分頁不關** —— 擺著三天就是「一個階段」）。判定只看備份表的 `MAX(created_at)`。

**唯一的硬保證（規格層級）**：

> **距這份劇本的上一筆自動備份 ≥ 2 小時**時，該次存檔先寫一筆備份。
> 對外可講的承諾：**「任何時候最多只會退回兩小時。」**

**降級為實作層 heuristic（非不變量）**：「距上次成功存檔 ≥ 30 分鐘就視為新的一次坐下」。它的語意是**系統對使用者行為的推測**，而規格該描述系統能保證的事。它安全地待在實作層，是因為**它只會讓備份變多、絕不會變少**。

**這條規則住在 persistence 模組裡** —— 呼叫端只知道「存」，完全不知道有備份這回事。

#### 寫入放大（誠實的代價）

每次自動存檔重寫整份 doc（幾百 KB，走 TOAST ＋ WAL）。v1 不是問題（單人、單劇本、寫作是低併發活動），處理方式是**調 debounce 而不是改資料模型**：用「停頓」而非「節流」（打字停 2～3 秒才存，加一個最多每 15 秒強制存一次的上限）。真痛了再說，那時的解法是**傳 Step 而不是傳整份 doc**，仍然不動儲存粒度。

**欄位型別 `jsonb` 而非 `text`**：投的是除錯能力（出事時能在 `psql` 裡 `doc -> 'content' -> 0 -> 'attrs'` 看一眼）。真被寫入放大咬到時，`jsonb` → `text` 是一行 migration。

## 7. 編輯器與輸入體驗

**選型：Tiptap**（3.30.x）＋ React。原型已驗證，見 [`prototypes/editor/`](./prototypes/editor/)。**變體 A · 內嵌簡表** —— metadata 直接嵌在編輯器裡、像一列簡表。

### 7.1 鍵盤與手勢總表

| 手勢 | 動作 |
|---|---|
| `/next`、`⌘+Enter`、場次腳部按鈕 | **建立下一場**（三個入口共用同一條路徑） |
| `Tab` / `Shift+Tab` | **只改變游標所在區塊的型別**（動作 → 對白 → 插入畫面），**永遠不動容器** |
| `/insert` | 建立 `種類＝插入` 的子場次 |
| `/continue-to` | 建立 `種類＝接續` 的子場次 |
| `/back-to` | **不建立任何東西**，游標跳回主場次 |
| `/` →「對剪到…」 | 建立場次群組 |
| `⌘+1` / `⌘+2` / `⌘+3` | 切換游標所在片段的歸屬（直接定址；超出成員數是無效鍵） |
| `⌘+A` | **漸進式全選**：區塊 → 這一場的內文 → 整場（含 metadata）→ 整份 |
| 雙 Enter | 在子場次末尾的空區塊按 Enter 提升出去（`liftEmptyBlock`） |
| ⠿ 拖曳 | 場次、子場次、區塊，可跨層 |
| 點場次號 `SX` | 選單 → 搬移到…／與其他場次對調…／刪除這一場 |

**焦點串接**：`/next` → 第一個 metadata 欄位 → Tab 逐欄 → Tab 進正文；對白的人物欄 → Tab → 台詞。**欄位上的 Tab 要 `stopPropagation`。**

⚠️ **用滑鼠點的入口必須自己傳插入位置** —— 靠 selection 推算會插到游標所在的那一場後面。

**`/insert` 與 `/continue-to` 在主場次與子場次裡都可用，語意不變** —— 它們永遠是「在本主場次底下建立一個子場次」。深度兩層那條規則讓「在子場次裡按下去」只有一種合法解讀（建立兄弟），沒有歧義。

### 7.2 為什麼建立場次是 `/next` 而不是 `/scene`

文件是場次序列，你永遠在某個場次裡打字，「在場次裡建立場次」語意上是矛盾的；真正的動作是**序列性**的。

### 7.3 為什麼 Tab 不參與階層

**不變式：Tab 只改變游標所在區塊的型別，永遠不動容器。** 環在任何深度都是同樣三個成員，主場次與子場次一致。

推演過「主場次環 4 個含插入子場次」的版本：**它破壞了環的不變式** —— 環能當心流按鍵，靠的是「按下去總能再按回來」。從對白繞回動作必然經過「插入子場次」，而經過就是生成；生成那一步同時換了游標的層級與環的成員（4 → 3），於是繞不回原本那一層。**一個成員會改變環本身的環，就不是環了。**

也否決了折衷版（只准從空的動作區塊轉進去）：**同一顆鍵依看不見的狀態做不同的事，是那批 bug 的家族特徵。**

**通用規則**：

> **會產生永久錨點的動作，入口只有一個，而且那個入口的名字要說出它會建立東西。**

因此 `@` 不能一鍵兩用（它的語意是「指向已經存在的東西」）；「套用既有場次的時空」掛在 `/insert`／`/continue-to` 的**第二步**。`/back-to` 不受此規管，因為它不建立永久錨點。

### 7.4 時間欄下拉選單依種類排序

| 種類 | 排法 |
|---|---|
| **接續** | 把主場次的值**置頂並標注「（原場次）」** |
| **插入** | 只標注、**不置頂**（閃回的時間常刻意與主場次相反） |

**地點欄兩者都不置頂** —— 接續的前提就是地點變了，主場次的地點保證是錯的答案。

⚠️ **這不是預填**：欄位仍然是空的，草稿防呆照常運作。它在錯誤發生**前**作用，比事後跳提示好。

### 7.5 拖曳排序

**三個方向都允許**：子場次拖到主場次之間 → 升級；主場次拖進場次內部 → 降級；區塊跨層拖。

判準：拖曳是**明確的使用者意圖，不是誤觸**，所以可以做鍵盤路徑不准做的事。而且三個方向都**無損** —— `sceneId` 全程存活，變的只有推導出來的場次號。

**必須拒絕的落點**：帶著子場次的主場次不能被拖進另一個場次（會生出第三層）。**UI 表現是那些位置不畫落點指示線**，而不是允許放下再彈錯誤。

**⚠️ 規格不能只寫「支援拖曳排序」，必須連成本一起寫**：

1. 得繞過 `isolating`（`isolating` 保留 —— 拿掉會讓跨場次的鍵盤選取與刪除把兩場合併，`sceneId` 錨點隨之消失）
2. 得處理「搬走最後一個區塊」後的空場次（沿用 `moveNode` 的「補一個空動作區塊」）；階層化多一個變體：主場次自己最後一個區塊被拖走、只剩一個子場次
3. 得跟 ProseMirror 的原生拖放搶事件（`dragGuardDOMEvents`）
4. 可拖的東西從 2 種變 3 種，落點合法性從「同 kind」改成**依位置計算**
5. `isolating` 多一層巢狀，鍵盤選取／刪除／貼上的邊界行為要重測

### 7.6 中文 IME

**不是架構障礙。** 問題不在 Tiptap，是受控輸入的經典 bug：組字期間回寫文件會清掉組字緩衝。**修法是組字期間只更新本地狀態、`compositionend` 才回寫**（原型 `src/cjk-input.tsx`）。這解除了「metadata 不能放在編輯器內部」的疑慮。

**注音組字期間，自動補全選單完全不動作。**

### 7.7 ⚠️ 已知的成本：六個 bug 是同一個家族

**每一個自訂互動都要跟一層 Tiptap／ProseMirror 的預設行為協商。** 這是選型的實質代價，實作時會反覆遇到：

| 現象 | 根因 |
|---|---|
| 內容掉到場次外，變成孤兒段落 | StarterKit `Paragraph` 的 parse priority（1000）蓋過 `p[data-type=…]`，三種區塊型別要設 `priority: 1100` |
| 新增場次後，後面場次的編號不更新 | node view 只在「自己的節點變了」時重繪；`ReactNodeViewRenderer` 收到 decoration 變更會直接 `return true` 跳過 |
| ⌘+A 被吃掉 | Tiptap 內建 Keymap 的 `Mod-a` 要靠 `priority` 搶，不是註冊順序 |
| 拖曳吃字、跑版、偶爾拖不動 | PM 的原生拖放跟自訂 handler 搶同一個事件；落點狀態會被 `dragleave` 清掉，提早 return 又沒 `preventDefault()` |
| 選取反白畫不出來 | React 的 `className` 洗掉 PM 透過 decoration 寫上去的 class —— **兩邊不能碰同一個屬性** |
| 漸進式全選在前兩層打轉 | `TextSelection.between()` 會把端點正規化到最近的合法文字位置，拿正規化前的原始位置去比對永遠不成立 |

**另一類值得預期的坑**：ProseMirror 的同一個位置有兩種表示法（結構位置 vs 正規化後的文字位置）。

### 7.8 場次引用 `@`

- 正文**只印場次號**（`S5`／`S5.1`），**連動**。
- **metadata 一律走快速參考**（彈窗或抽屜）即時讀取，**不寫進正文**。

**判準是那串字是誰寫的**：人物與地點的顯示文字是編劇親手寫下的（漸進揭露是敘事手段，所以快照才對）；場次號與場次 metadata **不是寫在引用處的字，而是別處資料的鏡子** —— 鏡子快照就會說謊，而且是最難察覺的那種，因為它看起來仍是一句通順的話。

**階層在這裡免費多給一個好處**：引用子場次顯示 `S5.1`，日後它被拖出來升級成主場次，引用自動變 `S6` —— 引用存的一直是 `sceneId`。

**快速參考是共用元件**，三處都用：`@` 選單裡展開預覽、`/insert` 的場次選擇器裡預覽、點擊正文既有引用。

## 8. 場次表規格

**第一層投影：純從劇本推導，零新增資訊。**

⚠️ **判準不是「[票券 02](./issues/02-scene-breakdown-fields.md) 查出的那五欄」，而是「能不能從劇本推導、零新增資訊」。**

| 欄 | 來源 | 備註 |
|---|---|---|
| 場次號 | 推導 | `12` / `5.1` / `26`；草稿不出現 |
| **景**（內外） | metadata | 業界欄名 |
| **光**（時間） | metadata | 業界欄名 |
| **地點** | metadata | ⚠️ 業界順場表此欄名為「場景」，**本專案輸出時一律標為「地點」**（[ADR-0001](../../docs/adr/0001-scene-and-location-terminology.md)） |
| 登場人物 | metadata | |
| **群演** | metadata | 編劇寫的、從劇本推導，所以屬第一層 |

**地點欄與登場人物欄印 `實體名（這一場的顯示名）`**，**只在兩者不同時才印括號**（`海豚公寓房間（未知大樓房間）`、`小明（男子）`）。括號裡放的是**這一場的**顯示名而非所有別名 —— 場次表的一列是一個場次，而製片是拿場次表對照 PDF 看的，列出別的場次的叫法反而對不上。

**進場次表的東西**：

| | 進不進 | 說明 |
|---|---|---|
| 場次 | ✅ | 一列 |
| **子場次** | ✅ | **自佔一列**，緊接主場次之後，縮排僅作視覺次級。附屬列（塞進主場次的儲存格）不能被排序也不能被篩選，等於 metadata 白做 |
| **群組成員** | ✅ | 各自一列（各佔頂層場次號） |
| **群組本身** | ❌ | 不佔號、不進表 |
| 草稿 | ❌ | |
| 子場次的 `種類` | ❌ | 消費者在第三層。現在加一欄是替一個還不存在的消費者改已定案的規格 |

**折返是免費的** —— 主場次在場次表上仍然只有一列，因為折返的內容是主場次自己的區塊而非新場次。

**雜景是刻意接受的資訊密度損失**：不拆的雜景印出的是編劇填的地點清單，地點留空時印推導文字「參照敘述」。

**❌ 第二層與第三層都不做**：服裝代號、美術道具、備註、預估時長是**製作端另填的**（[票券 02](./issues/02-scene-breakdown-fields.md) 發現順場表的「男一～女三」欄填的是**服裝代號**而非出席勾選，業界把「誰出場」與「穿哪套」壓縮在同一欄 —— 這反而印證了分層模型）。

**❌ 場次表沒有自己的寫入路徑。** 它是零新增資訊的投影，要改就回頭改 doc（走 command 層）。

> **⚠️ 業界背景**：調查到的表單**清一色以會變動的場次號互相參照，沒有任何一個使用永久識別碼**。
> 所以「場次是穩定錨點」在業界**無範本可循，是我們要自建的機制** ——
> 這同時意味著「重排場次後下游文件對不上」是業界真實存在且未解的痛點，可能是本產品的隱藏賣點。

## 9. PDF 匯出規格

**水準線：拿去參賽會被接受。不追求排版精美。**

**v1 只做一種格式：GHSA 優良電影劇本獎。** 它與那份 4 頁範本（BAMID 劇集劇本創作獎公告的附件）**實質等同** —— 後者明文聲明其格式「係參考優良電影劇本獎之劇本內文寫作格式」，範例文字逐字相同。

> ⚠️ **獎名訂正**：本效力一路稱的「文化部劇本獎」**不存在**，那份 4 頁 PDF 是 BAMID 的附件。凡地圖與票券中出現該名稱處皆應讀作 BAMID。

### 9.1 技術管線

**Puppeteer / Playwright ＋ `@sparticuz/chromium`。**

理由：CJK 排版精度最高（直接沿用瀏覽器原生引擎）、CSS `@page` 可精確對應格式規範、`break-inside: avoid` 可做分頁控制、與 Next.js／React 生態無縫，且**換格式等於換 CSS 模板**。

**已排除**：LaTeX（TeX Live 數百 MB～數 GB）、Typst（標點擠壓仍是官方追蹤中的缺口）、WeasyPrint（引入 Python 語言棧）、Prince（商業授權）、pdf-lib／Satori（等於自己重造排版引擎）。
**第二順位**：`@react-pdf/renderer` —— 部署包最輕，但 **CJK 逐字折行與避頭尾是官方已知且未修復的開放缺陷**。

**兩條被更正的常見說法**：

- 「Vercel 50 MB 卡死 Puppeteer」**已過時** —— 現行為未壓縮 250 MB，AWS Lambda zip 同為 250 MB。此空間足以同時容納完整 CJK 字型與 `@sparticuz/chromium`（v149 實測 69.7 MB unpacked）。
- 「字型太大」**不是真問題** —— 所有候選引擎在輸出階段都會**自動子集化**。真風險是「渲染當下執行環境能不能讀到完整來源字型檔」，而這在 Vercel／Lambda 上不構成阻礙。

> **⚠️ 硬邊界條件（反向約束了部署平台選擇）**：
> **Cloudflare Workers 純執行模式不可行**（每個 Worker 僅 10 MiB）。
> 若日後傾向 Cloudflare，PDF 匯出必須拆成獨立子服務，或改用其 Browser Rendering API（**未實測其字型行為**）。

### 9.2 渲染的輸入是一筆交付，不是 live doc

> **Delivery 是渲染的輸入，不是渲染的產物。**

順序是**先提交交付，再渲染**。兩種失敗嚴重不對稱：

| 失敗 | 後果 |
|---|---|
| 交付已記錄、渲染失敗 | 一筆沒有紙的交付。**它沒有說謊**（只宣稱「T 時刻承諾的內容是 C」），可回復 |
| 紙已到對方手上、交付沒記錄 | 紙上印著我們沒存過的號碼 —— **永久損壞** |

這一句同時買到四樣東西：**atomicity 邊界縮成只有一個交易**（建立交付），其餘全是它的純函式；**重試 ＝ 用同一筆交付重新渲染、不產生第二列**；「凍結連結的內容來源不得依賴 current state」PDF 路徑**免費**拿到；**頁尾時間戳必然是交付的建立時間**而非渲染當下的 now（否則重新渲染會印出不同的字）。

⚠️ **PDF 的 byte-for-byte determinism 不是 domain invariant** —— 它只是這個順序的良好後果。把它升格會直接撞上不變式 E。

### 9.3 頁面設定

| 項目 | 值 | 來源強度 |
|---|---|---|
| 語言／方向 | 直式橫書，正體（繁體）中文 | **GHSA 明文硬性** |
| 字級 | **12 級** | **GHSA 明文硬性** |
| 紙張 | A4 | 跨來源一致（GHSA 未規定） |
| **每頁行數** | **不存在這個規定** | 五個一手來源全部沒有 —— 台灣簡章用的是字級＋行高＋邊界，不是美式的每頁行數。**這是一條實質差異，不是資料缺漏** |
| 字型、行高、邊界 | **GHSA 未規定** → 由模板選定 | 建議初值：邊界四邊 2 cm、行高 1.5 倍、中文字型走系統可得的思源／Noto 系列 |

⚠️ **不得沿用北藝大（TNUA）的數字冒充 GHSA 規範** —— 那是完全獨立的另一套教學規範（唯一使用 △、唯一要求場次標題列人物、唯一給出完整頁面設定數字）。TFC 與編劇高雄的數字同樣不能合成一組「台灣通則」（字級 12 vs 14、行高 26 PT vs 20 pt 互相衝突）。

### 9.4 各元素的印法

| 元素 | 印法 | 來源 |
|---|---|---|
| **場次標題** | `1. 內景 阿強家客廳 夜` —— 場次號後接**半形句點**、**不含人物欄位**、**不加 △**、不粗體、不縮排 | 範本 |
| **子場次標題** | `5.1　內景 醫院走廊 日` —— **無尾點**（改用一個全形空白，`5.1.` 有兩個點難讀）、**不縮排**、**不加「插入」字樣前綴** | 自行發明 |
| **動作** | 純段落文字，**無 △ 或任何符號**，靠空行與對白區隔 | 範本 |
| **對白** | **行內式**：`人物名：對白內容` 同一行，人物名後接**全形冒號**，不換行、不置中、不縮排。整段對白與前後動作之間各空一行 | 範本，見 §9.5 |
| **發聲方式** | `小明（V.O.）：…` | |
| **插入畫面** | 渲染為 `INS`（模板產物，不進資料模型） | |
| **折返** | `回到　公寓客廳` —— 印**地點顯示名，不印場次號**（場次號在同一頁重複，在台灣慣例裡很可能被讀成排版錯誤） | [ADR-0006](../../docs/adr/0006-continuous-action-as-continuation-subscenes.md) |
| **交叉場次** | **先建立、再宣告、再交錯**：兩地各自完整場次標題 → `以下對剪` → 交錯片段。交錯段落的歸屬標記印**地點名、不印場次號**；顯示名相同時（同一套陳設、只差日夜）補印區別欄位 | [ADR-0004](../../docs/adr/0004-scene-groups-for-intercut.md)（依王瑋《淡入》的裁決規則採美式寫法 A） |
| **登場人物** | **匯出選項，預設關閉** —— GHSA 範本 2022-02-26 改版已拿掉人物欄，但可能有比賽要求、劇組也有偏好 | |
| **群演** | **不進 PDF** | |
| **頁碼** | 置中，**跨區段連續** | |
| **時間戳** | 每頁、靠左、小字。**匯出選項、預設開啟**，投稿前可關 | |
| **浮水印** | 掛 `@page`。**文字必須是可輸入參數**（GHSA 強制且文字含屆別，每屆不同） | |

> **⚠️ 頁尾時間戳的論證已兩度被更正，結論不變**：不是「紙面可有非劇本內容」，而是
> **GHSA 明確安全**（強制壓浮水印，紅線是不得署名）＋ **TFC 也明確安全**
> （FAQ 兩屆逐字答「非必要／沒有硬性規定，但不能有姓名地址等記號」—— 禁的是**識別身分的資訊**）。

**折返標記的推導規則**（全部從結構讀得出來，不必問編劇）：

| 情況 | 印什麼 |
|---|---|
| 主場次一段**非空**內容，且之前出現過主場次內容 | `回到　公寓客廳` |
| 兩個子場次相鄰（中間沒有非空主場次內容） | **不印** |

「本場次第一次出現主場次內容」因不變式 ① 而不可能發生。**空區塊不算內容** —— 這讓編劇雙 Enter 跳出來、卻又改打 `/continue-to` 時，標記從頭到尾沒有出現過，畫面不會自己閃一下。

**「以下對剪」「回到」「INS」都不進資料模型**，位階相同（約束 2）。

**⚠️ 編輯器裡也要即時顯示折返標記**，機制與場次號相同（decoration）。只印在 PDF 會讓編劇跳出子場次後不知道自己在哪一層 —— 那正是那六個 bug 的病根：**結構變了但畫面沒說**。空區塊改用 placeholder 交代「你在哪一層」（縮排是另一半），placeholder 與標記同一位階，都不進資料模型。

### 9.5 對白排版變體 —— 本規格書裁決

GHSA 範本把**行內式**與**置中分行式**都列為可接受的參考範例，沒有強制擇一。第 44、46 屆只有行內式，**第 48 屆才新增置中分行式**（「內文寫作格式參考二」）—— 與 2022-02-26 那次減法改版同方向，這次是加法。

**v1 選定：行內式。**

理由三條：(1) 它是三個屆別**連續存在**的那一種，置中分行式是新加的；(2) 兩種都是官方認可的參考範例，所以這個選擇**在投稿風險上是零**；(3) 它與「人物名與對白分離存成欄位、渲染時才組成那一行」的資料模型自然對應。

**代價與退路**：置中分行式需要置中對齊與整段縮排，人物名獨占一行且**不加冒號**（⚠️ 北藝大那套人物名後**有**冒號，不可混用）。**加上它是換一個 CSS 模板，不動資料模型** —— 這正是「格式退化成渲染樣式」這個賭注的第一次兌現。

### 9.6 匯出前防呆

彈窗的語意是**「這份 PDF 會少掉這幾場」**，不是「要不要輸出這一場」—— 草稿本來就不輸出。

```
本次輸出會略過 2 場草稿：
 ☐ S11[D1]「小明在雨中奔跑……」— 未填寫內／外、地點
 ☐ S17[D1]「……」— 手動標記為草稿
 ☐ 全選　　[ 之後不再提醒勾選的場次 ]
```

- **列出時要附內容首行摘錄** —— 草稿常常正是 metadata 沒填的那些場次，`S11[D1]` 對編劇來說是個空號，首行文字才是他認得出來的東西。
- **支援多選與全選。**
- **⚠️ 即使全部勾了「不再提醒」，輸出完成後仍要顯示一行「本次略過 N 場草稿」** —— 不擋流程、不需點掉。**靜默地少印幾場，對一個要拿去投劇本獎的人是最糟的失敗模式**；防呆的價值在這裡，不在彈窗本身。
- **草稿成員 → 整個群組印不出來**（殘缺的對剪比不印更糟）。草稿清單要**特別標示「這場屬於一個對剪群組」**，讓編劇知道略過它的後果比表面上大。
- **登場人物提示另外列，提醒但不阻擋**（§4.7）—— 與草稿分開，因為它可能是正確狀態。

### 9.7 交件 PDF 的區段結構

**交件是單一 PDF**（三重證據）。順序 46 與 48 屆逐字未變：

```
標題頁 → 長版劇情大綱 → 人物介紹 → 劇本內文
```

- **各自獨占一頁**（短區段也要）。
- **一趟 `page.pdf()`，不需要 pdf-lib 合併層。** 頁碼跨區段連續，浮水印掛 `@page`。
- TFC 是同樣三件、順序一致，**只少一個標題頁**。
- **人物介紹的欄位與字數，兩獎全部留白** → 不欄位化，模板負責整齊。
- **交件大綱的字數上限不寫死** —— 那是各案特例（GHSA 800–1200／TFC 明文無上限／高雄拍 500／編劇高雄 1500）。產品只提供**字數計數器**，不執行規則。
- **不放圖片、不留「插入自備圖片頁」的逃生口** —— GHSA 明文禁止圖片，而**沒有任何來源要求「劇本內文」放圖**。

### 9.8 v1 之後要參數化的維度（架構預留）

「換格式 ＝ 換 CSS 模板」要兌現，模板必須是這些維度的組合：頁面設定（紙張／邊界／中英文字型分開／字級／行距／頁碼位置／浮水印）、場次標題是否含人物欄位、場次標題是否加粗、動作是否加符號前綴（△ 及符號本身）、對白呈現方式（行內式 vs 置中分行式／人物名後是否加冒號／是否置中縮排）、對白前後空行規則、新場次前空行規則、場次編號格式（是否攤平）、是否需要投稿包裝頁。

## 10. 分享與交付

### 10.1 即時分享

- 路徑 `/s/<token>`，**免註冊可看**，劇本與場次表是**同一個 share 的兩個視圖**（頁內切換）。
- **頁頂固定一行**：「即時連結 · 最後更新於 X」。它的價值不在資訊量，而在**讓漂移變得可察覺** —— PDF 有實體差異可察覺，活連結什麼都沒有。
- ⚠️ **「內容是否變更」以 `doc_seq` 定義；timestamp 只是那個 canonical 事實的人類可讀投影，不是判準本身。**

### 10.2 凍結分享

- **不是分享面板上的第二個選項**，而是匯出 PDF 的副產品：「取得這次交付的連結」。
- **快照必然，連結自願** —— 每次交付都建立（不變式 D 強制），但 **token 懶惰鑄造**。否則「我只是想印一份 PDF」會在背後多出一條公開可讀的網址，那是安全面的意外。
- 頁頂固定顯示「**這是 X 時交付的版本**」。
- **⚠️ 不對凍結連結的讀者說「作者後來又改了」。** 這不是第 10.1 節的對稱套用 —— 它的受眾是被**刻意凍結**的一方，告訴他「作者後來改了 40 次」是把 current state 洩漏給沒有資格知道的人，投獎與交件情境下是明確的害處。而且「我後來改了」是**編劇該主動說的話**。
- **反過來，在編劇自己的分享清單裡**顯示「這條連結凍結在 3 天前，之後 canonical state 已變更」**有用且零洩漏**。

### 10.3 token、撤銷、有效期

- **token 要求 opaque 且不可枚舉。** nanoid 是實作選擇，不寫進規格。
- **撤銷**：寫 `revoked_at`、**保留該列** —— 刪掉就查不出「這條連結曾經存在過」，而整個交付哲學是不說謊。被撤銷的連結對訪客顯示**中性頁面**（「這條連結已停用」），不透露劇本是否存在、不透露是誰撤的、不引導去要新連結。重新分享 ＝ 鑄新 token。
- **有效期：v1 不做。** (1) 它製造的失敗模式**專挑最糟的時機發作**（製片開拍前打開連結發現過期）；(2) 對「不小心被轉傳」這個真實威脅模型，過期是安全劇場，**撤銷才是真正的控制**；(3) 對凍結連結它自相矛盾 —— 給一個**全部保留、不清理**的交付的把手設有效期，等於讓把手比它指的東西先死。

### 10.4 交付與備份不共用

| | 交付 | 自動備份 |
|---|---|---|
| 性質 | **唯一刻意不可變** | before-image、recovery |
| UI | 凍結連結 | **無** |
| 清理策略 | 不可碰 | 可被清理策略碰 |
| `doc_seq`／`doc_schema_version` | **無**（不被載入編輯、不遷移） | 有 |

**混用會讓「唯一刻意不可變」這條分野失效。**

## 11. 不變式總表

實作時這些必須有測試。**它們的家是 command 層**（§6.3）—— 在瀏覽器外可單元測試的地方。

| | 不變式 | 由誰保證 |
|---|---|---|
| **①** | **主場次的內容必須以主場次自己的內容開始**（子場次不能是第一個孩子） | command（空場次裡 `/insert`／`/continue-to` 不可用） |
| **②** | **子場次的 metadata 不得與主場次完全相同** | command → 視為不完整 → 自動草稿 → 匯出前被攔 |
| **③** | **同一群組的成員之間，metadata 不得完全相同** | 同上 |
| **④** | **群組不能巢狀，一個場次不能同時屬於兩個群組** | **schema**（§5.1） |
| **⑤** | **深度固定兩層** | **schema** |
| **⑥** | **同一份 doc 內 id 不得重複** | `appendTransaction`（`addToHistory: false`） |
| **⑦** | **場次身分只在五個時刻被鑄造，其餘一切保住身分** | 剪貼簿邊界 ＋ command（§4.3、§6.5） |
| **⑧** | **所有 domain command 拒絕建立對不存在實體的引用；doc 必須允許懸空引用** | command（寫）／projection（讀）—— §6.6，**兩半並排** |
| **D** | **交付的判準是承諾而非通道**：任何對外承諾「在後續 canonical state 改變後仍保持不變」的動作，都必須先建立一筆交付；該動作輸出的一切都指向那筆交付 | application |
| **E** | **semantic freeze / visual drift**：渲染器日後的純視覺變更**可以**影響已存在的交付；但**不得重新計算該次交付已承諾的語意推導值** | 渲染管線 |
| **F** | **`documents.kind` 固定其合法層級**，不由使用者決定 | 資料層 ＋ command |
| — | **一筆交付必須能獨立重建它承諾的語意**（寫成能力，不寫成欄位 —— 存不存 doc 是 persistence concern） | 交付寫入路徑 |
| — | **backup ＋ canonical document update 是同一個 atomic state transition**；**schema migration ＋ doc 更新 ＋ `doc_seq` 遞增**同理 | persistence 模組 |
| — | **距上一筆自動備份 ≥ 2 小時就先寫一筆**（對外：任何時候最多退回兩小時） | persistence 模組 |

**⚠️ 保護升級路徑的四條（[ADR-0006](../../docs/adr/0006-continuous-action-as-continuation-subscenes.md)，通往重疊群組）**：

1. **`種類` 從 v1 就存** —— 沒有它，遷移分不出插入與接續，得叫編劇回頭標
2. **任何東西都不准引用「第幾個子場次」或 `26.1`，只能引用場次 id**
3. **片段在 v1 不給 id、不給任何東西引用**（§5.2 說明了為什麼群組可以有 id 而片段不行）
4. **子場次的內容型別必須是場次內容型別的子集**（深度兩層那條規則正好保證了這件事）

**⚠️ 保護升級路徑的五條（[票券 04](./issues/04-screenplay-storage-model.md) Q4 ＋ [票券 19](./issues/19-yjs-migration-spike.md)，通往 Yjs）**：

1. schema 是 **isomorphic** 的獨立模組，不含任何瀏覽器相依（node spec 與 node view 分家）
2. 所有節點一律靠 attr 上的**永久 id** 定址，不靠位置、不靠場次號
3. **「整份 doc 覆蓋」這個假設不准散進程式各處** —— 存檔集中在一個 persistence 模組後面
4. **undo 只透過 command 層對外曝露**（已被 edge boundary 規則吸收）
5. **任何可能裝 `null` 的 attr，schema 預設值必須也是 `null`**（§5.3，實測所得）

## 12. 三條約束如何被滿足

### 約束 1：場次是穩定錨點

| 機制 | 出處 |
|---|---|
| `sceneId` ＝ `sc_` 前綴全域唯一 nanoid，**使用者永遠看不到** | §4.3 |
| **場次號、子場次號、草稿標籤全部是推導值**，不進文件也不進資料庫 | §5.4 |
| **id 不編碼階層** —— 父子關係只由樹結構表達（編進去會在升級成主場次時說謊） | §4.4 |
| **場次身分只在五個時刻被鑄造，其餘一切保住身分**（不變式 ⑦） | §4.3 |
| **剪下＝保住 id、複製＝換新 id**，碰撞本身就是判別器 | §6.5 |
| **交付存推導結果而非輸入** —— 紙上印過的號碼永遠不被重算改寫 | §4.9 |
| **否決字母尾綴** —— 它是假保護（一搬移就變成 `S2A`），在業界成立是因為底下有顏色稿的鎖定層 | §3.2 |

⚠️ **這條在業界無範本可循**（§8）—— 調查到的表單清一色以會變動的場次號互相參照。這是我們要自建的機制。

### 約束 2：資料模型不含呈現性資訊

| 被擋在資料模型外的東西 | 它住在哪 |
|---|---|
| △ 三角形、粗體、斜體、刪除線 | 不存在（StarterKit mark 全關） |
| 場次號、子場次號、草稿標籤 | decoration ＋ 推導函式 |
| 「以下對剪」、「回到」、`INS`、placeholder | PDF／編輯器模板 |
| 縮排、置中、空行規則 | CSS 模板 |
| 登場人物印不印、時間戳印不印 | 匯出選項 |
| 對白行內式 vs 置中分行式 | CSS 模板（§9.5） |

**型別本身在強制這條**：`projectSceneTable(doc)` 的簽名裡沒有 doc 以外的輸入，有人想加一欄製作端另填的東西時會發現簽名裝不下（§6.4）。

**兩次被擋下的漏水口**：通用備註欄（[15](./issues/15-multi-spacetime-scenes.md)，沒有消費者）、專案自訂欄位的界線（[20](./issues/20-submission-docs-product-shape.md)，只能裝文件層級的散文）。

### 約束 3：不得堵死協作

**正面回答：存 ProseMirror JSON，不存 Yjs。**

四個代價讓「第一天就存 Yjs」不划算：伺服器每一條讀 doc 的路徑都要跑有狀態的 runtime；**儲存變不透明**（劇本工具最可怕的故障是「某位編劇的劇本壞了」，那種故障需要能用眼睛看）；`y-prosemirror` 是**第二層**要協商的預設行為，而我們有幾個載重的自訂行為正好落在那層（`appendTransaction` 去重、⌘Z 一步還原子樹、⌘Z 留下的孤兒實體被刻意容忍）；**Yjs 不是「協作完成」按鈕** —— CRDT 保證收斂但不知道我們的不變式。

**但這條決策沒有堵死協作**：

- **metadata 住在 doc 裡而非表裡** —— 若在表裡，協作時是「後到的贏、前者無聲消失」，日後要加同步層得先把 metadata 搬回 doc，而那時已經有真實使用者的資料。
- **`doc_seq` 已經是 optimistic concurrency token** —— 多寫入者的地基已經在。
- **command → Step → doc 三層**：中間層 `Step` 就是協作的傳輸單位，已經預留。
- **五條保護規則**（§11）。
- **⚠️ 「日後遷移不貴」這條承重事實已實測成立**（[票券 19](./issues/19-yjs-migration-spike.md)）：六項驗收全過（node type／tree／attrs／`sceneId`／text／marks），含子場次、場次群組、雜景多值地點、草稿在內的完整 fixture 往返等價，且中間走過真正的 bytes 持久化；`prosemirrorToYDoc()` / `yDocToProsemirror()` 兩個方向都有，遷移是無狀態的離線批次腳本。附帶：**Y.Doc 沒有比 JSON 大**（0.91×），「換 Yjs 會撐大儲存」不是有效論據。

### 13.1 技術棧

| 層 | 選擇 | 鎖定程度 |
|---|---|---|

| 認證 | 未定 —— 見[票券 24](./issues/24-auth-and-project-owner.md) | — |

### 13.2 建議順序

分層的判準是**依賴方向**，不是功能大小。前三階段完全不需要知道部署與認證的答案。

| 階段 | 內容 | 為什麼在這裡 |
|---|---|---|
| **0** | **isomorphic schema 模組**（node spec，node view 分家）＋ `projectScenes()` ＋ `projectSceneTable()` | 所有東西的地基。純函式、無瀏覽器相依，可在 Node 裡跑測試 |
| **1** | **domain command 層**＋不變式測試（§11 全部） | 不變式的家。**在有 UI 之前先寫**，否則它們會散進最難測的那一層 |
| **2** | **編輯器**：場次 ＋ 三種區塊 ＋ 內嵌簡表 ＋ `/next` ＋ Tab 環 ＋ IME | 最小可寫作單元。⚠️ 六個 bug 家族在這裡 |
| **3** | **persistence 模組**（存／載入／`doc_seq`／自動備份，全部藏在一個模組後面） | Yjs 保護規則 3 |
| **4** | **實體**：人物、地點、自動補全三列、群演、登場人物提示 | 依賴 1 的引用完整性規則 |
| **5** | **階層與平行**：子場次（兩種種類）、場次群組、拖曳跨層 | 依賴 2 與 4；⚠️ 拖曳 bug 會部分重來 |
| **6** | **草稿** ＋ **場次表**檢視 | 依賴 0 的推導函式 |
| **7** | **PDF 匯出** ＋ **交付** ＋ 匯出前防呆 | 依賴 3、6 |
| **8** | **分享連結**（即時 ＋ 凍結） | 依賴 7 的交付 |
| **9** | **交件文件**：交件大綱、角色設定表、專案 meta 欄位、四區段 PDF | 依賴 4、7 |
| **10** | **分場大綱** | 獨立，最小 |

**⚠️ 一個關於優先序的成本訊號**：業界有人自陳**多數情況根本不寫插入鏡頭**（「那根本不是故事的一部分，而且不用我寫其他人也知道該怎麼做」）。這不推翻子場次（需求反覆出現三次是真的），但**子場次機制的使用率可能比預期低** —— 階段 5 若卡住，先出貨階段 6–7 是合理的。
