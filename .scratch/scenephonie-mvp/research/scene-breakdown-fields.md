### 關於「場景」欄的專節說明（信心存疑，誠實列出）

真實 .docx 範例中「場景」欄排在「場次」欄之前，且與後面的「光」「景」兩欄（分別對應日/夜、內/外）並列，是獨立的第 14 欄之一。業界慣例上，順場表最前面通常是地點/景名欄位（例如「紫禁城－太和殿」），所以合理推斷「場景」= 地點。

但要誠實標註兩個不確定點：

1. 這份範例模板的「場景」欄在所有資料列都是空白，**沒有任何實際填入的範例文字可以核對語意**，所以以上判讀是根據欄名位置與業界慣例的推論，不是直接證據。
2. 更關鍵的是，「場景」這個詞在本專案 CONTEXT.md 中被明文列為**要避免使用的詞**（因為業界常用「場景」指場次的環境描述文字，會與本專案的「地點」欄位語意撞車）。這正好印證了 CONTEXT 裡「場景」一詞在業界确實存在歧義用法 —— 但無法排除這份範例文件作者用「場景」是指別的東西（例如「場景描述文字」而非單純地點名稱）。若真是後者，這欄位本身在劇本裡有對應文字，仍可能屬於第一層，只是對應到「動作」的一部分而非「地點」欄位。

**建議**：v1 實作時，此欄位直接對應 CONTEXT 定義的「地點」欄位（第一層），因為地點本身無疑是可從劇本 slugline 推導的資訊；但若日後拿到有實際填值的範本，應該重新核對這個判讀。

### 關於「劇情概要」是否算第一層的討論

CONTEXT.md 把「一句話的摘要」列為場次實體本身擁有的 metadata 之一（與動作、對白並列），所以形式上摘要屬於場次的固有屬性。但「摘要」本質上是人工撰寫的**濃縮**，不是逐字從動作/對白算出來的（不像「內/外」「日/夜」「登場人物」可以用機械規則從劇本結構抽取）。

兩種合理分法都存在：
- **分法 A（傾向第一層）**：摘要是場次實體與生俱來的欄位，寫劇本時就该同時寫，視為場次「投影」的一部分，沒有引入劇本以外的新資訊來源（人物、事件都还是劇本裡的）。
- **分法 B（傾向第二層）**：摘要的產生需要人的判斷與撰寫動作，機器/系統無法保證從動作與對白「零新增資訊」地自動推導出摘要文字本身（除非未來接 LLM 自動摘要，但那也不是「純推導」）。

本研究不強行選邊站，交給決策方依 CONTEXT 既有定義（「摘要」屬於場次固有 metadata）採**分法 A**，但需注意：這意味著寫作流程上摘要的「來源」是編劇手動輸入，而非系統計算欄位，這點在 UI/資料模型設計上要說清楚（欄位屬於第一層，但**填值方式**是人工撰寫，只是掛在場次實體本身而非另一張標註表）。

## 4. 這些表單如何識別、參照場次？（本票券最關鍵的問題）

**結論：業界表單一律以「場次號」（劇本裡的顯示序號，如「第12場」）互相參照，沒有觀察到任何獨立於顯示序號之外的永久識別碼機制。**

證據：
- 真實 .docx 範例的表頭第 2 欄就叫「場次」，直接使用序號欄位作為這張表最基本的索引軸；其餘欄位（光/景/演員/道具/備註）都是掛在這個序號上。
- papiin 文章對「場記表」的描述明文寫「記錄每個鏡頭的拍攝細節，**包括場次、鏡號**、備註等」——場次號是場記表的主鍵之一。
- 「拍片行事曆」描述「包含日期、**場次**、通告時間與地點」——行事曆用場次號把場次分派到拍攝日。
- 「通告單」是每天發給劇組的指令，業界慣例（雖然本次素材沒有拿到通告單的實例欄位）幾乎必定是列出當天要拍「第 X 場、第 Y 場…」的清單，用場次號做引用。
- 「剪接編輯表」「拍攝順序表」都是把場次重新排序/分組，若不是用一個穩定於重排的識別碼，唯一能拿來標示「這是原本劇本裡的哪一場」的欄位就是場次號。

**這對本專案架構約束的直接意義**：

CONTEXT.md 明訂「場次號」是**呈現用標籤，不是識別碼**——重新排序時會變動。但從這次調查看到的所有真實表單（順場表、場記表、拍片行事曆、通告單、剪接編輯表），**業界實務清一色是用會變動的場次號來互相參照**，沒有任何觀察到的表單使用獨立於顯示序號的永久 ID。這代表：

1. 這條「場次要有永久識別碼」的架構約束，**在業界紙本/表格工作流程裡並不存在對應機制**——傳統做法是重排場次時人工手動改標所有下游文件裡的場次號（這是已知的痛點類型，但本次素材沒有直接文獻佐證這個手動修正的具體流程，此點為推論而非證據，信心中等）。
2. 本專案要達成「重新排序不破壞外部引用」，**勢必需要自建一套業界原本沒有的機制**：對內用永久 id 儲存場次與其被參照的關係（例如道具表、標註、跨場次投影都掛在 id 上），對外顯示/匯出時才即時算出當下的場次號。這不是「翻譯業界既有做法」，而是本專案需要主動設計、業界表單本身無法提供參考範本的部分。
3. 換句話說，這也印證了為什麼 CONTEXT 要把「場次號」和「場次」的識別碼分開定義——如果不這樣做，本專案做出來的東西跟業界那些一改場次順序就要人工到處改編號的紙本表格,不會有本質差異。

**信心水準**：「業界表單普遍用場次號互相參照」——高信心（多個獨立來源一致）。「業界如何處理場次號變動後的下游文件同步」——未直接觀察到證據，屬合理推論，中信心，建議日後若能拿到通告單或拍攝場記表的實例範本（非只有說明文字），可以進一步驗證。

## v1 場次表規格建議（第一層欄位，可直接作為實作依據）

依 CONTEXT.md 對「場次」實體與「場次表」投影的既有定義，加上本次真實範例的交叉核對，v1 場次表應包含以下欄位，全部可從劇本結構零新增資訊地推導：

| 欄位 | 來源 | 說明 |
|---|---|---|
| 場次號 | 場次在劇本中的順序 | 顯示用標籤，會隨排序變動，對內須有永久 id 對應 |
| 內／外 | slugline | 對應範例的「景」欄 |
| 日／夜 | slugline | 對應範例的「光」欄 |
| 地點 | slugline | 對應範例的「場景」欄（語意存疑，見上方專節） |
| 登場人物 | 場次與人物的關聯 | 對應範例「男一～其他演員」欄的「出席」語意（不含服裝代號） |
| 摘要（一句話） | 場次固有 metadata | 對應範例「劇情概要」欄；是否嚴格算「零新增資訊」有討論空間，見上方專節 |

不建議放進 v1 第一層的欄位：「其他演員」中若涉及劇本未具名的群演，其歸屬待決，不應強行塞進第一層。

## 資料模型應預留的擴充點（第二層標註欄位）

以下欄位需要掛在單一場次的永久 id 上，但填值需要人工輸入，資料模型應設計成可擴充的標註表（而非場次核心 schema 的固定欄位）：

- 服裝／服裝代號（含服裝版本延續性追蹤，例如範例中的 A1/B1/C1 編碼機制）
- 道具（對應範例「美術道具」欄）
- 預估秒數／預估時長（對應「劇本計時樣表」的用途）
- 備註（自由文字）
- 佈景／場景需求（對應「場景需求單」「分景清單」，可能是道具/服裝/設備的彙整）
- （待決）群演／未具名角色的登場標註，若本專案的「人物」實體不支援匿名群演，這類資訊也只能落在標註層

以下欄位屬於第三層（外部），明確不應該進入場次的資料模型，而應該是完全獨立的實體/表，僅透過場次號或場次 id 做鬆散引用：演員檔期、場地租借合約、預算、天氣、拍攝日通告安排、剪輯順序、後製技術參數、合約與法律文件。

## 不確定與缺口

1. **「場景」欄的真實語意**：docx 範例所有資料列皆空白，無法用實例核對「場景＝地點」的判讀，僅憑欄位排列與業界慣例推斷（中信心）。
2. **「劇情概要」（摘要）是否算零新增資訊的第一層欄位**：兩種分法都合理，本文採用 CONTEXT 既有定義（摘要屬場次固有 metadata）判為第一層，但填值方式仍是人工撰寫，實作時建議在 UI 上明確標示「這是你要手動寫的欄位」而非系統自動算出。
3. **群演／未具名角色如何處理**：CONTEXT 的「人物」定義為獨立實體，但「其他演員」這類群演角色劇本裡未必具名，本專案的人物實體模型目前未定義如何處理，需要另外決策，不屬本票券範圍。
4. **業界如何實際處理場次重排後下游文件同步**：只推論出「用場次號互相參照」這個事實，但沒有直接證據看到業界如何應對重排後的同步問題（可能就是純手動）。若要更嚴謹驗證，建議之後找一份實際填寫過的「通告單」或「場記表」範本核對。
5. **只調查到一份場次表範例**（且是空白模板），樣本數為 1，欄位清單可能因劇組/公司慣例而有差異（例如簡表格式，CONTEXT 已提及「格式分歧」是已知現象），不宜視為業界唯一標準格式。
6. **papiin 文章的表單清單為二手整理**（文中自述「資料來源取自於網路進行整理編修」），未逐一核對每個下載連結內的實際欄位，只根據文章對每個表單的一句話說明做分類判斷，可能與該表單實際欄位有出入。
