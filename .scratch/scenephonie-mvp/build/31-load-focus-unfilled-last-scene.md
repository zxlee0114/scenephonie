# 31 — 載入時若最後一場還沒填 metadata，焦點該落在 chip row（upkeep）

**What to build:** 票券 26 的規則再收一次邊：載入既有劇本時，若**最後一場的 metadata 全空**（內外景／時間／地點都沒填），焦點落在該場的 chip row，而不是文件末端的內文。

**為什麼：** 同一個文件狀態，目前有兩種「你該從哪裡接著做」的答案 ——

| 情境 | 焦點落點 | 出處 |
|---|---|---|
| `/next` 剛建完一場 | 該場的 chip row | `command-bridge.ts:97` |
| 同一份稿重整回來 | 文件末端的內文 | 票券 26 |

重整後的落點特別彆扭：新場次的最後一個區塊是空的動作描述，所以游標停在一個空區塊裡，而這一場的內外景／時間／地點都還沒填 —— 系統前一秒才說「請你先填這裡」，重整後卻把人放進內文。

兩邊的判準本來就是同一條（「手不必先去點一下才能開始工作」）。票券 26 把「工作的位置」寫死成 `Selection.atEnd(doc)`，沒有涵蓋「末端那一場還沒填 metadata」這個狀態。

**這比「記住上次游標位置」便宜得多** —— 不必存 selection，不必決定多裝置怎麼算，而且答案不依賴使用者上次是怎麼離開的。

**Blocked by:** 26（`initialFocus` 的分岔在該票交付）

**Status:** done

## 影響檔案

- `apps/web/src/editor/use-screenplay-editor.ts` —— `documentEnd` 分支要先看最後一場的 metadata
- 可能需要一個「這一場的 metadata 是不是全空」的判準；`@scenephonie/schema` 裡若已有類似的東西（匯出前檢查用的）就用那個，別另立一套

## 待決

- 判準是「全空」還是「有任一欄沒填」？傾向**全空** —— 填了一半代表人已經在處理這一場，把游標搶回 chip 會打斷他。
- 若最後一場 metadata 全空**但已經有內文**（有人先寫戲再回頭填表），該搶回 chip 嗎？傾向不搶：有內文就代表工作已經在內文裡。這條會讓判準變成「metadata 全空**且**沒有內文」。

## Comments

**開票（2026-09-04）** —— 票券 26 的本機驗收中由使用者發現：「重整之後，游標跑到文件中，可能是預期行為，但小小的不太一致」。

**實作（2026-09-04）** —— `hasEmptySceneMeta`（`packages/schema/src/scene-meta.ts`）＋ `use-screenplay-editor.ts` 的 `isUnstartedScene`。

兩個待決的落點：

- 判準取**全空**，且「全空」＝ §5.3 的 `nullableSceneAttrNames` 全為 null／空陣列。比票券字面多一欄 `appearingCharacters`（目前不在 chip row 上，未來才有入口）—— 這是照票券「schema 裡若已有類似的東西就用那個」走：null 鐵律名單本來就是「空著＝尚未填」那份名單，另立一套會分歧。
- 「沒有內文」判準不是 `textContent === ""`，而是**單一空 `action` 區塊**（＝ kernel `emptyScene()` 的形狀）。空的對白／插入畫面區塊也沒有文字，但那是人已經把游標帶進內文按過 Tab 的痕跡，一樣不搶。

**已知範圍限制** —— 新分支只看 `doc.lastChild`。`/next` 若在文件**中間**建場（腳部按鈕、游標在中段），那一場重整後仍落在文件末端。票券限定「最後一場」，把焦點拉回中段場次是另一個判斷（會把人從稿子末端拽走），沒做。

本機驗收待使用者確認。
