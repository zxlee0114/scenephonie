# 52 — 握著一筆實體、清空重打前綴，要重新命中它自己

**What to build:** 原本握著 `Leon`，清空、打 `L` —— `👤 Leon` 那一列就該出來。**現在不會。**

`editRef` 把引用從 doc 上拿掉，只被這一場引用的實體於是暫時掉出 `existing()`，而
`editingMatch` 只認**完全相等**的名字。結果是：只被一場用到的實體重打前綴命中不了自己，
被多場用到的卻可以 —— **同一個手勢兩種結果，而差別在編劇看不見的地方**。

這是票券 38 那個 bug 的同一條裂縫，38 只補了「完全相等」那一格。

**Blocked by:** 40

**Status:** in-review

## 從哪來的

原本是票券 42 的第 4 條。42 是一張**措辭票**（`↩︎ 不修改，返回` 與 `↰ 回上一步` 要在每個
階段都看得見），而這一條是**既有的 bug**：不是措辭、不是階段、不需要等措辭那一側的任何
東西。留在 42 裡它會被措辭的討論壓著不做（使用者裁決 2026-09-12）。

## 建議做法

把手上那一筆當成一個**暫時仍存在**的候選丟進 `hits` 的比對（前綴／包含都算），而不是只在
「完全相等」那一格認它 —— 讓「拿在手上」與「還在目錄裡」在自動補全這一側**完全同形**。

⚠️ **不放寬到真正的孤兒**：ADR-0005（實體因引用而存在）那條線不動。差別是握在手上的那一筆
有一個明確的持有者，而孤兒沒有。

## 驗收

- [x] 被多場引用的實體行為不變
- [x] 命中列 `👤 派出所（3 場）` 的場數沒有被弄丟
- [x] 真正的孤兒仍然不出現在候選裡（ADR-0005 不動）
- [x] 人物欄與地點欄行為一致

## Comments

### 2026-09-14 — 實作

`entity-field.tsx` 的選單那一段，`known` 從 `existing()` 改成「`existing()` 再加上手上那一筆
（如果它已經掉出去了）」—— **一句**：

```ts
const held = heldEntity();
const known = held && !listed.includes(held) ? [held, ...listed] : listed;
```

`exact` 與 `hits` 於是讀的是同一份候選，「拿在手上」與「還在目錄裡」在自動補全這一側完全同形。
票券 38 只補了 `exact` 那一格，這裡補的是**同一條裂縫的另一半**。

- **放在最前面**不是排版：`hits` 有 `.slice(0, 5)`，附在尾巴會被別的候選擠掉，而手上那一筆
  是最該印出來的一列。已經在 `existing()` 裡的（被多場引用）走原本那條路，次序一個字沒動
  —— 驗收第 2 條因此是恆等的。
- `existing()`、`byName()`、`resolve()` 都**沒有動**：孤兒沒有持有者，仍然不進候選（ADR-0005）。
  `byName()` 放寬的後果票券 38 那則已經寫過（升格那一列會說假話），方向不變。
- `editingMatch` 留著：它認的是**顯示名**，而目錄裡那筆的名字可以不一樣（別名、或實體改名後
  舊引用留著舊字）—— `known.find(o => o.name === query)` 撈不到那一種。
- 場數（驗收第 3 條）本來就走 `scenesOf` 的 `heldScenes` 快照，這一改沒有碰到它；補了回歸測試
  釘住「拿起來之前是 3 場，打前綴時仍印 3 場」。
