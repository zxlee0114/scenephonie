# 34 — chip row 與內文之間的鍵盤往返（方向鍵）

**What to build:** 讓焦點在**內嵌簡表（chip row）**與**場次內文**之間用方向鍵雙向走通。
今天只有單向的一條路：Tab 從 metadata 一格一格串到內文，**進去就回不來**。

**Blocked by:** 04（`extensions/block-cycle.ts`、chip row 的 focus 串接都在該票交付）。
落點那一格是群演欄，由 09 交付 —— 排在 09 之後。

**Status:** in-review

## 症狀（使用者回饋 2026-09-10，票券 09 驗收期間順帶發現）

> 「如果在場次內容用方向鍵，沒辦法導回 metadata 欄位，感覺有點反直覺，如果直接跳進內容區塊，
> shift tab 也沒辦法直接回去，而是倒轉動作到插入畫面、對白一圈後才跳回去，且會在原地留下對白區塊。」

## 根因（已定位，不必再查）

兩件互相獨立的事湊在一起：

1. **方向鍵那條路根本不存在。** chip row 是 `contentEditable={false}`（`nodes/scene.tsx`），
   ProseMirror 的游標進不去，所以 ArrowUp 在場次第一個區塊沒有任何 handler 接 —— 不是壞掉，是沒做。

2. **Shift+Tab 被 `BlockCycle` 接走，那是反向轉型不是反向移動。**
   `extensions/block-cycle.ts` 把 `Shift-Tab` 綁到 `cycleBlock(editor, -1)`：動作 → 插入畫面 → 對白。
   轉到對白且該區塊是空的時候，`focusSpeaker` 把焦點丟進人物欄那顆 `<input>`；在那裡再按一次
   Shift+Tab 就是瀏覽器原生的反向 focus，於是「繞一圈才回到 metadata」。
   **代價是那個區塊已經被改成對白留在原地** —— 使用者要的是「回去」，付出的是內容被改。

第 2 點的每一步都是各自的設計意圖（§7.3 的環、票券 04 的 `focusSpeaker`），組合起來才成為壞經驗。

## 形狀

> **⚠️ 2026-09-10 使用者本機驗收後大改。** 原本的形狀是「離開鍵」（↓ 一律離開 chip row 進內文、
> ↑ 完全不接），驗收當場撞牆：chip row 在畫面上是**二維**的，格子之間根本沒有路。
> 下面是修訂後的模型；原形狀留在「已否決的第一版」一段。

chip row 的版面（`editor.css` 那條 `flex: 1 0 100%`，使用者回饋 2026-09-06）：

```
第 1 排  [內外] [時間] [地點——————————]
第 2 排  [登場人物——————————————————]
第 3 排  [群演————————————————————]
```

**方向鍵在這一排的意思就是「移到隔壁那一格」**，走到邊界才越界：

| 位置 | ← | → | ↑ | ↓ |
|---|---|---|---|---|
| 內外 | 上一場內文末端 | 時間 | 上一場內文末端 | *（開選單）* |
| 時間 | 內外 | 地點 | 上一場內文末端 | *（開選單）* |
| 地點 | 時間 | 登場人物 | 上一場內文末端 | 登場人物 |
| 登場人物 | 地點 | 群演 | 地點 | 群演 |
| 群演 | 登場人物 | 本場內文 | 登場人物 | 本場內文 |

反向（文件側，`extensions/vertical-nav.ts`）：

- 場次**第一個區塊**的第一行 ↑ ／ 第一個字之前 ← → 本場 chip row 的最後一格（群演）
- 場次**最後一個區塊**的最後一行 ↓ ／ 最後一個字之後 → → **下一場** chip row 的第一格（內外）

### 一格裡面還有 chip 要走（2026-09-10 第三輪回饋）

地點／登場人物／群演三格各自可以裝下好幾筆。上表那個「←→ 走到隔壁那一格」是**這一格走完
之後**的事 —— 欄位裡面還有 chip 可以走：

```
[👤 小明] [👤 小華] [👤 阿姨] |輸入框
    ↑ ←—— ↑ ←——— ↑ ←———————— ←
    └ 再往左才離開這一格（換上表接手）
```

| 鍵 | 在輸入框 | 在一個 chip 上 |
|---|---|---|
| ← | 空欄位時退進**最後一個** chip | 前一個 chip；第一個再 ← 就出這一格 |
| → | （不變）貼著字尾就跳格 | 下一個 chip；最後一個 → 回輸入框的**字首** |
| ⌘← | 空欄位時到**第一個** chip | 第一個 chip |
| ⌘→ | （原生）字尾 | 輸入框字尾 |
| ↑↓ | （不變）格線導航 | 格線導航（原封轉交） |
| Enter／Backspace | （不變） | 把那一筆拿下來重編輯（同滑鼠點它） |

chip 都是 `tabIndex={-1}`：走得進去，但 **Tab 序一個字都沒改**（§7.3 的環）。

**輸入框裡還有沒定案的字時，← 不退進 chip**（⌘← 同）—— 離開輸入框會 blur，而 blur 會把那個字
定案成一個新的 chip，那一刻整排的序就變了，剛算好的「最後一個」指向別人。有字時 ← 照舊是
「貼著字首就跳去隔壁那一格」，字定案之後才輪到 chip 那條路。與 Backspace 的「空欄位才把最後
一筆拿下來」是同一條線。

### Enter 與 ⌘↑↓（2026-09-10 第三輪回饋）

- **`Enter` ＝ 這一格好了，去下一格** —— 與正向 `Tab` 同終點，差別只在它不看游標在哪。
  輸入框那三格：還有字沒定案時 Enter 先把字切成 chip（欄位自己吃掉），**空欄位的 Enter
  才換格** —— 使用者感覺到的就是「chip 確認後再按一次 Enter 就換一格」。
  群演欄的「下一格」是本場內文。
  代價：下拉那兩格**開選單只剩 `Space` 與 `↓`**（Enter 讓出去了）。
- **`⌘↑`／`⌘↓` ＝ 一路走到底**，不管現在在哪一格：⌘↓ 直接進本場內文、⌘↑ 直接回上一場
  內文末端。五格共用同一組，所以不必記哪一格通往哪裡。

  選它而不是另造一顆鍵，是為了跟欄位裡的 `⌘←`／`⌘→`（走到這一格的最前／最後）湊成同一個
  心智模型：**⌘ ＋ 方向 ＝ 這個方向上走到不能再走**。`⌘Enter` 不能用 —— 那是「新增下一場」。

### 對白：人物欄 ↔ 台詞的水平那一半

- 台詞第一個字之前 `←` → 人物欄（早就有了，`extensions/vertical-nav`）
- 人物欄游標貼著字尾 `→` → **台詞的開頭**（第三輪補上，`nodes/blocks`）

`↓` 進的是台詞**末端**、`→` 進的是**開頭** —— 兩顆不同的鍵、不同的落點，因為水平那條路
走的是「字的順序」，上下走的是「區塊的順序」。

三條例外，各有理由：

- **下拉那兩格的 ↓ 歸選單**（使用者裁決，見下）。要往下走先 → 到地點格。
- **輸入框的 ←→ 要游標貼著字首／字尾**（且沒有反白）才跳格 —— 這一格裡還有字要讀時，
  方向鍵屬於那串字。下拉那兩格是 `<button>`、沒有游標，所以直接跳。
- **自動補全／下拉選單開著時 ↑↓ 是選單的** —— 只有選單關著才輪到導航。

**Tab 環一個字都不改。** §7.3：「環能當心流按鍵，靠的是按下去總能再按回來」；
讓 Shift+Tab 在某個位置離開環，環就不對稱了。方向鍵是空間移動，沒有環的包袱，
而且那正是使用者的第一直覺。

正向 `Tab` 與 `→` 在輸入框那三格同終點，差別只在 Tab 不看游標在哪 —— 它本來就是「離開這一格」。

### 每一條路都要走得回來

跨場次那兩條互為反向，缺任何一半就是「過得去回不來」—— §7.3 的環不變式在方向鍵上同樣成立。
使用者對「向右」原本不確定（「向右我不是很確定」），做的理由就是這個：← 那一半要了，
→ 不做就不對稱。

### 待決 —— 開工時定案（2026-09-10）

- **ArrowUp 的落點是「最後一格」**（＝ Tab 順序的反向）。往上退一步就退回「Tab 進內文之前
  的那一格」；「上次離開時那一格」是依看不見的狀態做不同的事，§7.3 否決過。
- **選單開著時方向鍵是選單的。** 這一條在 `EntityField`／`ExtrasField` 裡本來就成立：
  `handleKeyDown` 先吃掉 ↑↓（`rows.length > 0`），只有選單關著才把事件轉交給呼叫端。
  已寫測試釘住。
- **非第一場的 ArrowUp 進本場 chip row。** 由 `ctx.blockIndex === 0` 判定，與場次是第幾場無關。
- **第一個區塊是對白時，往上是兩步**（新增的一條，實作時才浮出來）：台詞 ↑ → 本區塊的人物欄
  → 再 ↑ → chip row。人物欄在畫面上就夾在台詞與 chip row 之間，一步跳過它會讓 2026-09-04
  那條「台詞第一行 ↑ 回人物欄補填」失效。順帶把人物欄的 ↑ 修對：本場第一個區塊時它原本會
  跨到**上一場**的內文，跳過本場的 metadata。

### 內外／時間兩格（ChipSelect）的 ↓：兩次裁決

**第一次（開工時）：整條 chip row 一套方向鍵語意** —— 選單關著時 ↓ ＝ 離開這一格進內文，
開選單改由 Enter／Space／點擊。理由是「同一排上同一顆鍵不該依落在哪一格做不同的事」。

**第二次（驗收後，現行）：↓ 還給選單。** 使用者的話：

> 「覺得下拉選單往下還是展開選單感覺比較好，直接跳到內容，覺得一瞬間掉太多，要回來又要
> 經過許多欄位，但我有點不確定一致性的問題」

那句「掉太多」的抱怨對象其實是**距離**，而距離在新模型下自己消失了（↓ 只移到隔壁一排）。
一致性那一半換成這樣結：**↓ 歸選單，是因為選單本來就往下展**；反過來 **↑ 不開選單** ——
第一排需要一顆「回上一場」的鍵，而「↑ 開一個往下展的選單」本來就是原生慣例的怪癖，捨掉不心疼。
代價是這一格的 ↑ 和 ↓ 做不同種類的事，記在這裡。

### 已否決的第一版形狀（2026-09-10 驗收推翻）

- ~~ArrowUp 在場次第一個區塊 → chip row 最後一格；**ArrowDown 在 chip row 任一格 → 回內文**~~
- ~~↑ 在 chip row 不接（「這一排上面沒有東西可去」）~~

錯在**把 chip row 當成一維**。實際版面有三排，於是「群演往上到不了登場人物、登場人物到不了

## 已否決：把登場人物／群演欄移出 Tab 循環

使用者的原始提案是「既然能靠內容新增這兩種實體，也許沒必要進 Tab 循環」。不做，三個理由：

1. **它們不是內容那條路的重複捷徑。** 登場人物的判準是**入鏡**不是台詞 —— 沒有一句話的角色只能
   從這一欄填；群演能從對白建的只有「一群齊聲說」那種，**不出聲的背景演員**（`咖啡廳客人 x8`）
   沒有第二個入口。
2. **鍵盤唯一的路就是那顆 input。** chip 的 `×` 與「點 chip 改人數」都是 `tabIndex={-1}` 的滑鼠路徑。
3. §9「metadata 預設可見，且缺漏不可被預設 UI 隱藏」的同一條理由 —— 移出鍵盤路徑是部分隱藏。

**真正的問題（Tab 走完 metadata 太長）由上面的 ArrowDown 解掉**，而不是讓某幾格退出循環。
「依已填未填決定要不要停」更不行：§7.3 已否決過「同一顆鍵依看不見的狀態做不同的事」。

**「沒有去處」與「攔了那顆鍵」被分開了**：`ChipNav` 的每一個方向回傳 `boolean`，回 `false`
（第一場沒有上一場）就不 `preventDefault` —— 攔了卻什麼都不做，使用者看到的是「按了沒反應」。

**順帶抓到一個真 bug**（測試逼出來的，不是設計）：chip row 的欄位住在 node view 裡，也就是
**在 `view.dom` 之內**，它們的方向鍵照樣會冒泡到 `vertical-nav` 這支 keymap ——
欄位那側的 `stopPropagation` 擋不住，因為 React 把 listener 委派到 root container，
跑得比 ProseMirror 掛在 `view.dom` 上的原生 handler **晚**。少了守衛，在內外格按一次 ↑
會同時「回上一場」和「回本場群演欄」。守衛加在 `vertical-nav` 的 `caret()`：
`activeElement` 在 `view.dom` 裡但不是 `view.dom` 自己 ＝ 焦點被欄位拿走了，這幾顆鍵不歸文件。

那道守衛也讓兩個既有測試需要補一行 `editor.view.dom.focus()`（`dialogue-tab.test.tsx`
與本票的 `pressInBody`）—— 掛載後的初始焦點在 chip row 上，不補就等於在模擬別的情境。

測試從 13 條長到 63 條（`chip-row-caret-return.test.tsx` 37 條 ＋ `chip-select.test.tsx` 14 條 ＋ `chip-entity-caret.test.tsx` 12 條），
其中格線導航那張表逐格釘住，跨場次那兩條正反向各一組。

### 驗收後再修（2026-09-10，第三輪）

使用者原話：

> 上一場末端往下，會直接到這場的內容區塊而非 metadata 區塊
>
> 當地點、登場人物、群演有兩個或以上的實體時，左右鍵希望能在實體間導航，到最前面時才跳欄，
> cmd + 左右鍵 能夠跳轉到欄位最前方或最後方

**① 往下回不到 metadata。** `vertical-nav` 判斷「游標是不是已經在最後一行」只問了
`view.endOfTextblock("down")` —— 那支讀的是 `getClientRects()` 的實際版面，落在區塊末端時
它並不是每次都答得出 `true`（軟換行的 `\n`、空區塊的 placeholder `<br>`、行高剛好對齊時的
邊界比較都會讓它翻臉），而 jsdom 裡所有 rect 都是 0，所以第二輪的測試全綠也照樣漏掉。

修法是**再加一條不看版面的判準**：游標貼著區塊的字首／字尾時，它必然就在第一／最後一行 ——
`parentOffset` 就是答案。兩條取聯集，只會讓判準更寬，不可能誤判成越界。新測試把
`view.endOfTextblock` 整支換成 `() => false`，逼出那條不看版面的路。

順帶把 `requestFocus` 改成**回報有沒有人領走**（`focus.ts`）。文件側攔下一顆鍵之前得先知道
那條路真的走得通 —— 沒人領走卻照樣 `preventDefault`，使用者看到的是「按了沒反應」。這與
第二輪那條「沒有去處就把鍵原封還回去」是同一條線。

**② 欄位裡的 chip 走不進去。** 新模組 `editor/chip-caret.ts`（一個 hook，實體欄與群演欄共用）
——規則見上面「一格裡面還有 chip 要走」。三處接線：

| 檔案 | 改動 |
|---|---|
| `editor/chip-caret.ts` | 新檔：chip 之間的方向鍵、⌘ 跳端點、轉交給格線 |
| `editor/entity-field.tsx`／`extras-field.tsx` | chip 掛上 `chipProps(i)`；輸入框的 ← 先問過它 |
| `editor/nodes/scene.tsx` | `chipNavHandler` 收得下**非 input** 的 target（chip 沒有游標，一律算貼著端點） |

`onKeyDown` 的型別從 `HTMLInputElement` 放寬成 `HTMLElement`：轉交過來的那顆鍵，
`currentTarget` 是那個 chip。

### 第三輪回饋的第二批（2026-09-10）

使用者原話：

> - 對白區塊的左右也能夠切換：游標在對白最前方 -> 往左 -> 跳至說話的人物（目前已經是了）
>   說話的人物 -> 往右 -> 到對白最前方
> - metadata 感覺在 chip 確認後，按 Enter 也可以切換成下一個欄位
> - 然後要選定一組直觀的快捷鍵，讓使用者可以直接跳從 metadata 的任意位置，直接跳到內容區塊上

三件事的形狀寫在上面「Enter 與 ⌘↑↓」與「對白：人物欄 ↔ 台詞的水平那一半」兩段。實作上的
一個整理：`chipNavHandler` 與 `ChipNav` 從 `nodes/scene.tsx` 搬進新的 `editor/chip-nav.ts`
—— 現在有三個地方要問「這顆鍵算不算已經走到這一格的邊緣」（chip row 的輸入框、下拉那兩格的
`<button>`、欄位裡的 chip），還有對白人物欄的 `→` 也要同一個答案。那個判準只該有一份。

| 檔案 | 改動 |
|---|---|
| `editor/chip-nav.ts` | 新檔：`ChipNav`、`fieldEdge`、`chipNavHandler`（從 `nodes/scene` 搬出來） |
| `editor/chip-select.tsx` | 關著時 Enter ＝ 下一格（開選單剩 Space／↓）；⌘↑↓ 走 `exitUp`／`exitDown` |
| `editor/nodes/scene.tsx` | 五格共用一組 `exits`（⌘↑ 上一場末端、⌘↓ 本場內文） |
| `editor/nodes/blocks.tsx` | 人物欄游標貼著字尾的 `→` → 台詞開頭 |
