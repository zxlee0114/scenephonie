# 65 — 存檔失敗後每 2.5 秒重試一次，斷線多久就打多久

**What to build:** 讓自動存檔失敗後的重試有節制：間隔逐次拉長、有上限，網路回來時馬上補存。

**為什麼現在會一直打：** `src/persistence/save-scheduler.ts` 的 `flush()` 在 `save()` 失敗時把變更標回 dirty，
再呼叫 `arm()`。`arm()` 用的是正常打字的節奏（`SAVE_PAUSE_MS` 2.5 秒停頓、`SAVE_MAX_WAIT_MS` 15 秒上限）。
這樣斷線時每 2.5 秒就會重試一次，沒有退避，也沒有上限。
這段重試本身不能拿掉：沒有它，存檔失敗後只要使用者停手，那份修改就永遠不會再寫出去（註解裡寫了原因）。

**Blocked by:** 無

**Status:** in-review

## 開工前要定的事

- **用「最多重試 N 次」還是「退避到一個上限後持續重試」**：使用者提議設最大請求數。要注意的是，次數用完就停手，
  等於畫面說「會再試一次」卻再也不試，和上面那段重試要防的是同一個失敗。比較可能的形狀是：指數退避（例如 2.5 → 5 → 10 → … 封頂 60 秒），
  加上 `online` 事件與使用者繼續打字時立刻重試。如果要設硬上限，停手後畫面要說清楚，並給一個手動「再存一次」。
- **`navigator.onLine === false` 時要不要乾脆不送**：它只能確定「一定斷線」，不能確定「一定連得上」，所以只能拿來省掉請求，
  不能拿來判斷存檔成功。
- 匯出 PDF 的 `flush()`（票 18）是使用者主動按下的，應該立刻試一次，不受退避影響。

## 驗收

- [ ] DevTools 切到 Offline 後，重試間隔逐次拉長，不會固定每 2.5 秒打一次
- [ ] 切回 Online 後很快就補存成功，不用等退避時間到
- [ ] 斷線期間繼續打字不會讓請求變密
- [ ] 存檔狀態的文字和實際行為一致：說「會再試」就真的會再試
- [x] 用 fake timers 的測試把退避序列與封頂值釘住

## Comments

**開票（2026-10-22）**：驗收票 18 時手動切離線，發現請求一直持續。使用者提議設最大請求數，另開這張票處理。

**實作（2026-10-23）**：開工前裁決 —— **退避到上限、持續重試，不設次數上限**（2.5 → 5 → 10 → 20 → 40 → 60 秒，之後每 60 秒）；
狀態文字「存檔失敗，會再試一次」因此不改。`navigator.onLine === false` 時不送、當成失敗繼續退避；`online` 事件立刻 `flush()`。
等重試期間打的字搭下一次重試的車（票裡原寫「繼續打字時立刻重試」，與驗收「不會讓請求變密」衝突，取後者）。
`flush()`（匯出、離開分頁、網路回來）不受退避限制；成功一次退避歸零。測試只放在 `createSaveScheduler` 邊界。
code review 抓到三個時序問題，一併修掉並各補一個測試：失敗得比停頓還慢時重試會連發、兩個 `flush()` 同時等時後一個誤回 `true`、
`cancel()` 擋不住路上那一次失敗後的重排。剩下四條驗收要在瀏覽器 DevTools 切 Offline／Online 人工確認。
