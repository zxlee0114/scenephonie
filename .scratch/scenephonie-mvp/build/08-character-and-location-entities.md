# 08 — 人物與地點實體

**What to build:** 存在 ＝ 被引用（[ADR-0005](../../../docs/adr/0005-entities-exist-by-reference.md)）。`characters`（`ch_`、`project_id`、`name`、`description`）與 `locations`（`lo_`、`project_id`、`name`，**無描述欄**）兩張 append-only 表。引用形狀 `{ 實體 id, 這一場顯示的名字 }`，用在場次 metadata（地點／登場人物）與對白人物欄。引用完整性（不變式 ⑧，**兩半必須並排**）：所有 domain command **必須拒絕**建立對不存在實體的引用，且「**先建立實體、再寫入 doc**」；doc 讀取**必須允許**懸空引用 —— 顯示名是渲染權威，PDF／場次表照印，只是少一條可聚合連結。否決「載入時用顯示名自癒補一筆」（讀取路徑的寫入 ＋ 漸進揭露下補出來的名字是錯的）。三列自動補全選單：命中既有（`📍`）／建立新實體（`＋`）／作為既有實體的另一個名字；打字當下不問任何問題，注音組字期間選單完全不動作；新建 chip 與命中 chip 視覺可辨。名字是真欄位（初值 ＝ 建立時打的字，可改），別名不存在實體上（就是各引用上的顯示名）。多值欄輸入規則（同時適用地點欄與登場人物欄）：標點（`、，,；;`）是分隔符，全形半形空白一律視為名字的一部分；即時切成 chip，Backspace 還原成可編輯文字，貼上用同一規則解析。地點身分判準 ＝ 美術上要不要分開處理（不是名字、不是地理位置）；地點實體之間沒有包含關係。兩者都屬於專案，不屬於劇本。**v1 先假設 `owner_id` = hardcoded test user**（認證整合待票 06 完成後接上，不擋本票）。

### 四個實作當下才定案的決定

1. **存在性由呼叫端注入（`EntityDirectory`）。** command 是純函式、不能自己查資料庫，所以
   「這筆實體在嗎」是一個介面而不是一次查詢。伺服器端傳查詢結果，編輯器傳手上那份專案目錄，
   兩邊問的是同一句話。這也讓「先建立實體、再寫入 doc」在型別上看得出來：目錄要先多一筆，
   command 才放行。

2. **地點欄多值，但只有雜景真的存得下多個。** 多值輸入規則同時適用兩個欄位（票券要求），
   但 §4.3 說 metadata 一律單值、雜景是唯一逃生口 —— 於是**規則在欄位、限制在 command**：
   UI 讓人打第二個地點，`setSceneLocations` 在非雜景場次拒絕它。UI 擋得住滑鼠，擋不住
   伺服器端呼叫。

3. **「新建 vs 命中」的視覺差別是 session 內的事實，不是持久化的旗標。** chip 的 `＋` 只掛在
   「這一輪由這個欄位建出來的」那些實體上；重新整理之後全部都是 `📍`。這是誠實的 —— 那個
   區別的價值在**打字的當下**（我是接上既有那筆，還是又開了一套陳設），不在一小時後。
   懸空引用另有一個弱化的樣子（虛線、不上 error 色）：它不是錯誤狀態。

4. **範例稿（票券 07）順手升級成真實體。** 它當初把 id 留 null 並寫著「票券 08 一來就是一批
   待清的髒資料」。實體表落地後那個理由消失，換成更強的要求：**我們唯一出貨的那份稿自己也要
   滿足不變式 ⑧**。實體由訪客入口先建（每位訪客一份自己的，同 `sceneId` 的理由），再把 id
   交給組稿 —— 那條順序的第一個真實呼叫端就是它。`landingProject()` 的 `opening.screenplay`
   因此改吃一個 `AuthorizedProject`：要先有專案，才輪得到在它底下建實體。

**畫面上今天真的看得到的是 chip**：懸空引用照樣顯示、不跳警告、不消失。

4. **（自己發現的）`runKernelCommand` 結尾的 `view.focus()` 會搶走焦點。** 實體欄位是

### 與票券原文的第二處出入（這一次是推翻，不是補充）

原文：「多值欄輸入規則（**同時適用地點欄與登場人物欄**）」。實作照字面做了：地點欄一律吃頓號，
再由 `setSceneLocations` 在非雜景場次拒絕第二個。**順序是反的** —— 編劇打進去的字先被切成
chip，再被 command 悄悄退回去，畫面上只是「第二個 chip 沒出現」。

裁決（使用者，2026-09-10）：**多值是雜景的性質，不是地點欄的性質。** 地點欄的 `multiple`
綁到內外欄的值，非雜景場次的頓號就是名字裡的普通字元（跟對白人物欄同一條規則）。欄位一開始
就沒有收下第二個值，也就沒有東西需要被拒絕。

command 那一層的拒絕**照舊留著**，而且必須留：UI 擋得住滑鼠，擋不住伺服器端呼叫。兩層現在
講的是同一句話，只是一個在事前、一個在事後。「雜景」這個判準收成 `MONTAGE` 常數（`schema.ts`），
因為問這個問題的地方不只一個。

### 四個 metadata 欄位各掛一個說明（ⓘ）

原本的需求是「非雜景場次被拒絕加入第二個地點時給軟性提示」。grilling 之後形狀變了：**既然
欄位不再拒絕任何東西，就沒有「被拒絕的那一刻」可以掛提示**。改成常駐的欄位說明 —— 事前，
而不是事後補救（與 ADR-0006 否決「偵測到時間欄不同就跳提示」、改採事前標注是同一條方法論）。

彈窗**只講定義與出路，不勸、不擋**（§4.3「給選項，不給功課」）。地點那一份給的是**兩條**
出路而不是一條：雜景接快速跳接的散文，接續子場次（ADR-0006）接連續動作 —— 只給一條，編劇
會把走廊戲寫成雜景。登場人物那一份講判準是**入鏡**、以及匯出預設不印（spec.md:1110）。
時間欄沒有坑，但四欄三個有 icon、一個沒有看起來像漏了，所以也給一份。

**無障礙**：icon `tabIndex={-1}`（編劇每一場都要 Tab 走一遍 metadata，四個 icon 會讓那條路
加倍長），代價由兩條等價路徑補回來 —— 欄位的 `aria-describedby` 指向一句話版本（螢幕閱讀器
一聚焦就聽見，不必開彈窗），欄位上按 **F1** 開彈窗（`aria-keyshortcuts` 宣告）。三條路各有
一條測試：拿掉任何一條，`tabIndex={-1}` 就從取捨變成 WCAG 2.1.1 的違規。彈窗 Esc 關閉、
焦點回到**欄位**（回到一個 Tab 走不到的 icon 等於把焦點丟掉）。

### 上一輪驗收第 2 條就此作廢

原文寫「地點欄打『派出所、警局』→ 非雜景場次只會留下一個 chip（command 拒絕第二個，
console 有一行 warn）」。現在**不會有 warn** —— 非雜景場次得到的是一個叫「派出所、警局」的
地點（頓號是名字的一部分）；把內外改成雜景再打一次，才切成兩個。

### 第二個地點不再靜悄悄地覆蓋第一個（同日追加裁決）

單值欄原本的 `merge` 只留最後一筆 —— 非雜景場次打第二個地點，第一個就沒了，畫面上什麼都
沒說。裁決：**打第二個地點的編劇多半不是要換掉第一個**，而是這一場真的橫跨兩地，那是場次
形狀的問題，不該由一次覆蓋替他決定。

按 Enter 時**不 resolve、不建實體、不寫 doc**：那串字停在輸入框裡並且**整串反白**（一個
Backspace 就清得掉），面板取代自動補全問一句「要留哪一個」，三條路 ——

| 路 | 做什麼 |
|---|---|
| ⇄ 改成「警局」 | 明確取代，原本那筆被拿掉 |
| 🎬 兩個都留 | 先把這一場升級成雜景（`setSceneIntExt`），成功了才寫第二筆 |
| ✕ 放棄 | 清掉那串字 |

Esc 收起面板但**留著反白的字**（他還沒回答）；再打一個字就當作不是在回答面板，面板收起來。
blur 也不定案 —— 離開欄位不是答案。

實作上兩個時間差要當心，都寫在程式碼註解裡：升級成雜景之後**不能走 `merge`**（`multiple`
還是上一次 render 的 `false`，交給它正好會蓋掉第一筆）；`confirmReplace` 是 opt-in 的，
對白人物欄不給 —— 那裡換一個人講話是常態，問他等於每次改口都要按兩次。

Backspace 維持「還原成可編輯文字」（使用者確認）。

### 重新編輯的兩件（同日追加）

**① Backspace 拿下來的那一筆整串反白。** 空欄位按一次 Backspace 仍是「還原成可編輯文字」
（維持原裁決），但那串字現在**全選**著 —— 再按一次就一起刪掉。滑鼠點 chip 進來的**不**反白：
那是「我要改這個名字」，游標該留在字尾。兩個入口各自合理。

**② 修一個會憑空多建實體的缺陷（使用者從 POST 紀錄發現）。** `editRef` 先把引用從 doc 拿掉，
那一筆實體如果沒有別場引用它，**當場就變成孤兒** —— 而孤兒不算存在（ADR-0005），於是
`resolve` 把原封放回的名字當成新東西又建一筆，舊的那筆變成真的孤兒。症狀是「進入重新編輯、
什麼都不動就跳出，多一筆 POST 200」。

修法：記住正在被編輯的那一筆（`editing`），名字沒改就用回它自己的 id。改了名字才走一般流程
（那時它本來就該重新走命中／新建／別名那三列）。反證過：拿掉這條路，測試確實 fail。

### 對白人物欄：多值 ＋ 新建人物自動掛登場人物（同日追加）

**① 對白人物欄改成多值，chip 住在那條底線上。** 多個具名角色可以同時說一句台詞（齊聲），
所以 `dialogue.character` 的形狀改成與地點欄同一套 —— **單值 ｜ 陣列 ｜ null** ——
舊稿的單值物件照樣讀得出來，不必遷移。讀取正規化多一支 `dialogueCharacters`；command
`setDialogueCharacter` 複數化成 `setDialogueCharacters`（吃 refs 陣列、拒絕同一句裡重複的人）。
UI 這一側底線從 input 移到 `.entity-field` 容器，chip 因此住在欄位裡（同地點欄 2026-09-06 的做法）。

**② 在對白人物欄新建的人物，順手掛進本場的登場人物欄。⚠️ 這是暫時的。**

§4.7 寫得很清楚：「登場人物的判準是**入鏡**，不是有沒有台詞」，而且「系統絕不從對白推導
（推導會讓製片誤排通告），只提示」。這裡是**刻意的偏離**，理由是發聲方式（V.O./O.S.）還沒
實作（票券 10）—— 目前每一句對白都是一般發聲，於是「有台詞」與「入鏡」暫時是同一件事，
§4.7 那個提示的觸發條件恆為真，提示等於自動掛。

**票券 10 一落地就要換回提示**（可忽略的選單：`＋ 新增為登場人物` ／ `✕ 不新增 —— 他不入鏡`）。

範圍刻意收窄：**只在新建人物時掛，選既有人物時不掛**。編劇如果刻意把某個人從登場人物欄
拿掉（他有聲音但沒入鏡），我們不該再把他塞回去。

### 「新增完人物後再按一次 Enter，整組不見」（使用者回報 2026-09-10）

兩個獨立的原因，兩個都修了：

**① Enter 讀的是上一次 render 的區塊（這才是使用者撞到的那個）。** 人物欄一寫進 doc，chip
就出現，但這個 node view 的 props 要到下一次重繪才換新。看到 chip 之後**立刻**按 Enter 時，
`onKeyDown` 這個 closure 裡的 `node` 仍然是 `character: null` 的那一份 —— 於是「人名與台詞
都空著」成立，剛填好的人物連同整個對白被當成空區塊取消掉。改成從 `editor.state.doc` 讀當下
那個區塊。**這個家族的問題本輪出現第三次**（目錄的存在性、組字狀態、現在是區塊內容）：
ref／doc 是真相（同步），props／state 是畫面（重繪）。

**② `isBlankBlock` 還在把 `character` 當單一物件讀。** 齊聲（陣列）時 `.displayName` 是
`undefined`，於是那一句永遠被判成「人物名也空」。單值時剛好讀得到，所以這一條單獨不會炸，
但它是同一顆地雷的另一半。改走 `dialogueCharacters` 正規化。反證過：還原舊寫法，齊聲那條
測試確實 fail。

順帶修掉同一批的第三處：`entityUsage` 也只認單值 —— 齊聲的兩個人都不會被計入引用數，
於是他們會被當成孤兒而從自動補全裡消失。

### 第十輪驗收回饋（2026-09-10）：⌘Z 兩次、快捷鍵改鍵位、組字中的預覽

**① 新建 chip 之後 ⌘Z 要按兩次才清得掉。**

文件那一側從來只需要一次（一個 chip ＝ 一支 command ＝ 一個 transaction，`undo-history.test.tsx`
第一條就是量它）。問題是**那一下根本到不了 ProseMirror**：Tiptap 的 `NodeView.stopEvent` 把
`INPUT`／`BUTTON`／`SELECT` 上的鍵盤事件整個攔在 node view 裡（那是為了讓表單控制項在
contentEditable 裡還能正常打字），於是瀏覽器拿去做 input 自己的原生 undo —— 表面上「按了
沒反應」。`history-keys.ts` 把它送回去，掛在 chip row 與對白人物欄兩處。

**框裡還有沒定案的字時不接手**：那一刻的 ⌘Z 是「撤銷我剛打的那幾個字」，原生 undo 正是為它
而生。框空了才輪到文件。反證過：拿掉轉送，鍵盤那兩條測試確實 fail。

**② 說明的快捷鍵 F1 → ⌥/（使用者裁決）。** macOS 的 F1 預設是螢幕亮度鍵，要 `fn+F1` 才傳得到
網頁 —— 那條路對多數人等於不存在。⌥/ 在 macOS 送出來的 `key` 是 `÷`（Option 會改寫字元），
所以判準用 `code === "Slash"`，`key` 的兩種寫法留著當備援。同時**懸停 icon 會印出快捷鍵**：
icon 走不到 tab 序，這是它唯一自己說得出「還有鍵盤這條路」的地方，而看得到 icon 的人正好
就是還沒發現快捷鍵的人。

**③ 組字階段就給提示選單（像搜尋框那樣）。** 組字中浮出一份**唯讀預覽**：只列命中的既有實體，
不列「建立新實體」與別名入口 —— 那兩列是動作，而這一刻不該有任何動作可按。§7.6 那條線
一步都沒退：預覽 `aria-hidden`、`pointer-events: none`、不接任何一顆鍵（注音的空白是選字鍵、
Enter 是送出鍵，這一刻它們全部屬於 IME）。真正做決定的那一刻仍然是 `compositionend`。

**看得見不等於動得了** —— 原本的規則是「組字期間選單完全不動作」，它的意思一直是「不接手」，
不是「不顯示」；把兩件事分開之後，編劇在送出之前就知道會命中還是會新建。
