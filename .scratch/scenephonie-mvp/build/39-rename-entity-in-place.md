# 39 — 把實體改名，要有一個正經入口

**What to build:** 改實體的名字今天**只有一條路**，而且藏在別名流程的第三層底下：
打一個目錄裡沒有的名字 → `🔗 作為既有實體的另一個名字…` → 挑出那筆實體 →
`同時把實體改名為「X」`（`entity-field.tsx` 的 `aliasMode`）。也就是說，編劇想改名，
得先**假裝自己在取別名**。這張票給它一個直說的入口。

**Status:** done

## 現況（能力已經接好了，缺的是入口）

改名的整條管線是通的：`onRenameEntity` → `catalog.rename` → `renameEntityAction` →
`entity-store` 的 `renameCharacter`／`renameLocation`。這張票**不碰那條線**，只加入口。

而「改別名」其實已經有路了：別名住在**引用**上（ADR-0005），所以改這一場的叫法＝
把 chip 拿回來改它的顯示名 —— 票券 38 之後這條路不再冒「建立新實體」，已經順了。

⚠️ 所以先釐清需求：這張票要補的是**改實體正式名稱**那一半。開票時編劇的原話是
「無論是正式名稱或者是別名」—— 如果別名那半有別的不順（例如想一次改掉某個實體在**所有**
場次的叫法），那是另一件事（見下面「不在範圍」的合併／代換那條）。

## 形狀

在**把 chip 拿回來改**的那份選單裡多一列 —— 條件是「手上那一筆命中，但框裡的字不等於它在
目錄裡的名字」：

```
📍 test1（1 場）                    ← 命中：指回同一筆實體，這一場顯示 `test`
✏️ 把實體改名為「test」（1 場）      ← 新的這一列
🔗 作為既有實體的另一個名字…
```

兩列的差別要讀得出來：上面那列是「這場顯示為 test，實體還是 test1」，下面那列是
「這筆實體從此叫 test」。

⚠️ **改名不代換全文** —— 這是既有決策（`entity-field.tsx` 的 `alias-rename` 註解）：
別場的顯示名是**那一場的別名**，不該被順手改掉。但改名之後編劇會看到別場仍印舊字，
所以那一列得把場數寫在按下去之前（`（1 場）`），比照升格那列的做法（ADR-0006）。

**待裁決：**（已裁決，見下面的 Comments）兩種都能說出道理 —— 所以**不在票裡裁死，交給按下去
的當下**：別場還印著舊名時才問，問完才動。

## ⚠️ 硬約束

- **改名是專案層級的動作。** 實體屬於專案，不屬於劇本 —— 改完之後**別的劇本也會看到**。
- **⌘Z 回不來。** 改名走 server action，不進 ProseMirror 的 history。這與票券 37
  （undo 回到打過的字）是同一個接縫，做之前先看那張票落地成什麼樣。
- **孤兒改不了名。** 改名列只在手上那一筆或目錄命中時出現，不放寬 `existing()`
  （ADR-0005，票券 38 那條界線）。

## 不在範圍

- **合併兩筆實體**（把指向 A 的引用全部改指向 B，A 變孤兒自動消失 —— ADR-0005 講過形狀）。
- **代換全文**：改名連帶改掉所有場次的顯示名。上面「待裁決」那段先有答案才談。
- 從場次簡表以外的地方改名（人物總表之類的面板，v1 還沒有那個畫面）。

## 驗收

- [x] 把 chip 拿回來改、輸入一個與實體名不同的字 → 選單出現 `✏️ 把實體改名為「X」（N 場）`。
- [x] 按下去 → 目錄裡那筆的名字變成 X；**這一場**的顯示名也變成 X。
- [x] 別的場次引用同一筆實體時，顯示名**不動** —— 除非編劇在第二步選了「連那 N 場一起改」。
- [x] 框裡的字等於實體名（沒改）時，那一列**不出現** —— 沒有東西要改。
- [x] 孤兒不出現改名列。
- [x] 地點欄、登場人物欄、對白人物欄走同一段程式碼。
- [x] 別名那條舊路（`🔗` → 挑實體 → `同時把實體改名為…`）行為不變 —— 留著的理由見下。

### 2026-09-11 — 收票

**裁決（編劇）：代換全文不在票裡裁死，交給按下去的當下。** 「顯示名剛好等於實體名」是還沒
取名、不是別名，所以它**可以**跟著改 —— 但那是編劇的話，不是系統的預設值。於是改名那一列
按下去之後，若還有別場印著舊名就展開第二步：

```
✏️ 把實體改名為「海豚公寓客廳」（3 場）      ← 第一步
   只改這一場的叫法 —— 另外 1 場繼續印「海豚公寓房間」
   連那 1 場一起改成「海豚公寓客廳」
```

沒有別場印舊名就一步改完 —— 沒得問就不問。真正取過名的引用（顯示名 ≠ 實體名）**永遠不動**。

**開票時的形狀改了一處：改名列排在 `＋ 建立新實體` 後面，不是命中列後面。** 第一列是 Enter
會做的事，而改名是專案層級、⌘Z 回不來的動作 —— 它該是按出來的，不該是打完字順手 Enter 就
發生的。命中列與改名列並列的樣子仍在（拿回來的是別名、字沒動時）。

**條件也不是開票時寫的「手上那一筆命中」。** 打了新字之後手上那一筆就不再算命中（票券 38 的
`editingMatch` 刻意如此），而那正好是要改名的時候。實際條件是**手上握著一筆實體、且框裡的字
不是它在目錄裡的名字**；孤兒仍然進不來（它沒有被握在手上）。

**舊入口留著。** 新的 ✏️ 只認手上那一筆，做不到「打一個新名字 → 指向另一筆既有實體 → 順手把
那筆改名」；舊的 🔗 路做得到。兩者不重疊，所以不收。

### 2026-09-11 — code review 之後改掉的四件事

1. **第一列的數字換算法。** 原本印「這筆實體用在 N 場」，聽起來像會動到那麼多場 —— 但改名
   預設一場都不代換。改成印**代價**：`✏️ 把實體改名為「X」（還有 N 場印著「舊名」）`，
   與第二步同一個數字（`scenesShowingName`）。一場都沒有時連括號都不印。
2. **「那 N 場」包含編劇正站著的這一場。** 他改的是**這一欄那一筆**，同一場的別欄（登場
   人物欄與對白人物欄常是同一個人）仍印著舊名 —— 那一場確實還印著舊名。所以措辭是
   「還有 N 場印著…」而不是「別的 N 場」，第二步第一列也改稱「只改**這一筆**的叫法」。
3. **寫不進 doc 時整個改名都不做。** 原本先改目錄、再寫 doc，command 被拒絕就只 warn ——
   留下「目錄改了、稿沒改」而且 ⌘Z 回不來的半套。順序反過來：doc 先，拒絕就整個不動。
4. **打的字剛好是另一筆存在實體的名字時，改名列不出現。** 那會讓目錄有兩筆同名；編劇要的
   多半是「這一場指的是那一筆」（`📍` 那一列），或把兩筆併起來 —— 合併不在這張票裡。
   同一條線本來就擋掉了 `＋ 建立新實體`，理由一樣。

另外把三個欄位的接線抽成 `editor/retitle-others.ts`（原本 scene.tsx 與 blocks.tsx 各抄一份）。

### 2026-09-11 — 收票回饋：三件關於「回饋感」的事

人工驗收之後編劇提了三條，都不在原票的七條驗收裡 —— 它們問的不是「改名做不做得到」，
而是**編劇看不看得出來自己在做什麼**。

1. **命中列的場次數少算一場（bug，不是措辭）。** `entityUsage` 走 doc，而把 chip 拿回來的
   第一步就是把引用從 doc 上撤掉 —— 於是 `📍 派出所（3 場）` 在編輯的那一刻變成 `（2 場）`。
   那筆實體並沒有變小，編劇也還沒決定要不要留下它。判準與 ADR-0005 那條邊界同一條：
   **手上那一筆不是孤兒**。改法是在 `editRef` 呼叫 `onCommit` **之前**先問一次場次數並記住
   （`heldScenes`）；同一場的別欄也引用它時不會多算一場，因為快照本來就是場次單位。
2. **字全刪光時完全沒有回饋。** `menuOpen` 的條件是框裡有字，刪到空的那一刻選單整個收掉 ——
   畫面上沒有任何東西說「你手上還握著『派出所』」，看起來跟從沒填過一模一樣。但後果完全不同：
   **空著離開就是把這一場的它拿掉**。
3. **編輯 chip 時看不到改名這條路。** 字還等於實體名時沒有任何一列提到改名（確實沒東西可改），
   於是編劇不會去試一個他不知道存在的東西。

②③ 是**同一行字的兩種狀態** —— 選單頂端一行唯讀抬頭（`heldNote`）：

```
✏️ 手上是「派出所」—— 打字可改名，空著離開就是拿掉它     ← 框裡是空的
✏️ 改這裡的字，就能把這筆實體改名                        ← 字還沒改
（沒有抬頭）                                             ← 字改了：真正可按的 ✏️ 已經在選單裡
```

它**不進 `rows`**：選不到、Enter 碰不到、`aria` 上是 `presentation`。標籤放結果、說明另外放
—— 這條分工是票券 36 立的，等 36 的側邊說明欄落地，這一行可以搬進去。

**沒有做的兩件事，以及為什麼：**

- **括號裡不塞第二個數字。** 一度想把改名列寫成「這筆用在 3 場，其中 2 場印著舊名」，編劇
  否決：別名多的時候一列括號會扛太多資訊。改名列維持一個數字（代價，`scenesShowingName`），
  命中列維持一個數字（這筆實體多大，`entityUsage`）—— 兩列各回答一個問題。
- **不提前做票券 36 的側邊說明欄。** 那是一整個跟著 active row 走的 detail pane；這裡要的
  只是一行固定的抬頭，形狀不同。
- 順帶澄清一條**不是 bug 的行為**：拿起一個**別名** chip、字沒動時 `✏️ 把實體改名為「分局」`
  照樣出現。那不違反「改字才能改名」—— 那個字本來就不是實體名，確實有東西可改。

**落地：** `entity-field.tsx`（`heldScenes` 快照、`scenesOf`、`heldNote`）、`styles/editor.css`
一條樣式、測試 6 條（`entity-field.test.tsx` 的「手上握著一筆實體時的回饋」）。既有兩條測試的
期望值從 `2 場` 改成 `3 場` —— 那本來就是實機會看到的數字，是測試 Host 的 `usage` 假成常數才
沒抓到；Host 的 `usage` 現在收得到欄位上還剩哪些引用。

### 2026-09-11 — 收票回饋第二輪：那行抬頭自己長出三個破綻

編劇看了實機，抬頭那一行本身有問題（前一輪的三條裡有兩條是被它引起的）：

1. **框裡空著時它不收。** blur 不會把它清掉（`commitText` 在沒字時直接 return，不 reset），
   所以移開了還掛在那裡。
2. **按 Esc 收掉之後重新打字，畫面說它仍在改原來那一筆** —— 冒出 `✏️ 把實體改名為「hff」`。
   編劇的原話：「弔詭的是，正在修改不應出現『建立新實體』的選項」，兩列同時在的畫面說不通。
3. **刪光第二個 chip 的字之後，感覺直接跳進了前一個 chip 的編輯狀態**，突兀。

三條是**同一個病**：字刪光之後我們還握著那一筆。按鍵次數其實一直是對的（反白 → 刪光 →
再一次 Backspace 才輪到前一個），錯的是**中間那一步畫面還說「手上是 B」**，而 B 早就不在了。

**改法：`onChange` 收到空字串就放手**（`editing.current`／`heldScenes` 一起清）。引用在 chip
被拿起來時就從 doc 撤掉了，字再刪光，編劇看到的就是「這一場的它沒了」—— 還握著它只會製造
一個看不見的狀態。放手之後那一步成為一個乾淨的落點：B 消失、游標停在前一個 chip 後面，
再一次 Backspace 才輪到它（票券 34 那條「空欄位的 Backspace」原封不動）。三條一起消失。

**抬頭的文案改成正式筆調**（編劇指定）：`✏️ 正在編輯「派出所」，修改文字可更新名稱`。
空字串那個狀態沒有了，所以只剩這一種措辭；而且它**字改過之後仍然在** —— 那時框裡的字已經
不是那筆實體的名字，「我在編輯誰」更需要有人說。

**「正在修改不應出現建立新實體」暫時不動。** 那個畫面出在「刪光重打」那條路上，放手之後
就不會再出現（重打的字只會有 `＋ 建立新實體`）。真的**改字**時兩列並存是刻意的：一列是
「這一場換成另一個人」，一列是「這個人改名」—— 那正是 §4.7 要編劇說清楚的兩件事。
⚠️ 若實機再看一次仍覺得不對，那會是票券 38 那條「編輯既有那一筆時不該冒出建立新實體」
沒補完的另一半，該開在那裡。

測試多 3 條（放手、重打不是改名、刪光是乾淨的落點），共 9 條。

### 2026-09-11 — 收票回饋第三輪：清空不等於放手

上一輪把「字刪光」和「放掉那一筆」併成同一步，**吃掉了改名最自然的手勢** —— 清空重打。
編劇指出：反白全刪是為了好刪，不是為了放棄那一筆；清空之後他可能正要重新命名它。

於是從尾端退回去是**三段**，每一下都是一個停得住的狀態（`a b c`）：

| 第幾下 | 發生什麼 | 畫面 |
| --- | --- | --- |
| ① | 拿起 `c`，變回文字並整串反白（票券 34） | `a b [c̲]` |
| ② | 清空。**還握著** —— 這裡才是 ✏️ 的入口 | `a b \|` ＋ 抬頭 |
| ③ | 放手：這一場對 `c` 的引用沒了 | `a b \|` |
| ④ | 才輪到 `b` | `a [b̲]` |

②③ 併不得。併了就是「清空＝放棄」；分開之後 ② 是個**除了抬頭以外看不見的狀態**（框空著、
chip 也不在了），所以那時抬頭換一句話，說出下一顆 Backspace 會做什麼：

```
✏️ 正在編輯「派出所」，修改文字可更新名稱                ← 框裡有字
✏️ 正在編輯「派出所」，再按一次 Backspace 移除這一場的引用  ← 框裡空著
```

**框裡空著時按 Esc 或移開欄位也是放手** —— 抬頭是那個狀態唯一看得見的地方，收掉它卻留著
持有，下一個字打下去就會變成「把它改名」（那正是上一輪那張截圖的弔詭）。

實作上多了一個 `letGo()`：手上那一筆住在 ref（`editing`）裡，放手不會自己驚動 React，所以
它順手 `redraw()`。空欄位的 Backspace 現在先問「手上還握著嗎」，握著就放手、不去拿前一個。

測試多 4 條（清空還握著、清空重打是改名、Backspace 三段一路到底、空著離開就是放手），共 13 條。

### 2026-09-11 — 收票回饋第四輪：放回原位

點中間那一筆改完之後它跑到隊尾。原因是 `editRef` 先把它從欄位上撤掉，而 `merge` 一律接在
後面 —— 對新加的一筆是對的，對「拿起來改」不是：**編輯不是新增**。

登場人物欄的次序是編劇排的（誰先出場、誰是主角，交件文件會照這個序印），改一個字不該
重排它。`editRef` 記下原本排第幾（`heldIndex`），`merge` 就插回那一格；一口氣切出好幾筆
（`小明、小華`）整串插在同一個位置，順序跟他打的一樣。真正新打的一筆仍然排在隊尾，
升格出來的那一位也是（它是新的一筆，不是誰被放回去）。

測試 4 條（原封放回、改成別人、一次切好幾筆、新打的照樣在隊尾）。

**（同日追加）編輯途中也要留在原位。** 上一條只修了放回去那一半：輸入框永遠渲染在所有 chip
之後，所以改到一半那一筆看起來在隊尾，放回去又跳回原位 —— 中間那一段畫面是騙人的。
現在輸入框渲染在 `heldIndex` 那一格（`阿盈 ▸輸入框◂ 小明`），放手之後回到隊尾。
`useChipCaret` 跟著多一個 `home`（輸入框排第幾格）：← 退進的是**輸入框左邊那一個**、
→ 走到輸入框左邊那一個就進框裡 —— 走的是看得見的順序，不是陣列的尾端。測試 3 條。

**（同日追加）夾在中間的輸入框寬度依內容而定。** 它平常是彈性的（`flex: 6ch`，吃掉整行剩下
的空間），夾在 chip 中間那條彈性就成了一道**把後半排推開的空白**。只在那個位置換成
`field-sizing: content`，並給 `size` 當退路（`size` 以平均字寬計，中日文會排得太窄，所以
拉丁字母與標點之外一律算兩格 —— `columns()`）。

### 2026-09-11 — 收票回饋第五輪：一次只編輯一筆

正在改 A 的時候點 B，B 進編輯而 **A 直接不見** —— A 早就不在 `refs` 裡（拿起來那一步就撤掉
了），`editRef` 裡那行 `onCommit(refs.filter(...))` 過濾不到它，於是它連個殘影都沒留下。

`editRef` 開頭早退：手上握著一筆就不接手。別的 chip 的 `×` 同一條線（它會走同一個
`onCommit`，一樣會吃掉手上那一筆）。要換一筆，先把手上這一筆定案。

⚠️ **另一條路沒有走**：點 B 時先把 A 定案（等同 blur 的行為）再拿起 B。它比較順手，但編劇
這一輪明確說的是「不允許啟用其他 chip 的編輯」，所以照字面做；真要改成自動接力，把這條
註記翻出來即可。測試 3 條。

**（同日追加）動不得的 chip 要看得出來，chip 之間也太擠。** 鎖住之後指標仍是 `pointer`，
× 看起來照樣可按 —— 加 `.entity-chip--locked`（chip 與它的 × 都改回一般指標）。
間距那條是 `display: contents` 的缺口：chip 都包在 `.entity-field__chips` 這個純結構 span
裡，那個 span 不是 flex 容器，所以 chip 之間**一條 gap 都沒有**（只有 span 與輸入框之間有）。
改成 `display: contents` 讓每個 chip 直接成為 `.entity-field` 的 flex 項，整排吃同一條 gap，
順手把 gap 從 4px 調到 8px。輸入框夾在中間時同一排有兩個這種容器，這條也讓間隔不會分成兩種。

### 2026-09-11 — 收票回饋第六輪：改成接力，編輯中也還是一顆 chip

**接力取代上一輪的「擋住」**（編劇裁決，想先試用看看）。手上握著一筆時點別的 chip 或按它的
×，手上這一筆先定案放回原位，那一下才輪到新的。決定的理由是一致性：**跨欄位點過去本來就是
接力**（焦點一走，`blur` 就把手上那一筆定案，它鎖不起來也不需要鎖），同一欄裡擋住會讓同一個
手勢有兩種結果。

實作上「放回 A」與「拿起 B」必須落在**同一次 `onCommit`**（`refs` 是 prop，中途不重繪，分兩次
寫會被舊清單覆蓋），所以拆出 `settleHeld()`：它只算出「放回之後的清單」，不自己寫回。定案
可能要先建一筆實體（`onCreate` 是 async），所以接力那條路是非同步的 —— **沒握著任何一筆時
同步走完**，不讓平常點一個 chip 慢一拍（第一版忘了這條，34 條既有測試立刻紅）。

編劇問過的兩件，一併記下來：

- **「不小心點到刪除鈕」不是新風險。** 接力下是「A 定案回原位、B 被刪」，兩件都可預期，⌘Z
  也回得來。唯一有代價的情況是 A 的字被改過且是個新名字（接力會順手建一筆實體）—— 但那跟
  打到一半移開欄位完全一樣，`blur` 早就這麼做了。
- **刪除鈕不給警告。** 刪 chip 只是拿掉這一場的引用，doc 進 undo 歷史；實體也不會被刪
  （「刪除實體」這個動作不存在，ADR-0005）。可逆的動作加確認只會讓人學會無視確認框。

**編輯中的那一筆看起來還是一顆 chip。** 原本點下去 chip 整個變成裸字，記號、邊框、內距一起
消失，整排跟著位移 —— 畫面跳得比實際發生的事還大。現在輸入框住在一層外殼裡，記號與邊框
都留著，寬度跟著字走。那層外殼刻意**不掛 `.entity-chip`**（那個 class 是「一筆已經定案的
引用」，選它的程式與測試數的就是這個），視覺靠共享同一組宣告。

順帶把上一輪的 `.entity-chip--locked` 拆掉 —— 沒有東西被鎖住了。測試：接力 4 條、外觀 1 條。

### 2026-09-11 — 收票回饋第七輪：接力改回擋住，游標歸編劇管

**接力被推翻，改回擋住**（編劇裁決，試用後）。理由是他實際用出來的：「很難說編劇是想建立
實體還是改名」。接力少一次點擊，但同一個手勢有兩種看不見的結果 —— 手上那串字可能被當成改名
定案，也可能被當成一筆新實體建出來，而**按下去之前沒有人說得出是哪一種**。上一輪我用「跨欄位
本來就是接力」論證一致性，那個論證本身沒錯，但它比不過可控性：跨欄位是編劇主動離開這一欄
（焦點走了，`blur` 定案是他預期的），同一欄裡點隔壁那顆 chip 不是。

`settleHeld()` 整支拿掉（沒有呼叫端了），`.entity-chip--locked` 裝回來。擋住時**`preventDefault`
一定要照做** —— 少了它，那一下會讓輸入框 blur，而 blur 會把手上那一筆定案，擋住就變回接力。

**`caret`：游標停在哪，是一個獨立的狀態。** 原本只有 `heldIndex`（拿起來的那一筆排第幾），
這一輪擴成一個 ref，因為編劇要的三件事本來就是同一件事：

1. 拿一筆起來改時，輸入框停在它原本那一格（上一輪就有）；
2. **定案之後游標停在那一顆之後** —— 原本無論改哪一顆，游標都退回最後方；
3. **點兩顆 chip 之間那道縫，游標就插進那一格** —— 下一筆實體落在編劇指的位置。

那道縫**同時是間距與插入點**：橫向間隔改由它自己撐（`.entity-field` 的 column-gap 設 0），
否則縫隙兩側會各再多一道空白。游標現在站的那一格不掛 `--pick`（點了也是原地），握著一筆時
整排都不掛。連帶：空欄位上的 Backspace 拿的是**游標左邊**那一顆，不是隊尾那一顆；放手之後
游標也留在那一格（`阿盈 |小明`），不跳回最後。

**滑鼠點 chip 進來也整串反白。** 原本滑鼠進來游標停字尾、Backspace 進來整串反白，同一個狀態
兩種樣子。統一成反白：可以直接覆寫，也還是能按 → 收起來接著改。`selectAll` 這個參數於是沒有
`false` 的呼叫端了 —— 一併從 `useChipCaret` 與 `extras-field` 拿掉。

**編輯中那一顆的 × 裝回來，行為與唯讀 chip 的 × 一致**（移除這一場對它的引用）。編劇提的三個
選項是「保留 ×／只留空間／換一個同空間的圖標，點擊＝清空文字」，我選了第一個：同一個符號在
兩個狀態下不該有兩種意思，而「清空文字」已經有 Backspace 與全選覆寫兩條路。裝回來也順便讓
「點下去那一刻整排不位移」這件事真的成立 —— 上一輪少了這顆按鈕，寬度還是會縮一下。

**編輯中那一顆改用底色，不用焦點環。** 那一圈實線把一顆 chip 讀成了一個對話框。游標本來就在
框裡閃，底色只是指出它在哪一顆裡面。

測試：擋住 4 條、縫隙 5 條、游標位置 2 條，改寫 2 條（滑鼠反白、放手之後的位置）。

### 2026-09-11 — 收票回饋第八輪：把跳動的最後幾格擠掉

四件外觀的，一件是問的。

**編輯中那一顆改用邊框顏色，不用底色。** 底色用的是 `--selection-bg` ——**與選字的反白同一個
顏色**。在一個正在編輯的文字框裡，那是最容易被讀成「這幾個字被選起來了」的訊號，於是「正在
編輯」這件事反而更看不出來。邊框本來就在，只是換個顏色，不多畫任何東西（焦點環那一圈實線
上一輪已經被否掉：太重，把一顆 chip 讀成了一個對話框）。

**游標插進 chip 之間不再撐開一塊空間。** 原本一道縫的地方變成「縫 ＋ 空輸入框 ＋ 縫」。兩層
都修：空的輸入框兩側那兩道縫收成零寬（`--flush`），輸入框本身也不再吃那條彈性寬度 ——
`--inline` 的條件從「正在編輯」放寬成「夾在 chip 中間」，只是把游標插進去也算。打了字兩道縫
就回來，字自然把兩邊的 chip 擠開。

**單字元的名字點一下不再變胖。** `size` 的下限是 2，而 `.entity-field__input--inline` 的
`min-inline-size` 也是 `2ch` —— `a` 這種名字於是被撐得比它唯讀時還寬（其他名字都超過 2ch，
所以只有短名字看得出來）。兩處下限都拿掉：`size` 下限 1（`0` 不合法），`min-inline-size: 0`，
空的時候靠 `field-sizing: content` 自己留出游標的寬度。

**按不動的 × 不再有 hover／active 回饋。**

長出來的一個 bug：**打頓號切出 chip 那條路沒有放下手上那一筆。** `Enter`／離開欄位走的是
`reset()`（會清掉），`小明、` 這樣即時切 chip 走的是 `resolveAll()`，少了那一句 —— 手會一直
握著一筆放不下來（抬頭不消失、其餘 chip 一直是 locked）。這一輪才看得出來，是因為
`--inline` 的條件現在也問「手上握著誰」。

**「改過字之後直接點別的欄位，要不要跳確認框？」—— 我的意見是不要，先不做。** 三個理由：
`blur` 定案是整個編輯器一致的行為（每一個欄位打到一半移開都會定案，不只這裡）；`blur` 的
結果其實是**可預期的單一種**，它永遠走「命中既有就用既有、沒命中就建一筆新的」，**永遠不會
改名**（改名只有選單那一列，而那一列要點）；而且它可逆，⌘Z 回得來。移開焦點在寫作裡發生的
次數太多，那個頻率的確認框會被學會無視，於是真正該攔的時候也攔不住（§7.3）。

真正的殘留風險只有一個：改過字之後 blur，會**憑空多一筆實體**。那筆實體是孤兒，不會出現在
自動補全（ADR-0005），但它確實躺在目錄裡。這件事該解的地方是票券 37（⌘Z 的接縫）—— 讓撤銷
把那一半也帶走，而不是在每次移開焦點時問一個問題。

### 2026-09-11 — 收票回饋第九輪：縫也是方向鍵的一站

**半寬，不是零寬。** 上一輪把空輸入框兩側的縫收成零，於是那兩顆 chip 直接黏在一起，比別處
更擠 —— 修過頭了。各收半寬：兩道半寬 ＋ 幾乎沒有寬度的空輸入框 ＝ 原本那一道，間距看起來
不變。

**方向鍵停得進那道縫**（編劇指定的順序）。`A B C |` 一路往左是 **chip 與縫交替**：C、
`B|C`、B、`A|B`、A、`|A`，走完最前面那道縫才出這一格；`→` 反向同理。`useChipCaret` 因此多
一個可選的 `moveCaret` —— 有給才有「縫」這一站（實體欄位有，群演欄沒有，它的輸入框永遠在
隊尾）。同時補上輸入框那一側的 `→`：夾在中間時它右邊還有 chip，原本走不過去。⌘→ 也順手把
輸入框排回隊尾（那一鍵的意思就是「這一格的最後」）。

`moveCaret` 在手上握著一筆時不動作 —— 那一刻「輸入框排在第幾格」說的是那一筆的位置，挪走它
畫面就對不上了。

**欄位右半邊那一大塊空白不再是死的。** 輸入框在隊尾時吃掉剩餘空間的是它自己
（`.scene__chip input` 的 `flex: 1 1 6ch`）；游標插到中間之後那條規則就不適用了，於是點欄位
右半邊既不聚焦也進不了游標。改成尾端那道縫 `flex: 1 1 auto` 吃掉剩下的，點它 ＝ 游標回到
最後面。
