# 69 — 存不進去的稿，關掉分頁之後救得回來

**What to build:** 自動存檔存不進去時，把手上那份稿在這台瀏覽器留一份（localStorage／IndexedDB）。
分頁關掉、重新整理、瀏覽器當掉之後再打開這份劇本，偵測到本機有一份比伺服器新、還沒落地的稿，
讓編劇決定要不要拿回來。

**Blocked by:** 65（重試、`hasPending()`、離開前提醒都在那張票）

**Status:** needs-triage

## 為什麼

票 65 之後，存不進去的稿**只活在這個分頁的記憶體裡**。離開前提醒擋得住「手滑關掉」，擋不住：

- 分頁被瀏覽器回收、作業系統重開、筆電沒電；
- 編劇看到提醒仍然按了「離開」（以為等一下再存就好）；
- 自動存檔停手（`conflict`／`forbidden`）之後，畫面叫編劇重新整理 —— 一整理，停手後打的字就沒了。

斷線時寫稿是編劇真實會遇到的情境（高鐵、咖啡店），而丟稿是劇本工具最不可原諒的故障。

## 為什麼另開、而不是併進 65

這已經碰到**離線編輯**的邊。spec 範圍表把「即時協作與離線編輯」列為不做（受約束 3 保護，§12）。
這張票要先回答它是不是「離線編輯」：只做「救回來」、不做「離線時照常同步」，範圍可能站得住；
但救回來的那一份怎麼跟伺服器版本、存檔 token 對上，就是一個小型的合併問題。

## 開工前要定的事

- **範圍站不站得住**：「本機備份 ＋ 重開時問要不要拿回來」算不算 spec 排除的離線編輯？要不要在 spec 範圍表補一行。
- **什麼時候寫備份**：每次存檔失敗時？每次 `changed()`（不管成敗）？只在 `hasPending()` 為真時？寫入頻率與 doc 大小（幾百 KB）對 localStorage 配額（約 5 MB）的影響 —— 可能要 IndexedDB。
- **什麼時候清掉**：存進去之後立刻清？要不要保留最後一份當保險？
- **救回來時跟伺服器版本的關係**：
  - 本機那份的基準 token 與伺服器現在的 `doc_seq` 相同 → 可以直接套上去再存。
  - 不同（別的分頁、別台裝置在那之後存過）→ 是 `conflict`。給編劇看兩份？只給「下載本機那份」當逃生口？
- **問的形狀**：重開時跳一個「這份劇本有一份沒存進去的版本（X 分鐘前）—— 拿回來／丟掉」？丟掉要不要再確認一次？
- **多個劇本、多個分頁**：備份的 key 用 `screenplayId`；同一份劇本開兩個分頁時誰的備份算數。
- **隱私**：共用電腦上，登出之後本機還留著稿。登出時要不要清？
