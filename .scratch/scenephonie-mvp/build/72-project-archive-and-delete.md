# 72 — 專案封存與刪除

**What to build:** 專案可以**封存**（從儀表板收起來，資料不動，隨時還原），也可以**刪除**（先進「已刪除」區
保留 30 天，期間可以救回；30 天後永久刪除，劇本、文件、備份、交付與分享連結全部清掉）。

**Blocked by:** 71

**Status:** needs-triage

## 為什麼

[71](./71-project-dashboard-and-create-flow.md) 把建立改成手動、片名可以留白之後，儀表板很快會堆出幾個
「未命名專案」。v1 原本沒有刪除專案這件事（票 06 的冪等論證就建立在「清不掉」上）。

## 已定（使用者裁決，2026-10-23 grilling）

1. **封存與刪除兩種都做。**
   - 封存：從儀表板主區收進「已封存」，資料不動，可以還原。
   - 刪除：進「已刪除」區保留 **30 天**，可以救回；卡片顯示「還剩 N 天」。過了就永久刪除。
2. **分享連結**（ADR-0008 的活連結與凍結連結）：
   - **封存期間兩種都照常有效** —— 封存是整理儀表板，不是收回作品；已經交出去的稿不能因此打不開。
   - **一進「已刪除」區兩種就全部失效，救回後恢復** —— 按刪除就是「我要收回這部作品」。
   - 失效的連結對訪客顯示的跟被撤銷的連結一樣（§ 分享連結：中性頁面「這條連結已停用」），
     不透露是封存、刪除還是撤銷。
   - 這不違反 ADR-0008：凍結連結承諾的是**內容不變**，不是**永遠打得開**；刪除與撤銷同類，是收回分享關係。
3. **永久刪除搭現有的排程** `/api/cron/guest-cleanup`（每天一次，票 07）。票 07 的立場是「同週期、同失敗後果的
   工作不另開排程」，這支清理同樣符合。端點仍然不收參數，只執行寫死的政策。

## 開工前要定的事

- **欄位**：`projects.archived_at`／`deleted_at`（兩欄可以同時有值嗎？刪除一份已封存的專案，救回時回到哪一區？）。
- **gate 怎麼看待已刪除的專案**：授權閘門（`authorizeProject`）要不要對 `deleted_at` 不為 null 的專案回 `null`？
  回 `null` 就是所有頁面 404，救回只能從儀表板走 —— 這最省，但要確認不變式 H 的 handle 不因此多一種狀態。
- **分享連結的失效寫在哪**：讀連結時 join 專案看 `deleted_at`，還是刪除時寫入連結？後者救回時要還原，前者不必。
  照「救回後恢復」，讀時判斷比較乾淨。
- **永久刪除的範圍**：`projects` 一列 `DELETE`、靠 FK cascade 帶走其餘（票 07 訪客清理就是這樣驗的）。
  要確認 `deliveries`／`share_links` 的 FK 都是 cascade —— `deliveries` 是「唯一刻意不可變」的表，
  刪除它是 ADR-0008 之下第一次有交付消失，在票裡記一句理由。
- **cron 改名**：它不再只清訪客。`/api/cron/guest-cleanup` → 中性的名字，`vercel.json` 一起改。
- **確認對話框**：刪除要確認，但本 repo 有「不觸發瀏覽器原生 dialog」的慣例嗎？用頁內確認。
