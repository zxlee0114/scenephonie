# 71 — 專案儀表板與建立專案流程

**What to build:** 登入之後先看到**專案儀表板**，總覽自己所有的專案；按下「建立專案」才建立專案。建立之後
依序走過「片名 → 交件大綱 → 劇本」，每一步都可以略過，也有一個「直接開始寫」的出口一次跳過整段、
直接進劇本編輯器。

**Blocked by:** 無（06 已完成）

**Status:** needs-triage

## 為什麼

使用者一直以來想像的流程就是這樣：登入 → 總覽專案 → 明確建立 → 依交件順序備好文件 → 寫劇本。
票 06 實作時把 `/projects` 做成轉接口、第一次登入就自動開專案（開工決定第 3 條），理由是「v1 使用者只會有
一個專案在寫」。**那一條是實作時寫在 Comments 裡的判斷，不是使用者裁決過的**；看到 `/projects` 這個路徑，
使用者以為建立專案的地方只是還沒做。本票補上的是使用者原本的流程，不是推翻一個裁決。

## 已定（使用者裁決，2026-10-23 grilling）

1. **登入落點是儀表板**（`/projects`），不再自動開專案。一個專案都沒有的人看到空的儀表板，上面一顆「建立專案」。
   - `/`、`/login`（已登入）、Google 登入的 `callbackURL` 都照舊指向 `/projects`，只是它從轉接口變成畫面。
   - `landingProject()` 的「沒有就開一個」退場。訪客入口仍然要替訪客建範例專案（票 07），那條路不受影響。
2. **建立專案不問類型。** v1 只有單一劇本（§4.2「v1 不提供類型選擇、不做 UI」照舊成立），`projects.type`
   照樣寫單一劇本。系列劇本做出來那天，類型這一步插回流程最前面。
3. **第一步填片名，可以留白**（留白＝預設名稱，之後在 hub 改）。「直接開始寫」放在同一個畫面上。
4. **依序建文件是建立流程本身，每次建專案都走**，不是教學（引導是另一件事，見 [73](./73-onboarding-tour.md)）。
   v1 的順序是 **片名 → 交件大綱 → 劇本**；角色設定表在票 21 第 ② 片完成時插到交件大綱之後。
   每一步都可以略過；略過的文件之後從 hub 補。
5. **儀表板卡片**：片名＋最後編輯時間，最近編輯的在前。「已封存」「已刪除」兩區的位置先留給
   [72](./72-project-archive-and-delete.md)。
6. **既有使用者不受影響**：已經有專案的人登入後看到儀表板，上面就是他原本那個專案。

## 開工前要定的事

- **建立流程的形狀**：精靈式的連續頁面（`/projects/new` → …），還是建好專案後在 hub 上依序亮起下一步？
  影響「中途離開，下次回來從哪裡接」。
- **交件大綱那一步**：直接打開那份（固定的）故事大綱編輯頁（帶「下一步」「略過」），還是只問要不要現在寫？
  交件大綱一個專案一份、第一次打開時建立（票 21，2026-10-24），所以這一步不會「新開一份」。
- **劇本什麼時候建**：專案與劇本 1:1 是單一劇本專案的定義（§4.2），劇本應該跟專案一起建，
  「進入劇本」只是導覽。照這樣，留白片名＋立刻「直接開始寫」等於一次建好專案和劇本，然後進編輯器。
- **建立是 POST**（server action），不是 GET —— 票 06 的 `landingProject()` 為了 GET 上的寫入花了兩個
  交易和一把鎖保冪等；明確的按鈕讓這個問題消失，但連點兩次仍然要想（建兩個專案是不是可以接受）。
- **最後編輯時間**取哪一欄：專案底下任何一份劇本或文件的 `updated_at` 最大值，還是 `projects` 自己記一欄。
