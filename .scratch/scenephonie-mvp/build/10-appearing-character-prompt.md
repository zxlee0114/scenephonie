# 10 — 登場人物提示

**What to build:** 提示不是推導 —— 推導替編劇做決定，提示只指出落差、決定權在他手上。觸發條件：某人物在本場有**一般**發聲方式的對白，且不在本場的登場人物欄。標了 V.O./O.S. 的**絕不提示**（編劇已明確宣告那個人不入鏡）；反方向（在登場人物欄但沒台詞）也不提示。提示是一個**可忽略的選單**：`＋ 新增為登場人物` ／ `✕ 不新增 —— 他不入鏡`。**ESC 與「不新增」語意刻意分開**：ESC ＝「現在別煩我」，不記錄任何判斷、下次還會提示；「不新增」＝明確判斷，存進場次的 `dismissedCharacterIds`，這一場的這個人不再提示。「不再提醒」記的是 `sceneId`（標籤只負責讓人在彈窗裡看懂是哪一場）。系統不自動把有台詞的人加進登場人物欄。

- [x] ESC 後同一場同一人下次仍提示

### 待人工驗收

見文末「驗收回饋第二輪」—— 流程改了，原本這裡的步驟作廢。

**2026-09-29 — code review 之後改的三件事。** Spec 軸抓到兩個真的缺陷，兩個都先寫測試重現、
反證過（退回舊的 plugin，新測試確實 fail）：

1. **人物欄定案那一刻就跳選單** —— 正是裁決 2 否決的時機。bridge 的整份 replace 把 selection
   沖到 doc 一端，plugin 把那當成「游標離開了這一句」。更陰的是沖過去之後 selection **停在**那裡，
   接著進來的 focus transaction（不動 doc、不動 selection）也會被當成移動。修法：bridge 的
   transaction 打上 `KERNEL_REPLACE` meta，只有 `caretAt`／`keepCaret` 明確放回去的游標算數；
   其餘 transaction 要 selection 真的變了才算。⚠️ 這條測試單獨跑時曾經**假性通過**（斷言得太早，
   focus transaction 還沒進來），整套跑才掛 —— 測試裡多等一拍是故意的。
2. **定址只靠 `sceneId ＋ 序`**：在對白開頭 Backspace 併進上一段時，序換人了，選單會掛到下一句
   （問的是根本沒被碰過的那個人）。改成記 doc 座標、跟著 `tr.mapping` 走，被併掉就是被刪了；
   只有 bridge 的整份 replace 才退回 id 定址。
3. **懸空引用不問**：目錄裡沒有那筆人物時，「＋ 新增」會被不變式 ⑧ 拒絕，那一列就成了按不下去的
   承諾。

Standards 軸的採納：選單的兩個 handler 改在點擊當下讀 plugin state（ref／doc 是真相），
`notAppearing` 改名 `dismissAsNotAppearing`。沒採納的：`sceneById` 與 `sceneNow` 的重複在改寫
之後消失了；兩支 command 抽共用 helper、`dismissAppearingPrompt` 改名、選單借用
`entity-field__*` 的樣式 —— 都是判斷題，留著不動。

**2026-09-29 — 瀏覽器驗收回饋，改兩件事。**

1. **選單會遮住剛打好的對白** → 改排在台詞**底下、佔版面**（原本是絕對定位浮在人物欄下，正好
   蓋在台詞上）。不用絕對定位浮在台詞下，是因為那裡就是游標所在的下一段 —— 換成蓋住他正在寫的字。
   代價是下一段被往下推一次。
2. **不能用方向鍵選** → 使用者裁決：選單開著時 ↑↓ 歸選單（焦點仍在內文、打字照常）。第一次按
   才亮起一列，**仍然沒有預選**；Enter 只在有亮起的列時才算選擇，否則照常屬於內文 —— 原本怕的
   「順手 Enter 被加進去」因此還是擋得住。代價：選單開著時 ↑↓ 不移游標，要先 Esc。監聽掛在
   window 的 capture 階段、只認焦點在內文 contenteditable 上的鍵（人物欄等輸入框不受影響）。
   反證過：拿掉監聽，↓ 與 Enter 兩條測試 fail。

**2026-09-29 — 驗收回饋第二輪：焦點在選單上、選完才開下一段。**

使用者改定流程：對白寫完 → 人物不在登場人物欄 → 出現選單（焦點在選單上）→ 選完才開下一個
區塊。選單改回絕對定位、不推版面 —— 下一段還沒開，底下那一格沒有人在寫字。

- **只有 Enter 會問**（使用者裁決）：點走、方向鍵走出去都不問，漏掉的留給匯出前清單（票 11／19）。
  plugin 追蹤「游標在哪一句、何時離開」的那一整套因此拿掉，state 只剩「開著的那一份提示」。
- 攔 Enter 的是 `AppearingPromptPlugin` 的快捷鍵（priority 1102，搶在 `ContinueBlock` 前）；
  問完呼叫 `continueBlock(editor)` 接著做原本那一顆 Enter（從 `ContinueBlock` 抽出來 export）。
  焦點在選單上時 ProseMirror 的 selection 不動，台詞中間按的 Enter 選完也在同一個位置切。
- **沒有預選**：打開選單的正是一顆 Enter，連按第二下不該做決定。第一次 ↑↓ 才亮起一列。
- **Esc ＝ 跳過，照樣開下一段**、不記錄；**點到別處 ＝ 只收起**、不開下一段。
- 選單開著時每一顆鍵都歸它（Tab 也吞掉）。ProseMirror 本來就不收 node view 裡非內文元素上的鍵
  （Tiptap 的 `stopEvent`），所以 Backspace 碰不到台詞 —— 那條測試量的是這個行為，不是我們的
  `stopPropagation`（反證時拿掉它測試照過，查到是 `stopEvent` 在擋）。
- 懸空引用：選單沒有一列按得下去時，DialogueView 直接接著做 Enter，不留一個空選單。
- 測試踩到的坑：`commands.keyboardShortcut` 只抄 handler dispatch 的 steps，只帶 meta 的那一筆
  （打開選單）會被丟掉 —— 改用真的 keydown。反證：拿掉 Enter 攔截，15 條裡 10 條 fail。

### 待人工驗收（第二輪）

1. Tab 出一句對白、人物欄打「小明」（新建）、寫台詞、按 Enter → 台詞底下浮出選單，**下一段
   還沒開**、版面沒被推動；登場人物欄沒有被自動加上小明。
2. 直接再按一次 Enter → 什麼都沒發生（沒有預選）。
3. ↓ → 亮起「＋ 新增」；再 ↓ → 換到「✕ 不新增」；↑ 回去。
4. 在「＋ 新增」上按 Enter → 小明接在登場人物欄隊尾，選單收起，下一段對白開出來、焦點在它的人物欄。
5. 另一句按 Enter 叫出選單後按 Esc → 收起、什麼都沒記，下一段照樣開；回那一句尾端再按 Enter → 又問。
6. 選「✕ 不新增」→ 下一段開出來；回那一句再按 Enter → 不再問；⌘Z 撤得掉那個判斷。
7. 選單開著時點頁面別處 → 只收起，不開下一段。
8. 游標從一句沒列入的對白用滑鼠或方向鍵走出去 → 不問。

**2026-09-29 — 驗收回饋第三輪。**

- **唯讀提示斷行、面板看起來歪** → 面板寬度改成 `max-content`、那一行不斷行。人物名極長時面板
  會跟著變寬（沒有上限）—— 實務上名字不會長到那個程度，先不處理。
- **⌘Z 撤掉判斷之後焦點不見** → 選完焦點在新那一段的人物欄；⌘Z 由 `forwardHistoryKey` 送回
  文件，而那一步把新那一段連同判斷一起撤掉（ProseMirror 把 500ms 內的兩步併成一次 undo），
  握著焦點的輸入框跟著被拆掉，焦點掉到 `body`。修在 `forwardHistoryKey`：撤銷／重做後按鍵的
  那一格不在頁面上了，就把焦點還給內文（selection 已由 undo 放回台詞尾端）。一般 Enter 開出
  新對白後 ⌘Z 走的是同一條路，也一併修好。先寫測試重現（焦點落在 `body`），修完才過。

**2026-09-29 — 驗收回饋第四輪：兩列同時亮著。**

- **原因**：滑鼠停著的那一列靠 CSS `:hover` 亮，鍵盤走到的那一列靠 `.is-active` 亮，兩套各亮
  各的。選單剛好彈在滑鼠游標底下、再按 ↑，就兩列一起亮。改成同其他選單：`onMouseEnter` 直接
  設成亮著的那一列，拿掉 `:hover` 規則 —— 整份選單只有一個「現在停在哪」。先寫測試重現、反證過。
- **順手補的**：全套跑時「焦點在選單上」那條偶爾 fail —— 選單拿到焦點之後，被延後執行的 focus
  搶回內文。實際使用時若發生，↑ 會移游標、Enter 被攔著沒反應，正是「卡住」的樣子。選單開著、
  還沒回答時，焦點被拉回內文就收回來；回答之後（選了、Esc、點走）不收，免得跟 `resume` 搶。
  測試的 `press` 也改用同步的 `view.focus()`。連跑 6 次全綠。
