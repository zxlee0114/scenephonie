# 38 — 正在編輯的那一筆被當成不存在，於是冒出「建立新人物」（bug）

**症狀：** 點 chip（或空欄位按 Backspace）把一筆已經落地的人物拿回來改，選單裡卻出現
`＋ 建立新實體「服務生小李」` —— 而那個名字明明就是**手上正在編輯的那一位**。
回報時的原話：「既然已經是實體，應該就可以不必出現建立新實體的選項，我發現每個實體的編輯都有」。

**Status:** in-review

## 根因（已定位，不必再查）

`entity-field.tsx`：

```ts
const existing = () => { const counts = usage?.(); return counts ? options.filter(o => counts.has(o.id)) : options; };
const exact = known.find((o) => o.name === query) ?? null;
…
if (!exact) rows.push({ key: "create", label: `＋ 建立新實體「${query}」` });
```

`existing()` ＝ 目錄減掉孤兒（**存在＝被引用**，ADR-0005）。而 `editRef` 為了把 chip 變回文字，
**先把那筆引用從 doc 上拿掉**。如果那是它唯一的引用，它的 usage 就掉到 0 → 它離開 `existing()`
→ `exact` 是 null → 第四列冒出來。

也就是說：**它不是孤兒，它只是暫時被拿在手上。** ADR-0005 要擋的是 ⌘Z 留在目錄裡的殘骸，
不是一個進行到一半的編輯動作。

### 為什麼「每個實體的編輯都有」，但打字新建的人物有時看起來沒事

只有**唯一一筆引用**的實體才會掉出 `existing()`。地點永遠只被場次的地點欄引用一次 → 一定中。
升格出來的人物**不掛進登場人物欄**（票券 35 的裁決）→ 也是一次 → 一定中。反而是「打字新建的
人物」目前常常有第二筆引用而躲過去 —— 因為票券 08 那個**暫時**措施會把它自動加進登場人物欄。

⚠️ 那個暫時措施會被**票券 10** 拿掉。也就是說：這個 bug 現在是斷斷續續的，10 落地之後會變成
**一律發生**。先修，不要等它變得更明顯。

## 行為是對的，說謊的是標籤

按下去不會生出重複的實體 —— `resolve` 第一件事就是問 `editing.current`：「名字沒改就是原封放回，
用回它自己的 id」。所以這是**標籤與事實不符**，不是資料會壞。（與票券 35 code review 抓到的
那條假註解同一種錯：程式是對的，寫在旁邊的那句話不是。）

⚠️ 修法因此**不是**去改 `resolve`，是讓「手上那一筆」算數。

## 形狀

`exact` 的判定多認一條：**`editing.current` 手上那一筆，只要 query 等於它的顯示名（或它在目錄裡
的名字），就算命中。** 命中之後第四列自然不出現，第一列（`👤 服務生小李`）照舊印出來。

⚠️ 只認**手上那一筆**，不是把整個 `existing()` 放寬。孤兒仍然不進自動補全 —— ADR-0005 那條沒有
鬆動，這裡補的是「編輯中」這個**暫態**被誤判成孤兒。

## 不在範圍

- 措辭。`建立新實體` → `建立新人物`／`建立新地點` 是**票券 36** 的事，兩張票會碰到同一行，
  誰先做誰改，後做的沿用。
- 孤兒的清理。目錄 append-only、v1 永不清理，不動。

## 驗收

- [x] 一筆只被引用一次的人物 → 點它的 chip 拿回來改 → 選單**沒有**「建立新…」那一列，
      而且第一列印著它自己。
- [x] 承上，一個字都不改直接定案 → **同一筆實體**，人物表不多一列。
- [x] 承上，把名字改成一個沒人用過的字 → 「建立新…」那一列**回來了**（那才真的是新的一位）。
- [x] 承上，把名字改成**另一位既有存在人物**的名字 → 命中那一列在、「建立新…」不在。
- [x] 被引用**兩次以上**的人物：拿一筆回來改時行為不變（它本來就沒離開 `existing()`）。
- [x] 孤兒仍然不出現在自動補全（ADR-0005 沒有被這張票鬆掉）。
- [x] 地點欄與登場人物欄走同一段程式碼，同樣不再冒那一列。

## Comments

### 2026-09-10 — 開票

票券 35 的人工驗收期間，編劇在「升格完按 Backspace 把名字拿回來改」這條路上撞到的，
但盤過之後確認**每一個實體欄位、每一筆只被引用一次的實體**都會這樣 —— 所以獨立開票。

### 2026-09-10 — 實作

`entity-field.tsx` 多一支 `heldMatch(name)`：手上正在編輯的那一筆（`editing.current`），
只要 query 等於它的顯示名或它在目錄裡的名字，就回傳它在目錄裡的那筆 `EntityOption`。
`exact` 的判定改成 `known.find(...) ?? heldMatch(query)` —— **只有這一行**。

- `existing()` 一個字都沒動：孤兒仍然不進自動補全，ADR-0005 沒有鬆掉（那條邊界順手寫進
  ADR-0005 的「正在被編輯的那一筆不是孤兒」一節）。
- `byName()` 也**沒有**放寬。放寬它會在升格那一列生出一句新的假話：`promote` 是先
  `editing.current = null` 再 `resolve`，於是標籤會說「指向既有的 ⋯」但實際上會建一筆新的
  —— 正好是這張票在修的那種錯，方向相反。
- `resolve` 沒動（票券開票時就講明了修法不在那裡）。
- 措辭仍是「建立新實體」—— 票券 36 的事。

驗收七條都有自動化測試（`entity-field.test.tsx` 的「編輯中的那一筆不是孤兒（票券 38）」），
含「兩次以上引用行為不變」與「孤兒仍不進補全」兩條回歸。地點欄與登場人物欄共用同一支元件，
測試以 `kind="location"` 走那段程式碼。全套 387 passed、typecheck 與 lint 乾淨。
**人工驗收待編劇跑一次真的編輯器。**

### 2026-09-10 — code review 收斂

兩軸審查各自獨立抓到同一條**新引進**的缺陷，已修：

- **別名會被目錄名蓋掉。** 手上那一筆的顯示名是這一場的別名時（引用上的字，ADR-0005），
  第一列印的是實體名（`📍 海豚公寓房間`）—— 那是對的，它指的就是那筆實體 —— 但按下去
  原本會把顯示名一起換成目錄名，而 `resolve` 那條路會保留別名，兩條路說法不一。
  改成命中列**只有手上那一筆**用回框裡的字（目錄命中時兩者本來就相同）。加了回歸測試。
- **同一條判準有兩份副本。** `resolve` 的「名字沒改」與選單的判定各寫一次 → `resolve`
  改用同一支 `editingMatch`。
- `heldMatch` → `editingMatch`（貼齊檔內既有的 `editing`／`editRef` 詞彙）；拿掉
  `isExtraId` 那條冗餘守衛（群演本來就不在目錄裡）。
- 補上 `kind="character"` 的測試（驗收第 7 條原本只有推論），以及「仍是命中 chip 而非
  新建」的斷言（驗收第 2 條原本只間接靠 `onCreate` 未被呼叫）。

⚠️ **範圍外、待決策者確認**：這次順手在 `docs/adr/0005-entities-exist-by-reference.md`
補了一節「邊界：正在被編輯的那一筆不是孤兒」。票券只說 ADR-0005 沒有鬆動、沒有要求改 ADR。
內容與裁決一致，但要拿掉的話拿掉即可，程式不依賴它。

### 2026-09-11 — 人工驗收：七條通過，抓到一條重覆列

驗收七條全過。但編劇跑出一條票券沒想到的路，抓到**這張票引進的**新缺陷：

A 場地點打 `test` 建了實體 → B 場打 `test1` 走別名那一列、並選「同時把實體改名」→
目錄裡那筆現在叫 `test1`，**A 場的引用顯示名還是 `test`**。回 A 場把 chip 拿回來改，
選單印出**兩列一模一樣**的 `📍 test1（1 場）`。

根因是 `hits` 的排除條件：

```ts
const hits = known.filter((o) => o.name.includes(query) && o.name !== query);
```

`o.name !== query` 是在排掉「已經當 `exact` 印過的那一筆」—— 這在票券 38 之前一直成立，
因為那時 `exact` 必定是 `name === query` 的那一筆。這張票讓 `exact` 多認了手上那一筆，
而**手上那一筆的顯示名不必等於它在目錄裡的名字**（別名，或實體改名後舊引用留著舊字），
於是同一筆實體從 `exact` 與 `hits` 各進榜一次。

改成排掉 `exact` **那一筆物件本身**（`o !== exact`），不是「名字剛好等於 query 的」——
排除條件與它想排除的東西這下對得上了。加了回歸測試。

（一鍵改名實體的需求另開**票券 39**。）
