# 場次編號與穩定錨點的落實

Type: grilling
Status: resolved
Blocked by: 08

## Question

業界所有拍攝表單都用**會變動的場次號**當 key 互相參照，且沒有任何永久識別碼機制。那麼「場次是穩定錨點」這條約束，實際上要怎麼落實與呈現？

這團霧原本卡在「業界有沒有 12A 這種插入編號慣例」。格式範本這條路已證實走不通（三份一手範本完全未觸及插入場次的情境），但「場次表與拍攝表單的真實欄位」揭露了更關鍵的事實：**業界清一色以場次號互相參照，重排後下游對不上是真實存在且未解的問題。**

作者是影視產業出身、有編劇經驗、身邊有編劇朋友 — 這張票的多數問題可以直接由領域知識回答，不需外求。

要回答：

1. **業界實務上，劇本重排或中途插入場次後怎麼辦？**
   有沒有 12A、12B 這類插入編號慣例？還是整份重新編號、然後手動同步所有下游表單？如果作者不確定，這是問編劇朋友或場記／製片統籌的好題目。

2. **對內永久 id、對外場次號的分離，要怎麼呈現給使用者？**
   使用者看得到 id 嗎？還是完全隱藏、只看得到場次號？分享連結與場次表上顯示哪一個？

3. **重排後，已經印出去的下游文件怎麼辦？**
   產品要不要主動處理 — 鎖定編號、標記版本、還是在重排時警告？或者這根本不是 v1 該碰的事？

4. **這是不是產品的隱藏賣點？**
   如果重排同步是業界真實痛點而現有工具都沒解，那它的優先序可能被低估了。但也要誠實評估：在 v1 只有編劇單人使用、沒有下游文件的情況下，這個賣點暫時無法兌現 — 它是為第二三層鋪路，還是應該現在就講出來？

5. **「場景」欄與「景」欄的語意分別是什麼？**
   真實順場表 14 欄中兩者並存（場景、場次、光、景、…）。研究未能確認，但作者應該一看就知道。這會影響 `CONTEXT.md` 中「地點」的定義是否精確，以及場次 metadata 的欄位設計。同時確認「劇情概要」是否算第一層投影、群演如何歸屬。

這張票的答案直接餵給「劇本儲存模型」— id 的生成、儲存與呈現方式是那張票的核心之一。

若第 1、3 點的結論夠份量（難以回頭、後人會問為什麼、真實權衡），值得寫成 ADR。

## Comments

### 來自 [區塊編輯器選型與 /scene 輸入體驗](./03-editor-prototype.md)（2026-08-20）

**插入戲已移出 v1，但它留下的問題正好是這張票的核心。**

原型實作了字母尾綴（`S5A`），然後證明它在本專案裡是**假保護**：把 `S5A` 搬到 `S2` 後面，它就變成 `S2A`。從「場次號是推導值」的角度完全正確，但編劇當初寫 `S5A` 就是為了不影響已發出去的下游表單 —— 一搬就失效。

更根本的是：字母尾綴是業界用來繞過「重新編號會讓下游表單失效」的 workaround，而那個洞正是架構約束 1 要填的。把 workaround 跟解法一起做進 v1，等於承認解法不管用。

**真正的觸發點不是「我要插一場」，是「這一版已經交出去了」。** 這是版本鎖定，不是場次屬性 —— Final Draft 的答案正是「鎖定頁面，之後的新場次自動給字母」。票券 08 的結論說我們不需要鎖定機制，前提是沒有人拿著舊號碼；一旦 PDF 寄出、唯讀連結發出，那個前提就不成立。

所以本票券要回答的第 2 題（對內永久 id、對外場次號的分離要怎麼呈現給使用者）應該連帶回答：

- **「已交付版本」是不是 v1 的概念？** 它同時連著 PDF 匯出與唯讀分享連結 —— 兩者都是交付。
- 若是，**字母尾綴應該是它的衍生結果**，由系統算出來，不是使用者手動打的旗標。
- 若否，v1 的編號就永遠是 1..N，而「劇本已經交出去、之後改稿」這個真實情境要有別的答案。

作者的領域判斷（2026-08-20）：插入戲在**編劇階段**基本用不到，他自己用到的時機是**拍攝時臨時加戲改戲**。實測拿掉之後「沒有什麼感覺」。

### 另一項：場次號不進資料庫

場次號是純渲染值，經 decoration 供給編輯器，不存節點屬性也不存 DB。細節見 03 的 Answer。這條同時約束了本票券的「呈現」設計 —— 使用者看到的場次號永遠是即時算出來的。


## Answer

ADR：[ADR-0002 場次號是推導的顯示值，永久 id 對使用者不可見](../../docs/adr/0002-scene-id-and-derived-scene-numbers.md)

### 1. 業界實務（第 1 點，收束）

業界**有解**，解法是**顏色稿制度**：正式開拍前的白稿（Production Draft）**鎖定場次號與頁碼**，之後每輪改稿依序換色（藍、粉、黃、綠、金黃……），且只發改動的那幾頁。顏色本身就是版本標示。

這回頭解釋了票券 08 查到的字母尾綴：**`12A` 是鎖定制度的產物**，白稿一鎖，新插進來的戲只能靠尾綴。所以我們當初否決手打尾綴的判斷是對的，但理由要更正 —— 問題不在尾綴本身，而在**我們缺了業界有的那一層鎖定**，尾綴在這裡是沒有根的旗標。

**我們不採用顏色稿。** 它解的是紙本流通問題：因為沒有共同的資料來源，只好靠凍結與換色讓人肉辨識版本。我們有共同的資料來源，套用鎖定等於自己製造出它要解決的那個問題。

已新增 `CONTEXT.md` 的 `顏色稿` 詞條。

### 2. 對內 id／對外場次號的分離怎麼呈現（第 2 點）

- **使用者完全看不到 id**（B1，先前已定）。id 只存在於網址、API 與下游關聯。
- **場次號是每次渲染即時推導的顯示值**，不進編輯器文件、不進資料庫（票券 03 已定，走 decoration）。
- **場次 id 是全域唯一的字串**，不是「劇本內遞增整數」這種複合 key。承諾對象是下游：第二三層的表單、匯出資料、外部整合想要的是「抓一個字串就走」。複合 key 每多一層下游就多一次出錯機會，而那正是我們宣稱要修的病 —— 業界表單對不上，根因就是引用需要上下文才能解析。
- **形式：nanoid + 型別前綴**（`sc_V1StGXR8_Z5jdHi6B-myT`）。UUID v7 的時間排序索引優勢在「一部劇本一兩百場」的量級用不到；id 會出現在網址與未來的匯出檔，短 15 個字元是每天兌現的好處。前綴補回了全域唯一字串「肉眼不可讀」的代價 —— 掃過資料庫一眼就知道這是場次而非人物或地點。

⚠️ **注意**：本票券只裁決**場次 id**。劇本／專案 id、以及唯讀分享連結的 token 是不同的東西，**token 尤其不該等於劇本 id**（撤銷連結就是換 token，若兩者相同，撤銷等於換掉劇本的身分）。歸票券 12。

### 3. 已交付的下游文件怎麼辦（第 3 點）

**「已交付版本」不是 v1 的功能，但它的資料是 v1 就要開始存的。**

- **不做版本鎖定**（Final Draft 那套）。它會把版本 diff、鎖定狀態 UI、「哪些場次是鎖定後新增的」一整串拖進 v1，而價值要到有下游文件時才兌現。
- **做交付快照，無 UI。** 每次交付存一份 `場次 id → 那次印出的號碼` 對照。理由是它**寫入時幾乎免費、事後補不回來** —— 交付當下的編號一旦沒存，後來永遠算不出來。
- **存推導的結果，不是推導的輸入。** 決定性論證：編號演算法還會改（子場次形式票券 09 才要定）。存輸入（當時的場次樹）等於讓演算法一改就回頭改寫歷史 —— 紙上印 `12A`，系統重算成 `12-1`。快照的全部價值就在於它不說謊。代價是失去「用新演算法回頭重算舊版」的能力，而那個能力我們根本不想要。
- **全部保留，不做清理。** 一次匯出是幾十到幾百個短字串；設保留上限就得決定刪哪一份，那沒有正確答案，卻會在某人真的需要舊的那份時咬人。
- **觸發定成原則，不定成清單**：「凡是產生離線副本或凍結視圖的交付動作，都存一份快照」。因為分享連結是活是凍尚未決定（票券 12），定清單會讓那張票日後回頭改本票券的結論。

**PDF 頁尾印匯出時間戳**（每頁、靠左、小字，頁碼維持置中），做成匯出選項、**預設開啟、投稿前可關掉**。查證支持這個位置：MOC／GHSA 兩份範本未規定頁碼與頁尾，北藝大範本明文「頁尾置中放頁碼，可加浮水印」；更關鍵的是 **GHSA 徵件須知強制全篇壓浮水印且不得署名** —— 紙面上有非劇本內容不但被接受還是強制的，真正的紅線是不得洩漏作者身分，時間戳踩不到。開關保留給作者的產業直覺（評審印象分）。

時間戳是交付快照的欄位，兩者是同一件事的兩面 —— 紙上那行字就是這筆快照的把手。

### 4. 這是不是隱藏賣點（第 4 點，先前已解）

痛點是真的（劇本改版後其他表單「乾坤大挪移」），投影模型正面解決它。但 **v1 單人使用、無下游文件，此賣點無法兌現**，不該對外宣稱。

### 5. 順場表欄位語意（第 5 點，先前已解）

「場景」欄＝地點、「景」欄＝內外、「光」欄＝日／夜／晨／昏，均已寫入 `CONTEXT.md`。「劇情概要」已確認**不是**可靠的第一層投影。群演另立概念（不是人物）。

### 本票券推翻的自己的推論

上一輪我主張「唯讀連結永遠是即時投影，所以沒有不同步問題」。**錯的。** 要拆成兩件事：

- **編號說謊**（製片手上寫 S12，系統裡 S12 已是別場戲）—— 投影模型確實消滅了這個。
- **內容漂移**（兩名組員在不同時間打開同一條連結，看到不同的戲）—— 投影模型**不但沒消滅，還讓它更隱形**。PDF 至少有實體差異可察覺，活連結什麼線索都沒有。

作者指出的正是後者，而且他的情境很具體：製作端的需求會回頭要求編劇改稿，**而需求有時候又會反悔**。查證顯示沒有任何主流工具「只做活連結」—— Google 文件的發布到網路有「變更時自動重新發布」開關，Figma 可對版本歷史中某一版複製連結（雖然社群長年抱怨難用）。**活連結與凍結連結是兩種不同的分享意圖，都存在。**

這個問題已畢業成[票券 12](./12-share-link-live-or-frozen.md)，不在本票券內裁決。
