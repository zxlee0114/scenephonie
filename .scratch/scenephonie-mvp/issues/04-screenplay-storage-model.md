# 劇本儲存模型

Type: grilling
Status: resolved
Blocked by: 02, 03, 07, 09, 10, 11, 15, 16, 17

## Question

劇本在 PostgreSQL 裡怎麼存？場次是關聯式資料表的一列，還是編輯器 JSON 裡的一個節點？

候選方案：

- **純 JSON** — 整份劇本存成編輯器的 document JSON。寫入簡單，但場次表要查詢時得把整份 JSON 撈出來在應用層解析。
- **純關聯式** — 場次、區塊各自成表。查詢自然，但要跟編輯器的 document model 雙向同步，複雜且容易不一致。
- **混合** — 場次 metadata 進關聯式表（可查詢），場次內容（Action／Dialogue）存 JSON。

要回答：

1. 選哪個？權衡是什麼？
2. **場次的永久 id 由誰產生**、存在哪、如何在編輯器與資料庫之間保持一致？（約束 1）
3. 場次表查詢要多快、多即時？是即時投影，還是可以接受衍生後儲存？
4. 人物與場次的關聯怎麼存？（登場人物是實體，不是字串）
5. 這個模型**擋不擋得住之後加協作**？（約束 3）— 即時協作通常要求 document 是單一 CRDT 結構，混合方案可能與之衝突，這點必須正面回答而不是繞過。
6. 專案與劇本兩個實體的邊界在哪？

依賴 02（要知道場次表需要查詢什麼欄位）與 03（要知道編輯器能提供什麼樣的 document 結構）。

這張票很可能值得一份 ADR — 難以回頭、後人會問「為什麼這樣選」、且是真實權衡的結果。三個條件都成立時就寫。


## Comments

### 來自 [區塊編輯器選型與 /scene 輸入體驗](./03-editor-prototype.md)（2026-08-20）

**三條已經定下來的約束，儲存模型不得違反：**

1. **`sceneNo` 不進資料庫。** 場次號是純渲染值 —— 系統裡沒有任何東西用它當 key（約束 1：下游一律掛 `sceneId`）。存衍生快取會讓 PDF 匯出必須選擇要不要相信它：相信則可能印出錯的場次號（而水準線是「拿去參賽會被接受」），不信則該欄位只剩說謊的能力。
   「場次表用 SQL 撈比較快」這條論據比看起來的弱：排序要用的**序列次序**無論如何都得存，有了次序就能算出場次號。

2. **文件是 `scene+`，場次是 `isolating` 的 block node，content 為 `sceneBlock+`。** 場次之外不存在可編輯內容，所以不會有「不知道該歸給哪一場」的孤兒資料。

3. **`sceneId` 由編輯器端產生並存在節點上，但複製貼上會產生重複 id** —— attribute 跟著序列化一起被複製。必須有 `appendTransaction` 主動去重。這決定了「永久 id 由誰產生」那一題的答案形狀：不能只靠資料庫發號，因為破損發生在編輯器內、寫入之前。

**另一類值得預期的坑**：ProseMirror 的同一個位置有兩種表示法（結構位置 vs 正規化後的文字位置），`TextSelection.between()` 會在不注意時從前者變成後者。若要持久化游標或選取位置，得先決定存哪一種。

#### 已定案：Q1 — doc 是唯一權威

三選一（純 JSON／純關聯式／混合）的問法要改成 **「誰是權威」**。

**結論：混合，但關聯式那一半永遠是衍生的（derived read model），不是權威。**

- **doc JSON 是結構與場次 metadata 的唯一權威。**
- 關聯式表只裝**本來就不在 doc 裡的東西**：專案、劇本、人物、地點、交付快照。

判準是客觀的：場次／子場次／區塊／群組／場次 metadata 是編輯器裡打出來的，樹就是它們的形狀；人物與地點**屬於專案**、跨劇本、append-only（ADR-0005），從來不住在某一棵樹裡。

**論據**：讓表也權威 → 兩個寫入者 → 雙向同步 → 一整個靜默 bug 家族（場次表印的地點與劇本不一致，而場次表是製片拿去排通告的）。且它**直接撞上約束 3**：CRDT 只保護它管得到的單一結構，metadata 若在表裡，協作時是「後到的贏、前者無聲消失」，日後要加同步層得先把 metadata 搬回 doc，那時已有真實使用者資料。

**承認的代價**：(1) 場次表要撈整份 doc 出來 parse，不能下 SQL（見 Q2）。(2)「編輯場次表直接改劇本」永遠不能走捷徑，必須回頭改 doc —— 這是對的限制，因為場次表是零新增資訊的投影，本來就不該有自己的寫入路徑。(3) doc 是大 blob，資料庫層級擋不住裡面的爛資料（見 Q6）。

#### 已定案：Q1b — domain command 層，v1 第一天就建

作者提問：從場次表更新資訊，能不能走編輯器的 command 而非直接改資料庫？→ **能，而且只能這樣。** 這是 Q1 的必然結論：Q1 說的「權威」翻譯成工程語言就是**寫入只有一個入口**。

**「domain command」有兩種讀法，取 A、否決 B：**

- **A（採用）command 是程式碼**：isomorphic TS 模組，純函式，吃 doc 吐新 doc。傳輸與持久化的東西完全不變。
- **B（否決）command 是資料**：可序列化的訊息、可寫 log、可重播。否決理由同 Q1 —— 會製造第二個權威（command log 與 doc 誰是真相？），不知不覺走進 event sourcing。且 B 想要的東西 ProseMirror 已經給了：**`Step`**（可序列化、可合併、可 rebase，協作就是傳 Step）。

**三層各司其職**：`domain command`（意圖）→ `ProseMirror Step`（機械變更／日後的傳輸單位）→ `doc`（唯一權威、唯一被持久化）。

**真正的獲利不是「多入口」（v1 只有一個寫入入口），而是給不變式一個家 —— 且是在瀏覽器外可單元測試的家。** 目前無家可歸的四條：主場次的內容必須以自己的內容開始（ADR-0006 ①）、子場次 metadata 不得與主場次全同（ADR-0006 ②）、群組成員之間 metadata 不得全同（ADR-0004）、群組不能巢狀且一場次不得屬於兩個群組（ADR-0004）。它們現在只能散進票券 03 那個「六個 bug 的家族」裡，也就是最難測的那一層。

**准入判準**（免得長成「每個 Tiptap command 包一層」的空殼）：

> 一個 domain command 要能進來，必須至少滿足其一：**它強制執行了一條不變式**，或**它以 `sceneId`／實體 id 定址（而非以位置定址）**。兩者皆非的留在編輯器裡當一般 Tiptap command。

**edge boundary 規則**（作者要求從「undo 不直接依賴 history」放寬）：

> **UI 與 application 層不得直接依賴編輯器的實作細節** —— 包含 transaction、mutation、`history`、以及以**位置**定址的任何東西。**凡具備 domain 或 application 意義的操作，一律透過 command abstraction 執行。**

邊界說明（否則會被讀成「不准用 ProseMirror」）：**編輯器套件內部**照常直接用 ProseMirror API（node view 怎麼畫簡表、`Tab` 怎麼排環、拖曳落點判定、注音組字期間選單不動作）。規則管的是**跨出編輯器邊界**的線：頁面、伺服器、日後的 API、日後可編輯的場次表。編輯器對外只曝露兩樣東西 —— **commands（寫）** 與 **projection（讀）**。介面窄、實作深。

**意圖 vs 手勢的分界**（這條線一鬆，command 層就會被 UI 細節污染而測不動）：

| 手勢（留在編輯器） | 意圖（就是 command） |
|---|---|
| `Tab` 怎麼排環 | `setBlockType(blockId, type)` |
| `/` 選單怎麼過濾、IME 組字期間不動作 | `insertSubscene(parentId, kind, meta)` |
| `⌘+1/2/3` 直接定址、`⌘+4` 是無效鍵 | `assignFragmentToMember(...)` |
| 拖曳時哪些位置不畫落點線 | `moveScene(sceneId, target)`（**它自己也要拒絕非法目標**） |
| 自動補全選單三列怎麼排 | `createLocation(name)` / `renameLocation(id, name)` |

最後一列的「它自己也要拒絕非法目標」是**縱深不是重複**：落點線是 UI 的預防，command 的拒絕是模型的保證；UI 只擋得住滑鼠，擋不住伺服器端呼叫或日後的 API。

**伺服器端可執行**：ProseMirror 是純 TS，`EditorState`／schema／transaction／command 在 Node 裡都跑得動；瀏覽器專屬的只有 `EditorView` 與 node view（渲染層）。而 Q4 選 PM JSON 已經逼我們維護一份伺服器端可載入的 schema（PDF 匯出要推場次號、推草稿清單），所以「伺服器也能寫」幾乎免費。

**三個附帶約束**：(1) schema 必須是 isomorphic 的獨立模組，node spec 與 node view 分家，schema 那半不准 import 瀏覽器的東西。(2) command 一律用 `sceneId` 定址，內部先做 `sceneId → pos` 解析 —— 與 ADR-0006 保護規則 2 是同一條規則的另一個角度。(3) 要有樂觀並行控制（見 Q4 的 `doc_seq`）。

#### 已定案：Q2 — v1 不建投影表，場次表即時推導

爭點不是權威（Q1 已定），而是**推導在讀時發生還是寫時發生**。

**v1 消費者全是低頻、且全在單一劇本範圍內**：編劇切到場次表檢視、唯讀分享連結、PDF 匯出。**沒有任何 v1 消費者需要 SQL** —— 要跨場次聚合查詢的是「按實體聚合的清單視圖」，那在地圖的 Not yet specified、v1 不做；影集多集在範圍外。

**成本**：130 場的 doc 幾百 KB，撈 jsonb + `Node.fromJSON` + 走一遍樹是**十毫秒等級**；而 PDF 匯出與 share link 本來就要撈整份 doc，場次表只是對它多走一遍。投影表買到的很少，要付的是**推導漂移**（何時重算、失敗怎麼辦、怎麼發現與 doc 不一致）。

**結論：不建，讀取當下推導。** 但推導邏輯要放進 Q1b 那個 isomorphic 模組，成為純函式 `projectSceneTable(doc) → SceneTableRow[]`，理由三條：(1) 這個簽名裡沒有 doc 以外的輸入，**型別本身在強制「零新增資訊」那條原則** —— 有人想加一欄製作端另填的東西時會發現簽名裝不下，比文件裡的一句話有力。(2) PDF、場次表、匯出前草稿清單共用同一次走訪（場次號、草稿判定、群組成員展開），不會長出兩套會分歧的實作。(3) 投影表日後加時是免費的：它就是這個函式輸出的快取，key 是 `doc_seq`，要重建就 `DROP` 再跑一次。

**點名的依賴（不阻塞）**：票券 12 若選「凍結分享連結」，那份凍結的場次表是**存起來的推導結果** —— 但它語意上是**快照**不是快取（同交付快照：刻意不可變、不隨 doc 更新）。兩者方向相反：快取要跟上 doc，快照要抵抗 doc。**Q2 對票券 12 的兩個答案都成立。**

#### 已定案：Q3 — 一個劇本一列，`jsonb`

**否決「一場一列」，理由是它裝不下已定案的東西**：(1) 子場次是巢狀節點（ADR-0003），拆成列後父子與先後要靠 `parent_id`／`order` 欄重建 —— 那正是 ADR-0003 否決「平坦 + `depth`」的同一條理由，從編輯器搬到資料庫理由不會失效。(2) **片段在 v1 沒有 id**（ADR-0006 保護規則 3 明文禁止），沒有 id 的東西存不進列 —— 一場一列會逼我們現在就違反一條寫進 ADR 的保護規則。(3) 群組是容器、成員沒有自己的內容（ADR-0004），要嘛拆 join 表要嘛留空欄，兩種都是在資料庫裡重建編輯器已經表達好的結構。

**真正的理由是原子性**：ProseMirror 的一個 transaction 是對整棵樹的原子變更，而我們有一堆天生跨場次的變更（帶子場次的主場次被拖走、刪父場次一併刪子場次、⌘Z 一步還原整棵子樹且 `sceneId` 一起回來、`appendTransaction` 改寫撞號的 `sceneId`）。一場一列時這些變成 N 次列寫入，**寫到一半失敗 ＝ 一份違反不變式的劇本**。

**誠實的代價：寫入放大。** 每次自動存檔重寫整份 doc（幾百 KB，走 TOAST，整列重寫 + WAL）。v1 不是問題（單人、單劇本、寫作是低併發活動），處理方式是**調 debounce 而不是改資料模型**：用「停頓」而非「節流」（打字停 2～3 秒才存，加一個最多每 15 秒強制存一次的上限）。真痛了再說，那時的解法是**傳 Step 而不是傳整份 doc**（Q1b 三層的中間層本來就為此預留），仍然不動儲存粒度。

**欄位型別 `jsonb` 而非 `text`**：投的是除錯能力（出事時能在 `psql` 裡 `doc -> 'content' -> 0 -> 'attrs'` 看一眼），對獨立開發者是實打實的價值。真的被寫入放大咬到時，`jsonb` → `text` 是一行 migration。

#### 已定案：Q4 — 存 ProseMirror JSON，不存 Yjs（約束 3 的正面回答）

**「從第一天就存 Yjs」不是加同步層，是把權威資料的形狀換掉**（Y.Doc 存進 `bytea`，⌘Z 換成 `Y.UndoManager`，日後接 websocket provider 即可，資料不用遷移）。

**四個代價**：

1. **伺服器每一條路徑都要跑 Yjs runtime** —— 需要伺服器讀 doc 的地方比想像多：PDF 匯出、場次表（Q2 的即時推導）、唯讀分享連結、**伺服器端執行 domain command（Q1b）**。存 JSON 時第一步是 `Node.fromJSON`（同步、無副作用）；存 Yjs 時是一個有狀態的 runtime，出現在每一條路徑上。
2. **儲存變不透明，Q3 剛買到的除錯能力當場退掉。** 劇本工具最可怕的故障是「某位編劇的劇本壞了」，那種故障需要能用眼睛看。
3. **它疊上第二層要協商的預設行為。** 票券 03 的結論是每個自訂互動都要跟一層預設行為協商（六個 bug 同一家族），`y-prosemirror` 會攔截 transaction、把 attr 對映到 Y 型別，是**第二層**同性質的東西。而我們有幾個載重的自訂行為正好落在那層：`appendTransaction` 去重（票券 03）、⌘Z 一步還原子樹且 `sceneId` 跟著回來（票券 09）、⌘Z 留下的孤兒實體被刻意容忍（ADR-0005，「存在＝被引用」靠它成立）。`Y.UndoManager` 的語意與 PM `history` 不同（以 origin 分群）。**在 v1 出貨前換掉 undo 引擎，是拿載重行為換一個 v1 用不到的功能。**
4. **Yjs 不是「協作完成」按鈕。** CRDT 保證收斂，但不知道我們的不變式，合併出來的樹可能違反「群組不能巢狀」「主場次的內容必須從自己的內容開始」。難的那一半仍然沒解決 —— 現在買 Yjs，買到的比看起來少。

**Yjs 那邊最強的論據是「日後遷移很貴」**，但判斷是**不貴**（純結構轉換，`y-prosemirror` 本身提供該方向的工具函式，遷移是一次性離線腳本）。**⚠️ 這條事實是承重的且未實測 → 已開票券 19。**

**為了不堵死那條岔路，v1 要守四條**（沿用 ADR-0006 留升級路徑的手法）：

1. schema 是 isomorphic 的獨立模組，不含任何瀏覽器相依（node spec 與 node view 分家）—— 日後 `y-prosemirror` 吃同一份 schema。
2. 所有節點一律靠 attr 上的永久 id 定址，不靠位置、不靠場次號。
3. **「整份 doc 覆蓋」這個假設不准散進程式各處** —— 存檔集中在一個 persistence 模組後面，呼叫端只知道「存」與「載入」。換 Yjs 時只換那一個模組。
4. **undo 只透過 command 層對外曝露**，不准任何 UI 直接依賴 PM `history` 的內部細節（已被上面那條更廣的 boundary 規則吸收）。

**兩個 version 現在就分開**（作者提出）：

| 欄位 | 是什麼 | 什麼時候變 | 誰讀它 |
|---|---|---|---|
| `doc_schema_version`（integer） | 這份 doc 用哪一版 node schema 寫的 | **部署時**（我們改了 schema） | 載入 doc 的程式 —— 落後就先跑遷移鏈 |
| `doc_seq`（bigint） | 並行控制 token | **每次成功改變 canonical document state** | 寫入時的 `WHERE` 條件 |

一個隨程式碼走、一個隨資料走，變動頻率差好幾個數量級。

**命名要避開地雷**：`CONTEXT.md` 把「版本／版次／revision／鎖定」列為交付快照的 Avoid 詞（因為**版本鎖定**是已否決的功能），所以不叫 `lock_version` 或 `revision`。規格書要明寫作者的定義：

> `doc_seq` 是每一次**成功改變 canonical document state** 的 optimistic concurrency token。它不是自動存檔次數、不是版次、不是任何產品概念。不對使用者曝露，與交付快照無關。

**三個附帶決定**：(1) `doc_schema_version` 存成**欄位**不存在 doc JSON 裡（查得到「還有幾份停在舊版」、載入前就知道要不要遷移、避免兩個權威）。(2) **遷移採 lazy，且永遠在記憶體中發生；寫回只發生在本來就會寫的路徑**（使用者存檔、伺服器端 command），**讀取路徑一律不寫回** —— 否則 PDF 匯出／場次表／唯讀分享連結都會觸發資料庫寫入（外人打開分享連結時寫我們的資料庫），且會製造兩個 client 同時載入舊 schema 互相覆蓋的 race。作者要求的原子性規則原封不動適用於真正會寫的路徑：**schema migration、doc 更新、`doc_seq` 遞增是同一個原子操作，並沿用 `doc_seq` 的並行檢查**。代價是「只被讀從不被編輯」的 doc 永遠停在舊版 —— 但遷移鏈無論如何都得留著，所以不算代價。(3) `documents` 表（分場大綱、角色設定表）若也是 PM doc，同樣要有這兩欄；**交付快照沒有這兩欄** —— 它刻意不可變、不被載入編輯、不遷移，那正是它與其他所有東西的分野。

**作者收斂時列出的邊界**（照抄）：

```
canonical document = ProseMirror JSON
storage            = jsonb
schema version     = doc_schema_version
concurrency        = doc_seq
write boundary     = commands
read boundary      = projection
migration          = schema migration
future collaboration = Yjs（待票券 19 驗證）
```

#### 已定案：Q5 — `sceneId` 由編輯器產生，資料庫沒有 `scenes` 表

**(a) 不要 `scenes` 登記簿。資料庫完全不知道場次的存在。** 理由同 ADR-0005：**存在＝被引用**，場次「存在」就是它在那棵樹上。登記簿等於第二份權威，唯一好處（外鍵完整性）在 v1 沒有消費者：第二三層下游文件在範圍外，交付快照存的是**推導結果**（一份死資料，不需要對方還活著）。

**這同時回答了票券第 2 題後半（「如何在編輯器與資料庫之間保持一致」）：不必保持一致，因為資料庫沒有要跟著同步的副本。** 唯一的一致性要求是**同一份 doc 內 id 不得重複**，完全在編輯器內解決。

**(b) 去重規則（票券 03 只講了一半）**：撞號時**誰改名**是有後果的 —— 交付快照與下游文件指著原 id。必須區分兩個動作：**剪下→貼上（搬移）id 必須保住**（約束 1）；**複製→貼上 id 必須換新**。

**碰撞本身就是判別器，不必猜使用者意圖**：剪下時原節點離開文件 → 貼上不碰撞 → 去重不觸發 → id 天然保住；複製時原節點還在 → 貼上必碰撞 → 去重觸發。

> 規則：`appendTransaction` 只在偵測到重複時動作，改的一律是**本次 transaction 新插入的那個節點**（step 資訊拿得到）。無法判定時的後備規則是**文件順序在前者保留**。

**(c) 跨劇本貼上 —— 要做，且論述重心經作者更正**：

> **跨劇本貼上，在語意上是建立一個新的場次身分。**（一份劇本的場次，身分只在那份劇本裡有意義 —— 交付快照與下游文件都是「這一部片」的事。貼進另一部片，得到的不是同一場戲的另一個位置，而是另一部片裡的一場新戲。）**全域唯一是實作結果，不是要去維護的規則。**

**且兩個機制分屬兩個層次，各自只做一件事**（作者更正）：

| 層次 | 機制 | 職責 | 它知道什麼 |
|---|---|---|---|
| **剪貼簿邊界** | `transformCopied` / `transformPasted` | **語意判斷**：這次貼上是延續既有身分，還是建立新身分 | 來源劇本、目的劇本 |
| **文件不變式** | `appendTransaction` | **結構修復**：同一份 doc 內不得有重複 id | 只有這棵樹，不需要 provenance |

`appendTransaction` 因此**永遠不必知道來源**，它是**最後一道防線**，對任何來源都成立（剪貼簿、程式化插入、日後的匯入、我們自己的 bug）。作法是在剪貼簿內容上蓋一個來源劇本的印記，**來源劇本 ≠ 目前劇本時一律重新產生 id**。

**(d) 去重的 transaction 標 `addToHistory: false`。** 否則：複製貼上 → 去重改 id → ⌘Z → **退回到重複 id 的狀態**。它不是使用者的動作，是模型的修復。（與票券 09「⌘Z 一步完整還原整棵子樹、`sceneId` 一起回來」不衝突，那條講的是刪除的還原。）

**(e) 適用範圍**：**場次**與**子場次**完全相同處理（票券 09 已註明 `StableIds` 要一併認 `subscene`；`種類` 是 attr，跟著複製沒問題）。**群演**是場次限定實體、id 只在該場次內有意義、不進人物表 —— 跟著場次被複製過去是**正確的**，不需去重。**場次群組**：v1 片段沒有 id（ADR-0006 保護規則 3）；群組本身需不需要 id 取決於它在 schema 裡是不是節點，那是票券 06 要展開的 schema 形狀 —— **本票券只定一條：如果群組有 id，它適用同一套去重規則。**

**掉出一條乾淨的不變式**（✅ 2026-08-30 作者採用抽象一層的措辭，已寫進 `CONTEXT.md` 的**場次**詞條；理由與實作邊界寫進 [ADR-0002](../../../docs/adr/0002-scene-id-and-derived-scene-numbers.md) 的「身分何時被建立、何時被保留」一節）：

> **場次身分只在下列時刻被鑄造**：(1) 建立場次（`/next`、⌘+Enter、場次腳部按鈕）(2) 建立子場次（`/insert`、`/continue-to`）(3) 建立群組成員（`/對剪到…` 第二步選「建立新的一場」）(4) 複製出一份副本（碰撞修復）(5) 跨劇本貼上。
> **其餘一切都保住身分**：拖曳、剪下貼上、升級降級、⌘Z。

第 1～3 條對應 ADR-0003 的既有規則「**會產生永久錨點的動作，入口只有一個，而且那個入口的名字要說出它會建立東西**」；第 4、5 條是同一條規則在剪貼簿上的延伸（**貼上會不會鑄造新身分，由來源決定，不由使用者猜**）。「其餘一切都保住身分」那半是**約束 1 的可執行版本**。

#### 已定案：Q6 — 不補外鍵；寫入嚴格拒絕，讀取無條件容忍

**洞的真實大小**：ADR-0005 已堵掉絕大部分入口 —— 「刪除實體」這個動作不存在（編劇只能拿掉引用，最後一個引用消失時實體變孤兒、永不清理），實體表是 append-only。所以懸空引用只剩兩個現實來源：正向 race（表寫成功、doc 沒存到 → 多一筆孤兒，ADR-0005 已裁定無害）；反向（doc 有 id、表沒有）**只可能來自資料庫還原到較早的時間點**，或我們自己的 bug。

**(a) 不補（A）。** 資料庫沒有能掛外鍵的地方 —— 要掛得先有 `scenes` 登記簿，Q5 已否決。反向發生時**顯示名是權威的渲染來源**（票券 10 對行內引用的裁決），PDF 照印、場次表照印，只是少一條可聚合的連結。這條容錯行為**明寫進規格書**。

否決「載入時用顯示名自癒補一筆」：(1) 它是**讀取路徑的寫入**，與 Q4「lazy 遷移永遠在記憶體中發生、讀取路徑一律不寫回」直接抵觸（外人打開唯讀分享連結時寫我們的資料庫）。(2) 它補出來的名字**是錯的** —— ADR-0005 明說實體的名字是真欄位不是推導值，漸進揭露下前 8 場的顯示名是「未知大樓房間」，自癒會把假名鑄成正式名字，而製片要知道去哪裡拍。**用一筆說謊的資料換掉一個誠實的缺口，是虧的。**

**(b) 加一條 command 層不變式（A+）。** 建立引用的 domain command（設定場次地點、加登場人物、設定對白人物欄）在寫進 doc 前，先確認該實體 id 存在於 `characters`／`locations` 表。它命中 Q1b 的准入判準（強制執行不變式 ✓、以實體 id 定址 ✓），且比外鍵**適用範圍更廣** —— 外鍵只在資料庫裡成立，command 層的檢查在伺服器端呼叫、日後的 API、日後可編輯的場次表上都成立。

**作者定下的三條措辭（照抄）：**

> 1. A+ 確保的是 **command-level referential integrity，不是真的 FK**，所以**系統不能保證懸空引用不會發生**；但**所有 domain command 必須拒絕**建立對不存在實體的引用。
> 2. **doc 需要允許引用不存在的 entity。** 懸空引用發生時不影響渲染，**顯示名稱是渲染權威（fallback 來源）**。
> 3. **建立 entity 時，先建立 entity 再寫入 doc。**

**這個不對稱是刻意的：寫入路徑嚴格拒絕，讀取路徑無條件容忍。** 兩半要在規格書裡並排寫出來，否則後人會把其中一半當成 bug 去「修」—— 有人會想在 projection 裡擋掉懸空引用（那會讓 PDF 少印一個地點，正是票券 11 說的最糟失敗模式），也有人會想讓 command 放行以求彈性。

第 3 條同時是 A+ 能成立的**前提**而不只是建議順序：檢查對象是實體表，反過來的話每一次建立新人物的 command 都會被自己的不變式擋下。

**(c) 「未來人物與地點重要性上升」不會改變這個答案**（作者提出的顧慮）。重要性上升時真正會缺的是**按實體聚合的查詢**（「這個地點有幾種叫法」「這個人物出現在哪幾場」、日後的第三層文件），而 Q2 已備好路：投影表是 projection 函式輸出的快取、key 是 `doc_seq`、要重建就 `DROP` 再跑一次 —— 而且**那張表可以有真外鍵**，因為它是衍生的、可重建的，不製造第二個權威。外鍵在那個未來一樣做不到（仍然要 `scenes` 表）。**A+ 現在打的是那條升級路徑的地基**：加聚合投影表的前提是 doc 裡的引用本來就乾淨；若 v1 期間累積了髒引用，那時得寫清理腳本，而清理依據只剩顯示名 —— 就是 (a) 反對自癒的同一個理由。

**(d) 引用缺失只做診斷，不落地。** `projectSceneTable(doc)` 額外回傳一份 `missingRefs`（哪個節點引用了哪個查不到的 id），伺服器端解析 doc 時輸出一筆結構化日誌。**不進資料庫、不對編劇曝露。**

> **`missingRefs` 是 projection 的診斷輸出（diagnostic output），不是業務輸出**（作者定義）。它不得參與渲染、不得被持久化、消費者的業務邏輯不得讀它。

理由三條：(1) 懸空引用是**事件不是狀態**，而狀態已經在 doc 裡 —— 存進資料庫會是第三份衍生資料且**會過期**（實體之後被建回來，那筆就成假警報），是 Q2 拒絕投影表時同一條「推導漂移」的論據。(2) 放進 projection 的回傳，與 Q2 讓簽名去強制「零新增資訊」是同一手；PDF、場次表、分享連結共用同一次走訪，不會長出兩套。(3) **不對編劇曝露**，因為對他沒有可行動的資訊：顯示名照印，沒有任何東西被少印。這正好與票券 11 的草稿提醒相反 —— 那裡會真的少印，所以即使全部抑制仍要說「本次略過 N 場」；這裡什麼都沒少，跳警告只是假警報。真的出事時（資料庫還原）看伺服器日誌，讀者是我們不是編劇。

「什麼都不做」的代價是資料庫還原後我們**永遠不會知道**發生過 —— 剛好把這個洞唯一現實來源的唯一偵測機會關掉。

#### 已定案：Q7 — append-only 自動備份表，存 before-image；硬保證只有一條

**風險是有牙齒的**：Q3 定了「一個劇本一列、自動存檔重寫整份 doc」，而 **⌘Z 只活在瀏覽器分頁裡**，分頁一關就沒了。編劇失去的不是一個功能，是三個月的稿。

**(a) 加一張 append-only 的自動備份表**（`screenplay_id`／`doc`／`created_at`），寫入的是 **before-image**（被這次存檔覆蓋掉的那一份 doc，成本幾乎為零 —— 它本來就在手上）。**無查閱 UI，v1 全部保留。** 論據同交付快照（票券 07）：**寫入時幾乎免費、事後補不回來**。

> **它是 recovery 機制，不是版本歷史功能**（作者措辭）。

加 UI 就是把保險變成功能，會立刻拖出「怎麼比較差異」「怎麼命名」「能不能只還原一半」一整串 —— 而**版本鎖定已被否決**。要救稿時從 `psql` 手動撈。命名避開 `CONTEXT.md` 的 Avoid 詞（版本／版次／revision／鎖定），叫**自動備份**。

**(b) 原子性（作者要求）**：

> 凡是依 backup policy 判定需要建立 backup 的 save，**backup 與 canonical document update 必須作為同一個 atomic state transition 提交**。

沿用 Q4 對「schema migration、doc 更新、`doc_seq` 遞增是同一個原子操作」的同一條規則，並繼承 `doc_seq` 的並行檢查。

**(c) 觸發判準是伺服器端的純時間判定，不由 client 宣告。** 否決「編輯器實例的生命週期（載入 doc → 關掉分頁）」這種定義：它是 client 宣告的，而 client 會開兩個分頁、會離線、會當掉；更糟的是**分頁不關** —— 擺著三天就是「一個階段」，三天只留一筆備份，而保護間隔正是這條決策唯一在買的東西。判定只看備份表的 `MAX(created_at)`，不問 client 任何事。

**唯一的硬保證（規格層級）**：

> **距這份劇本的上一筆自動備份 ≥ 2 小時**時，該次存檔先寫一筆備份。
> 對外可講的承諾：**「任何時候最多只會退回兩小時。」**

**降級為 heuristic（實作層，非不變量）**：「距上次成功存檔 ≥ 30 分鐘就視為新的一次坐下」。作者否決它進規格的理由**不是 30 這個數字**，而是它的語意是**系統對使用者行為的推測** —— 系統並不知道編劇是否真的重新坐下，只知道兩次寫入的時間差。把它寫進規格，等於把剛從 client 拿掉的 session 概念用 idle time 從後門放回來。**規格該描述系統能保證的事，不是系統對使用者行為的猜測。**

它安全地待在實作層，是因為兩條規則方向一致：**heuristic 只會讓備份變多、絕不會變少**，所以在任何參數值下都不可能弱化那個硬保證 —— 可以加、可以調、可以整條拿掉，規格書上那句承諾都不受影響。

**(d) 這條規則住在 persistence 模組裡**（Q4 為了不堵死 Yjs 定的第 3 條：「整份 doc 覆蓋」這個假設集中在一個模組後面）。呼叫端只知道「存」，**完全不知道有備份這回事** —— 日後換 Yjs 時，這條規則跟著那個模組一起換，不會散進程式各處。

**(e) 誠實的成本**：130 場的 doc 幾百 KB，`jsonb` 走 TOAST 會壓縮；依硬保證的頻率，重度連續寫作一天約 4～5 筆、一般一天 2～3 筆，一年數十 MB／劇本。v1 單人規模吃得下。真痛了再加保留策略（只留最近 N 筆 + 每日最後一筆）—— 那是**純刪除**，不動資料模型，所以不必現在決定。

**否決的兩條**：

- **只靠 PostgreSQL 備份／PITR。** 它救得了「資料庫掛了」，救不了**「編劇自己刪掉一整幕然後關掉分頁」** —— 那在資料庫眼中是一次完全正常的寫入，而後者才是這個產品真正會發生的事。
- **改存增量（Step log）。** 可序列化、可重播的 log **會製造第二個權威**（log 與 doc 誰是真相），正是 Q1b 否決「command 作為資料」、Q1 否決「兩個寫入者」的同一條理由，不知不覺走進 event sourcing。備份存的是**完整 doc 快照**，永遠不需要重播就能讀懂 —— 「能用眼睛看」正是 Q3 選 `jsonb`、Q4 拒絕 Yjs 時反覆買的那個東西。

#### 已定案：Q8 — 交付快照自己一張表，另外兩份收進 `documents`

**(a) 交付快照 → 獨立一張表**（`screenplay_id`／`exported_at`／`mapping jsonb`，append-only、v1 全部保留）。它是系統裡**唯一刻意不可變**的東西 —— Q4 已據此決定它**沒有** `doc_schema_version` 與 `doc_seq`（不被載入編輯、不遷移），那正是它與其他所有東西的分野。不為了少一張表把它塞進通用文件表。

**(b) 分場大綱 → `documents` 表**（`screenplay_id`／`kind`／`body jsonb` + `doc_schema_version` + `doc_seq`）。自由文字、不與場次關聯（`CONTEXT.md` 已定），掛在劇本上、v1 只有一份。票券 18 若長出劇情大綱／故事大綱，加 `kind` 即可。

**(c) 角色設定表 → 也進 `documents`，`body` 是一份極簡的 ProseMirror doc**（每個節點一筆人物引用），**不是**關聯表 `(screenplay_id, character_id, order)`。

否決關聯表的理由：它的誘惑是**可以掛真外鍵**，但那個外鍵**沒有消費者**（ADR-0005 之下人物 append-only、永不刪除），而代價是**引用會有第二種住所** —— ADR-0005 的「存在＝被引用」判定得同時掃 doc 又掃表，Q6 的 A+ 不變式與 `missingRefs` 診斷也要長出第二套實作。收進 doc 後，**引用只有一種住所**。

反方向的疑慮「只是一份排序清單，做成 PM doc 太重」是反的：**拖曳排序、⌘Z、command 層、projection 全部免費復用**（拖曳排序已在 v1，票券 03）；做成關聯表反而要另寫一套小 CRUD 加排序，而且繞過了 Q1b 的唯一寫入口。加上票券 18 遲早要把它排版進交件 PDF，走 PM doc + CSS 模板就是既有管線。

**⚠️ 作者附加的條件（已寫進 ADR-0007）**：

> 若角色設定表的職責僅是「有序人物引用清單 + PDF 排版來源」，則 PM doc 方案成立。
> 若未來它可能演化為具有**篩選、分類、群組、搜尋**能力的 **entity browser**，則應重新評估它是 document 還是 **projection/view**。
> v1 先採 PM doc，並把此假設記錄於 ADR，**避免未來把暫時決策誤認為永久不變量**。

重新評估的觸發條件是可指名的：地圖 **Not yet specified** 的「按實體聚合的地點／人物清單視圖」那塊迷霧畢業之時 —— 那正是 entity browser。

**(d) 專案／劇本邊界維持既有裁決**（同時回答本票券原本列的第 6 題）：**人物與地點掛專案**（`CONTEXT.md`：影集放寬成一對多時人物跨集有身分連續性）；**劇本 doc 與 `documents` 掛劇本**；v1 專案與劇本為 **1:1**。

**(e) 要點名的細節**：`documents` 的每個 `kind` 有自己的 node schema 與自己的遷移鏈，所以那一列的 `doc_schema_version` 存的是**該 kind 的 schema 版本**，不是一個全域數字。不點名的話，日後會有人以為那是共用的。

**(f) 順帶收掉「再往後」清單的兩項**（依既有判準推導，未另行盤問）：

- **`documents.body` 要不要也是 ProseMirror doc** —— 是（b、c 兩項都是）。
- **群演清單掛哪** —— 掛**場次節點的 attr**。這是 Q1 判準的直接結果：群演是**場次限定實體、id 只在該場次內有意義、不進人物表**（Q5 已定），所以它是「編輯器裡打出來的、住在那棵樹上」的東西，不是跨劇本的實體。這也正是 Q5 說「跟著場次被複製過去是正確的、不需去重」的原因。

## Answer

**劇本存成一份 ProseMirror JSON，`jsonb`，一個劇本一列；doc 是唯一權威，所有寫入只走 domain command 層。**

八個子問題的裁決（詳見上方 `## Comments` 的逐題記錄）：

| | 決策 |
|---|---|
| **Q1** | 混合，但關聯式那一半永遠是**衍生的** —— doc 是結構與場次 metadata 的唯一權威；表只裝本來就不在 doc 裡的東西（專案、劇本、人物、地點、交付快照）。 |
| **Q1b** | **domain command 層，v1 第一天就建。** command 是程式碼不是資料（否決 command log ＝ 第二個權威）。三層：domain command（意圖）→ PM Step（機械變更）→ doc（唯一權威）。准入判準與 edge boundary 規則見上。 |
| **Q2** | **v1 不建投影表**，場次表在讀取當下由純函式 `projectSceneTable(doc)` 推導。投影表日後加是免費的（key 是 `doc_seq`）。 |
| **Q3** | **一個劇本一列、`jsonb`**。真正的理由是原子性（跨場次變更寫到一半失敗＝違反不變式的劇本）。代價是寫入放大，用 debounce 而非改資料模型處理。 |
| **Q4** | **存 ProseMirror JSON，不存 Yjs**（約束 3 的正面回答）。四條規則保住升級路徑；`doc_schema_version`（隨程式碼）與 `doc_seq`（隨資料）分開；遷移採 lazy 且讀取路徑一律不寫回。⚠️ 「日後遷移不貴」是承重且未實測的事實 → 票券 19。 |
| **Q5** | **`sceneId` 由編輯器產生，資料庫沒有 `scenes` 表** —— 存在＝在那棵樹上。去重規則、跨劇本貼上鑄造新身分、`addToHistory: false`，以及「場次身分只在五個時刻被鑄造」的不變式。 |
| **Q6** | **引用不補外鍵。寫入路徑嚴格拒絕，讀取路徑無條件容忍。** command 層強制引用的實體必須存在；doc 允許懸空引用，顯示名是渲染權威；`missingRefs` 是 projection 的**診斷輸出**，不落地、不對編劇曝露。 |
| **Q7** | **append-only 自動備份表，存 before-image**，無 UI、v1 全保留；備份與 doc 更新是**同一個原子操作**。硬保證只有一條：**任何時候最多退回兩小時**。 |
| **Q8** | **交付快照獨立一張表**（唯一刻意不可變）；**分場大綱與角色設定表收進 `documents`**（body 皆為 PM doc）；實體掛專案、doc 與 documents 掛劇本，v1 1:1。角色設定表附一條有效期條件（見 ADR-0007）。 |

**作者收斂時列出的邊界**：

```
canonical document = ProseMirror JSON
storage            = jsonb
schema version     = doc_schema_version
concurrency        = doc_seq
write boundary     = commands
read boundary      = projection
migration          = schema migration
backup             = append-only before-image（recovery，不是版本歷史）
future collaboration = Yjs（待票券 19 驗證）
```

**已寫成 [ADR-0007](../../../docs/adr/0007-document-as-single-authority.md)** —— 三個條件都成立（難以回頭、後人會問為什麼、真實權衡的結果）。兩根支柱：**doc 為唯一權威**、**寫入只走 command abstraction**。

**留給後續票券的事**：
- 票券 19（Yjs 遷移 spike）驗證 Q4 那條承重事實。
- 票券 06（規格書定稿）要展開 schema 形狀（群組本身是不是節點 → 決定它需不需要 id，見 Q5(e)），並把 Q6 的寫入嚴格／讀取容忍**並排寫出來**，否則後人會把其中一半當 bug 修。

### 來自 [ProseMirror doc → Y.Doc 遷移可行性 spike](./19-yjs-migration-spike.md)（2026-08-30，prototype 已結）

**Q4 那條承重且未實測的假設已實測，結論是成立 —— Q4 維持。** 六項驗收（node type／tree／attrs／`sceneId`／text／marks）全過，含子場次、場次群組、雜景多值地點、草稿在內的完整 fixture 往返等價，且中間走過真正的 bytes 持久化。

**但 Q4 的附帶規則要加第 5 條**（spike 的探針實測發現，非推測）：

> **5. 任何可能裝 `null` 的 attr，schema 預設值必須也是 `null`。**
>
> `y-prosemirror` **不儲存 null attr**，回程一律由 schema 預設值填補。本次往返之所以等價，是因為 `kind` 的預設值剛好也是 `null` —— 那是巧合不是保證。探針證據：`default: '一般'` 的欄位裝 `null`，往返後**靜默變成 `'一般'`**。遷移不會報錯，只會改掉編劇的稿。

受害候選就在眼前：對白的**發聲方式**（一般 / V.O. / O.S.，票券 03 已決定未實作）。要嘛預設 `null`、要嘛不允許 `null`，不要兩者兼有。

**兩項數字，供 Q3 的取捨留底**：Y.Doc update **比 PM JSON 小**（0.91×，所以「換 Yjs 會撐大儲存」不是有效論據）；Y.Doc 的 attrs 是**結構化保存**的（陣列仍是陣列、布林仍是布林），所以換 Yjs 之後 Q3 買的除錯能力不是歸零，是從「`psql` 裡直接看」退成「得先跑一支解碼腳本」。

**Q4 附帶規則 1（schema 必須 isomorphic）也第一次獲得實地檢驗** —— spike 的 schema 只 import `prosemirror-model`，在 Node 裡直接跑得動。
