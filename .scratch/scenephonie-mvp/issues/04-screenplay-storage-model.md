# 劇本儲存模型

Type: grilling
Status: open
Blocked by: 02, 03, 07

## Question

劇本在 PostgreSQL 裡怎麼存？場次是關聯式資料表的一列，還是編輯器 JSON 裡的一個節點？

候選方案：

- **純 JSON** — 整份劇本存成編輯器的 document JSON。寫入簡單，但場次表要查詢時得把整份 JSON 撈出來在應用層解析。
- **純關聯式** — 場次、區塊各自成表。查詢自然，但要跟編輯器的 document model 雙向同步，複雜且容易不一致。
- **混合** — 場次 metadata 進關聯式表（可查詢），場次內容（Action／Dialogue）存 JSON。

要回答：

1. 選哪個？權衡是什麼？
2. **場次的永久 id 由誰產生**、存在哪、如何在編輯器與資料庫之間保持一致？（約束 1）
3. 場次表查詢要多快、多即時？是即時投影，還是可以接受衍生後儲存？
4. 人物與場次的關聯怎麼存？（登場人物是實體，不是字串）
5. 這個模型**擋不擋得住之後加協作**？（約束 3）— 即時協作通常要求 document 是單一 CRDT 結構，混合方案可能與之衝突，這點必須正面回答而不是繞過。
6. 專案與劇本兩個實體的邊界在哪？

依賴 02（要知道場次表需要查詢什麼欄位）與 03（要知道編輯器能提供什麼樣的 document 結構）。

這張票很可能值得一份 ADR — 難以回頭、後人會問「為什麼這樣選」、且是真實權衡的結果。三個條件都成立時就寫。


## Comments

### 來自 [區塊編輯器選型與 /scene 輸入體驗](./03-editor-prototype.md)（2026-08-20）

**三條已經定下來的約束，儲存模型不得違反：**

1. **`sceneNo` 不進資料庫。** 場次號是純渲染值 —— 系統裡沒有任何東西用它當 key（約束 1：下游一律掛 `sceneId`）。存衍生快取會讓 PDF 匯出必須選擇要不要相信它：相信則可能印出錯的場次號（而水準線是「拿去參賽會被接受」），不信則該欄位只剩說謊的能力。
   「場次表用 SQL 撈比較快」這條論據比看起來的弱：排序要用的**序列次序**無論如何都得存，有了次序就能算出場次號。

2. **文件是 `scene+`，場次是 `isolating` 的 block node，content 為 `sceneBlock+`。** 場次之外不存在可編輯內容，所以不會有「不知道該歸給哪一場」的孤兒資料。

3. **`sceneId` 由編輯器端產生並存在節點上，但複製貼上會產生重複 id** —— attribute 跟著序列化一起被複製。必須有 `appendTransaction` 主動去重。這決定了「永久 id 由誰產生」那一題的答案形狀：不能只靠資料庫發號，因為破損發生在編輯器內、寫入之前。

**另一類值得預期的坑**：ProseMirror 的同一個位置有兩種表示法（結構位置 vs 正規化後的文字位置），`TextSelection.between()` 會在不注意時從前者變成後者。若要持久化游標或選取位置，得先決定存哪一種。
