# 區塊編輯器選型與 /scene 輸入體驗

Type: prototype
Status: resolved
Blocked by: 01

## Question

Tiptap 撐不撐得起「場次是一等公民實體」的模型？`/scene` 的輸入體驗該長什麼樣？

這是整張地圖技術風險最高的一張票。作者對 Tiptap 只有初步研究、無實戰經驗，而編輯器一旦選錯，資料模型與整個 v1 都得重來。

**必須做出一個粗糙可跑的原型**，不是紙上評估。原型要能：

1. 用 `/scene` 插入一個場次區塊
2. 在場次區塊內填 metadata：場次號、日／夜／晨／昏、內／外、地點、登場人物
3. 在場次底下寫 Action 與 Dialogue
4. 場次可以重新排序，且**排序後外部引用不失效**（驗證約束 1）

要回答：

- Tiptap 的 node schema 能不能自然表達「場次是容器、內含 metadata 與內容節點」？還是得跟它的假設打架？
- 場次的永久 id 放在哪？Tiptap 節點屬性能不能穩定攜帶它、經過複製貼上與重排仍不變？
- metadata 的輸入 UI 是內嵌在編輯器裡（node view），還是側邊面板？哪個比較不打斷心流？
- 如果 Tiptap 不合適，替代方案是什麼（Lexical、ProseMirror 裸用、自建）？

**心流是這張票的驗收標準。** 產品的核心賭注就是「填 metadata 不該打斷寫作」— 原型若做出來自己都不想用，就是失敗，要換方案而不是硬幹。

依賴 01：需要先知道場次 metadata 的精確欄位，否則原型會建在錯的欄位上，浪費一次 HITL session。

產出：可跑的原型（連結為資產，不貼進票券）＋ 編輯器選型結論。

## 待納入考量

**區塊型別可能不只「動作」與「對白」。** 作者指出台灣劇本習慣把「插入鏡頭」寫進三角形（即塞進動作裡），並自覺這讓動作的邊界過於模糊。[插入戲與插入鏡頭的表達慣例](./08-inserted-scenes-and-shots.md) 正在調查三角形究竟承載多少種語意 — **每一種用途都是一個潛在的獨立區塊型別**。

這不阻擋本票券（多一種區塊型別，在架構上與既有的動作／對白無本質差異），但原型的 node schema 設計時應假設**區塊型別會增加**，不要寫死成兩種。

**08 已完成，結論如下：**

- **插入鏡頭應獨立成區塊型別，但不產生新場次。** Final Draft 與 Scrivener 兩套獨立軟體都這樣切分。它是「像場次標題但不產生新場次」的東西 — 這正是作者顧慮的根源，動作區塊不該承擔這個判斷。
- **三角形其餘 6 種語意（環境、表演、鏡頭、字幕、插景、雜景）仍併入動作**，不要每種都獨立成型別。
- **範圍警告**：插入鏡頭型別必須嚴格限定在「單一鏡頭描述」。一旦長出運鏡、景別欄位，就滑向已排除於 MVP 之外的文字分鏡。

因此原型的區塊型別應為**三種**：動作、對白、插入鏡頭。（08 的建議，作者已於 2026-08-18 確認納入 v1。）

### 已驗證的技術結論

1. **Tiptap 的 node schema 能自然表達「場次是容器、內含 metadata 與內容區塊」。** 場次為 `isolating` + `defining` 的 block node，content 限定為 `sceneBlock+`。沒有跟 ProseMirror 的假設打架。

2. **場次號完全不儲存，即時從序列推導可行。** 見 `src/numbering.ts`。插入戲的字母尾綴（S5A）也在同一個函式裡算出來。這是架構約束 1 的實證：**重排時場次號變、sceneId 不變**。

3. **sceneId 存 node attribute 可行，但複製貼上會產生重複 id。** attribute 會跟著序列化一起被複製，貼上的複本沿用原 id，錨點當場破損。**必須有一個 `appendTransaction` 外掛主動去重**，不會自己好。原型做成可切換（底部核取方塊），方便看見問題與修好的差別。

4. **中文 IME 的問題不在 Tiptap。** 原本擔心「node view 裡無法可靠支援注音」會是架構級障礙 —— **不是**。病因是受控輸入的經典 bug：組字期間 input 事件觸發 → 立刻回寫文件 → 值流回 input → 組字緩衝被清掉 → 注音符號一個個掉出來。修法是組字期間只更新本地狀態、`compositionend` 才回寫（`src/cjk-input.tsx` 的 `CJKInput`）。作者已確認修好。

   **這解除了「metadata 不能放在編輯器內部」的疑慮**，三個變體因此可以公平比較。（附帶發現：變體 B 側邊面板當時也有同一個 bug，它並不是這個問題的解方。）

5. **欄位裡的 Tab 會冒泡到編輯器。** 導致 `BlockCycle` 同時觸發，把正在編輯的區塊轉成別的型別、輸入框消失、焦點飛走。需在欄位上 `stopPropagation`。

## Answer

原型：[`../prototypes/editor/`](../prototypes/editor/)，導覽見該目錄的 `README.md`。Tiptap 3.30.1 + React 19 + Vite 8，`pnpm install && pnpm dev`。

### 選型結論：Tiptap 繼續

**node schema 的表達力沒有問題**，這張票最初的疑慮不成立。場次是 `isolating` + `defining` 的 block node，content 為 `sceneBlock+`；文件本身收成 `scene+`，**場次之外沒有可編輯的空間**。沒有跟 ProseMirror 的假設打架。

**真正的成本在別的地方：每一個自訂互動都要跟一層 Tiptap／ProseMirror 的預設行為協商。** 本輪五個 bug 全是同一個家族，這是選型的實質代價，規格書必須帶著它們走：

| 現象 | 根因 |
|---|---|
| 內容掉到場次外，變成孤兒段落 | StarterKit `Paragraph` 的 parse priority（1000）蓋過 `p[data-type=…]` 規則，三種區塊型別要設 `priority: 1100` |
| 新增場次後，後面場次的編號不更新 | node view 只在「自己的節點變了」時重繪；`ReactNodeViewRenderer` 收到 decoration 變更會直接 `return true` 跳過 |
| ⌘+A 被吃掉 | Tiptap 內建 Keymap 的 `Mod-a` 要靠 `priority` 搶，不是註冊順序 |
| 拖曳吃字、跑版、偶爾拖不動 | PM 的原生拖放跟自訂 handler 搶同一個事件；且落點狀態會被 `dragleave` 清掉，提早 return 又沒 `preventDefault()`，瀏覽器就執行預設放置 |
| 選取反白畫不出來 | React 的 `className` 洗掉 PM 透過 decoration 寫上去的 class —— 兩邊不能碰同一個屬性 |
| 漸進式全選在前兩層打轉 | `TextSelection.between()` 會把端點正規化到最近的合法文字位置，拿正規化前的原始位置去比對永遠不成立 |

### 驗收：心流過關

作者實測判斷「還好」，且**拿掉插入戲之後沒有感覺變差** —— 這正是想要的結果：拿掉一個概念而心流不變，代表它本來就沒在付出價值。

### 選定：變體 A · 內嵌簡表

metadata 直接嵌在編輯器裡、像一列簡表。B（側邊面板）與 C（漸進填寫）皆未獲選。

IME 修好後三者才具備公平比較的條件；`⌘+Enter` 在三個變體統一為「新增下一場」之後，差異純化成「metadata 什麼時候問」，比較才成立。

### 已定的輸入設計

- **建立場次走 `/next`（「新增下一場」）**，不是 `/scene`。文件是 `scene+`，你永遠在某個場次裡打字，「在場次裡建立場次」語意上是矛盾的；真正的動作是序列性的。三個入口共用同一條路徑：`/next`、`⌘+Enter`、場次腳部的按鈕。
  ⚠️ 用滑鼠點的入口**必須自己傳插入位置**，靠 selection 推算會插到游標所在的那一場後面。
- **切換區塊型別走 Tab**（動作 → 對白 → 插入鏡頭），`Shift+Tab` 反向。動作與對白交替太頻繁，打指令會毀掉心流。欄位上的 Tab 要 `stopPropagation`。
- **焦點串接**：`/next` → 第一個 metadata 欄位 → Tab 逐欄 → Tab 進正文；對白的人物欄 → Tab → 台詞。
- **漸進式全選**：⌘+A 依文件結構逐層擴 —— 區塊 → 這一場的內文 → 整場（含 metadata）→ 整份。內文與整場要分開，因為「重寫這一場但保留 metadata」是真實的寫作動作。
- **重排與刪除**：⠿ 拖曳（場次可拖，區塊可跨場次拖）；點場次號 `SX` 開選單 → 搬移到⋯／與其他場次對調⋯／刪除這一場。目標清單可用場次號、地點、人物篩選。刪除只剩一場時 disabled，確認彈窗含「下次不再提醒」。
- **無粗體／斜體／刪除線**，StarterKit 相關 mark 全關，落實架構約束 2。

### 場次號：decoration，不進文件也不進資料庫

`projectScenes()` 是純函式，瀏覽器與 Node 都能跑。場次表、PDF 匯出、唯讀分享各自呼叫它；編輯器也一樣，只是得透過 ProseMirror decoration 才能讓 node view 知道該重繪。

**決定性理由**：場次號在系統裡從來不是 key —— 約束 1 說下游一律掛 `sceneId`，沒有任何查詢用場次號 join。它只在渲染的那一刻才有意義，所以就該在渲染時才算。存成 node attribute（衍生快取）會讓 PDF 匯出必須選擇「相不相信這個欄位」：相信則可能印出錯的場次號，不信則該欄位只剩說謊的能力。

**對票券 04 的約束**：`sceneNo` 不進資料庫。而「場次表用 SQL 撈比較快」這條論據比看起來的弱 —— 排序要用的序列次序無論如何都得存，有了次序就能算出場次號。

### 已驗證的錨點行為

- 重排時場次號變、`sceneId` 不變（`numbering.ts` + 場次表投影）
- **複製貼上會產生重複 id**，attribute 跟著序列化一起被複製，貼上的複本沿用原 id、錨點當場破損。**必須有 `appendTransaction` 主動去重**，不會自己好。原型做成可切換以便看見差別。
- 中文 IME 的問題不在 Tiptap，是受控輸入的經典 bug：組字期間回寫文件會清掉組字緩衝。修法是組字期間只更新本地狀態、`compositionend` 才回寫（`src/cjk-input.tsx`）。**這解除了「metadata 不能放在編輯器內部」的疑慮。**

### 範圍變更（三項，已寫進地圖）

1. **拖曳排序拉回 v1** —— 作者實測後認為直覺、值得。但規格書不能只寫「支援拖曳排序」，必須連成本一起寫：得繞過 `isolating`、得處理「搬走最後一個區塊」後的空場次、得跟 ProseMirror 的原生拖放搶事件。
   `isolating` 保留，只有拖曳繞過它 —— 拿掉會讓跨場次的鍵盤選取與刪除把兩場合併，`sceneId` 錨點隨之消失。
