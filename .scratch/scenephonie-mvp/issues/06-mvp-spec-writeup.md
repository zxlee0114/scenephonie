## Answer

**規格書：[`../spec.md`](../spec.md)**（14 節）。七項要求逐一對應：功能邊界 §3、領域模型 §4、編輯器 schema §5、儲存模型 §6、編輯器與輸入體驗 §7、場次表 §8、PDF 匯出 §9、分享與交付 §10、不變式總表 §11、三條約束逐條交代 §12、技術棧與建議實作順序 §13。

### 三項在寫的當下被裁決的問題

寫規格書不只是整合 —— 有三個問題是「攤開來寫才發現非答不可」的，全部當場答掉：

**1. 場次群組的 schema 形狀（[票券 04](./04-screenplay-storage-model.md) Q5(e) 明文留給本票）：群組是節點，且有 id（`gr_` nanoid）；片段仍然沒有 id。**

- **是節點而非旗標**（在成員與片段上各掛一個 `groupId` attr、平坦排在頂層）：那是 [ADR-0003](../../../docs/adr/0003-inserted-scenes-as-subscenes.md) 已經否決過的「平坦 ＋ 旗標」家族**第三次**出現（前兩次是 `S5A` 與 `depth`）。做成節點時，ADR-0004 那兩條不變式（群組不能巢狀、一個場次不能屬於兩個群組）由樹結構**免費保證**；做成旗標則兩者退化成執行期檢查，而且文件狀態本身能說謊。
- **成員是另一種節點（`groupMember`）而非 `scene`**：成員場次**沒有自己的內容**（ADR-0004 明訂），這是真實的結構差異。若共用 `scene` 節點就得把它的內容規則放寬成可為空，那會讓**所有**場次都能是空的。`projectScenes()` 對兩者一視同仁。
- **群組要 id 而片段不要，理由不對稱且有依據**：ADR-0006 保護規則 3 禁片段 id 的理由是「插入子場次把一個片段切成兩半」的繼承問題 —— **片段會被切開，群組不會**。而群組需要 id 是因為 command 層要定址它（`assignFragmentToMember(groupId, fragmentIndex, memberId)`），而准入判準明文要求以 id 定址而非位置。`fragmentIndex` 是呼叫當下算出的**傳遞參數、不被儲存**，規則禁的是持久化的引用。
- **順帶掉出一條正規化規則**：相鄰兩個片段若歸屬同一個成員就合併（`addToHistory: false`）—— 那個區別在模型裡沒有意義，且 ADR-0006 的重疊群組遷移路徑假設片段是極大的。
- 附帶結果：文件頂層從 `scene+` 放寬為 `(scene | sceneGroup)+`。**這不是鬆綁「文件只由場次組成」** —— `sceneGroup` 只是一群場次的容器，沒有自己的可編輯空間。

**2. 對白排版變體（地圖迷霧，原文即註明「預期在規格書定稿時決定」）：選行內式。**

三條理由：(a) 它是第 44、46、48 三個屆別**連續存在**的那一種，置中分行式是第 48 屆才新增的；(b) 兩種都是官方認可的參考範例，所以這個選擇**在投稿風險上是零** —— 這不是在賭，是在兩個都安全的選項裡挑一個；(c) 它與「人物名與對白分離存成欄位、渲染時才組成那一行」的資料模型自然對應。

⚠️ 加上置中分行式是**換一個 CSS 模板，不動資料模型** —— 這是「格式退化成渲染樣式」這個核心賭注的第一次兌現。實作時注意北藝大那套人物名後**有**冒號、GHSA 範例二**沒有**，不可混用。

**3. 頁面設定的數字缺口（[票券 01](./01-taiwan-screenplay-format-spec.md) 起掛了兩張票的 ⚠️）：不是缺口，是問錯了。**

v1 只做 GHSA 一種格式，而 **GHSA 明文硬性的只有「直式橫書正體中文 12 級字」**，字型／行高／邊界它根本沒規定 —— 沒規定的東西由模板選定，任何合理值都過得了「拿去參賽會被接受」。[票券 22](./22-taipei-kaohsiung-submission-requirements.md) 撿到的那三組打架的數字（字級 12 vs 14、行高 26 PT vs 20 pt）**分屬三個不同的徵件**，本來就不該合成一組「台灣通則」，而 TNUA 的完整數字更是另一套獨立規範，**不得拿來冒充 GHSA**。
➕ 同時採納票券 22 的建議：**「每頁行數」從「待補」改成「不存在」** —— 五個一手來源全部沒有，台灣簡章用的是字級＋行高＋邊界，不是美式的每頁行數。**這是一條實質差異，不是資料缺漏。**

### 兩張畢業出來的新票券

按票券要求（「殘留的問題應該變成新票券，而不是塞進規格書當作已解決」）：

- **[票券 24 認證方案與專案擁有者欄位](./24-auth-and-project-owner.md)** —— 兩團霧合成一張，因為它們耦合（owner 指向誰取決於認證形狀）。夠銳利的原因是[票券 12](./12-share-link-live-or-frozen.md) 已把範圍砍掉一半：讀者端 by-token，認證只涵蓋編劇自己這一側。⚠️ 第 3 題有真正的爭點：owner 欄位要不要現在就加 —— 它像「交付快照／`種類`」那組「事後補不回來」的先例，還是像「專案類型」那組「日後補一欄帶預設值是廉價遷移」的先例？
- **[票券 25 部署與資料庫託管](./25-deployment-and-hosting.md)** —— 夠銳利的原因是[票券 05](./05-pdf-export-tech.md) 給了硬邊界條件（Cloudflare Workers 純執行模式不可行），選項因此收斂。

**兩張都擋部署，不擋開工** —— 規格書 §13.2 的階段 0～2（isomorphic schema ＋ command 層 ＋ 編輯器）完全不需要它們的答案。

### 誠實交代：地圖還沒到站

本票券原本寫「這張票關閉時，地圖到站」。**那句話現在只對了一半。**

**目的地（可直接開工的 MVP 規格書）達成了** —— 七項要求全部涵蓋，功能邊界、資料模型、三項關鍵技術選型（Tiptap、PM JSON、Puppeteer）全部寫定。

**但「沒有任何得先想清楚才敢動手的問題殘留」這條判準，嚴格說還差三張票**：24、25（擋部署）與 [21](./21-ask-industry-scene-numbering.md)（作者外出訪談，事後複核）。把它們塞進規格書當作已解決，正是本票券明文禁止的做法，所以照規矩開票。

**還留在迷霧裡的三塊**（新手引導的形式、按實體聚合的清單視圖、人物關係圖）**都不影響 v1 的資料模型與開工**，維持在迷霧。
