# 唯讀分享連結：活連結、凍結版本，還是兩者都要

Type: grilling
Status: resolved

## Question

地圖上「唯讀分享連結的機制」那團霧於 2026-08-21 由票券 07 畢業成本票券，並擴寫了題目。

**觸發它的觀察（作者，業界經驗）**：製作端的需求會回頭要求編劇改稿，**而需求有時候又會反悔**。劇組成員因看劇本的時間不一致，打開同一條連結會看到不同的內容 —— 「即使是線上分享的，可能也需要穩定的」。

**票券 07 承認這是它沒解決的問題。** 該票原本主張「唯讀連結永遠是即時投影，所以沒有不同步問題」，已自行推翻。正確的拆法是：

- **編號說謊**（製片手上寫 S12，系統裡 S12 已是別場戲）—— 投影模型確實消滅了這個。
- **內容漂移**（兩人在不同時間看到不同的戲）—— 投影模型**不但沒消滅，還讓它更隱形**。PDF 至少有實體差異可察覺，活連結什麼線索都沒有。

### 要回答

1. **v1 的唯讀連結是活的、凍結的，還是兩者都提供？** 若兩者都要，分享時怎麼讓使用者表達意圖而不變成一個沒人看懂的開關？
2. **凍結的連結凍結的是什麼？** 一份渲染快照，還是「指向某個時間點的資料」？這關係到它要不要落地成獨立的儲存（餵給票券 04）。
3. **URL 形式**：token 長什麼樣？
   ⚠️ 票券 07 已定：**token 不該等於劇本 id** —— 撤銷連結的動作就是換 token，若兩者相同，撤銷等於換掉劇本的身分。
4. **可否撤銷？有沒有有效期？**
5. **活連結要不要有「內容可能已變動」的線索？** 例如顯示「最後更新於 X」。這是本票券最便宜的一半 —— 就算完全不做凍結，光這一行就讓漂移可被察覺。
6. **交付快照要不要掛到分享連結上？**
   票券 07 已把觸發定成**原則**而非清單：「凡是產生離線副本或凍結視圖的交付動作，都存一份快照」。本票券的答案決定分享連結算不算這種動作。

### 背景素材（來自票券 07 的查證）

**沒有任何主流工具只做活連結，也沒有只做凍結連結的 —— 兩者是兩種不同的分享意圖。**

- **編劇業界：顏色稿制度。** 白稿鎖定場次號與頁碼，之後每輪改稿換色（藍、粉、黃、綠、金黃）且只發改動的頁。顏色本身就是版本標示。本專案不採用此制度（見 [ADR-0002](../../docs/adr/0002-scene-id-and-derived-scene-numbers.md)），但它證明**製作端對「穩定版本」的需求是制度化的，不是個別偏好**。
  - [Final Draft 標準修訂色序](https://kb.finaldraft.com/hc/en-us/articles/15575314119316-What-are-the-standard-revision-set-colors)
  - [Celtx：理解劇本修訂](https://blog.celtx.com/understanding-script-revisions/)
- **Google 文件**：「發布到網路」有「變更時自動重新發布」勾選框，取消勾選即凍結。[說明](https://support.google.com/docs/answer/183965?hl=en&co=GENIE.Platform%3DDesktop)
- **Figma**：檔案連結預設是活的，但可在版本歷史對某一版複製連結。**值得注意：這個功能在社群長年被抱怨難用** —— 若我們要做凍結連結，這是現成的失敗案例可學。[說明](https://help.figma.com/hc/en-us/articles/360038006754-View-a-file-s-version-history)、[論壇抱怨](https://forum.figma.com/t/sharing-specific-version-of-a-file-doesnt-work-as-expected-imho/11012)

### 注意範圍

**不要滑進版本管理。** 票券 07 已明確排除版本鎖定（Final Draft 那套）進入 v1。本票券若答出「凍結」，要守住它是**分享機制**的一部分，而不是替 v1 引入一整套版本概念與其 UI。

## Answer

一句話：**live 是分享語意，frozen 是交付的副產品** —— 兩者都要，但沒有開關；使用者表達意圖的方式是「我在交稿」vs「我在給人看」，那是他本來就懂的區別。見 [ADR-0008](../../docs/adr/0008-share-as-relationship-delivery-as-commitment.md)。

### 1. 活的、凍結的，還是兩者？—— 兩者，但拒絕做開關

分享面板只有一種東西：**活連結**（編劇日常「給導演看最新稿」）。凍結連結不是面板上的第二個選項，而是**交付動作的副產品**：按下「匯出 PDF」時，除了 PDF 檔，同時得到一條屬於那次交付的連結。

否決 toggle 的理由是背景素材裡現成的失敗案例：**Figma 有凍結連結，但藏在版本歷史裡，社群抱怨了十年**。凡是要使用者理解「活 vs 凍結」這組詞才能正確分享的設計，都會退化成那個樣子。

這同時兌現票券 07 已定的原則（「凡是產生離線副本或凍結視圖的交付動作，都存一份快照」）—— 凍結連結天生就是那個原則的一個實例，不必為它發明新觸發。

**紅線**：沒有版本列表、沒有比較、沒有還原。一次交付＝一條連結，如此而已。

### 2. `/s/<token>` 的 identity 是**分享**，不是劇本

⚠️ 這是本票券最承重的一步，作者要求先定 identity 再談 snapshot 邊界。

**論證不是「比較有彈性」，而是 frozen link 在 screenplay identity 下沒有位置可站** —— 它指的不是劇本的現在，而是劇本的某個過去。若 token 是劇本的別名，「同一個劇本的兩條 token 指向不同內容」就是矛盾。另兩處也會爆：撤銷一條 frozen link 不該撤掉劇本的存取權；「第 3 稿的連結」與「第 5 稿的連結」是**兩次不同的分享事件**，不是同一個東西的兩個門牌。

因此 **`share` 是一次具有獨立 identity 與生命週期的對外分享關係**（作者定義），劇本只是它的一個欄位。

**守住的紅線**：identity 是 share ≠ 要做設定面板。v1 的 share **零配置** —— 視圖組合固定、沒有標題、沒有密碼。選這個 identity 是為了讓 frozen 有地方站，不是為了長出開關。

由此順帶解掉「分享的是什麼」：**劇本與場次表是同一個 share 的兩個視圖**（頁內切換），不是兩條連結。它們共用的是**分享身分**，而不只是投影函式 —— 後者只證明 projection 可以共用，證不出 sharing identity 該共用（作者的修正）。

### 3. frozen 的 identity 是**某次交付**，不是 doc state，也不是 rendered artifact

兩個候選各有致命傷：

- **純 canonical doc state**：內容凍結，但**推導值沒凍結**。票券 07 對這件事下過判決 —— 存推導的輸入等於讓演算法一改就回頭改寫歷史（紙上印 `12A`，系統重算成 `12-1`）。票券 13 一旦翻案攤平子場次，同一條 frozen link 會顯示不同的場次號，frozen 就不 frozen 了。
- **純 rendered artifact**：像素凍結，代價是把樣式一起凍死 —— 排版 bug 修不了、字型換不了，而且會開始需要保留舊渲染器，那正是版本管理的坑。

**定案：frozen 的 identity 是一筆交付（delivery）**，它凍結的是**該次交付所承諾的 canonical content 與 semantic derived values**。它承諾的是「**這是那次交給你的那份稿**」—— 內容一致、場次號一致 —— 而不是像素一致；像素一致由 PDF 檔本身提供，那才是真正的離線副本。

於是**票券 07 的交付快照與 frozen link 是同一個東西的兩面**：快照是它的內在，連結是它的公開把手。不是三個實體。

這也修掉票券 07 的一個弱點：快照原本只存 `場次 id → 號碼`，若 doc 後來面目全非，那張對照表**無法單獨閱讀**（`sc_abc → 12` 是哪場戲？）。但這條要求**不寫成「必須有 doc 欄位」**（作者修正：那是 persistence concern），而寫成不變式：**一筆交付必須能獨立重建該次交付所承諾的語意。**

### 4. 兩條正式不變式

> **不變式 D（交付的判準）**：任何**對外承諾「在後續 canonical state 改變後仍保持不變」**的動作，都必須先建立一筆交付；該動作輸出的一切都指向那筆交付。

⚠️ 判準是作者改寫的。原先寫成「把內容送出系統之外」，那是**通道**而非**承諾**，會把純粹的線上唯讀誤判進來、也擋不住未來某個不出系統卻做出凍結承諾的功能。

v1 的實例是**衍生**的，不是定義：匯出 PDF ✅、frozen 分享連結 ✅（同一次交付的另一個把手，不是第二個動作）、活分享連結 ❌、畫面內的場次表 ❌。

> **不變式 E（semantic freeze / visual drift）**：渲染器日後的純視覺變更**可以**影響已存在的交付；但**不得重新計算該次交付已承諾的 semantic derived values**。

這條劃出允許漂移的邊界：樣式變好看是可以的（它不說謊），場次號被重算則絕對不行。

**兩個附帶裁決**：

1. **同一份劇本重複匯出＝兩筆交付。** 交付是**事件**不是狀態；去重會製造「這次沒有新交付」的困惑，且票券 07 已定全部保留、不清理。
2. **快照是必然的，連結是自願的。** 每次交付都建立（不變式 D 強制），但 **token 懶惰鑄造** —— 交付當下不產生可存取的 URL，直到使用者按「取得這次交付的連結」。否則「我只是想印一份 PDF」會在背後多出一條公開可讀的網址，那是安全面的意外。這條分離讓不變式硬得起來而不會咬人。

### 5. Atomicity boundary：delivery 是渲染的**輸入**

這裡有一條做不到的邊：PDF 的位元組送達對方硬碟，不可能與資料庫交易同一個原子操作。所以問題不是「怎麼讓它原子」，而是**失敗時往哪一邊倒**，而兩種失敗嚴重不對稱：

| 失敗 | 後果 |
|---|---|
| 交付已記錄、渲染失敗 | 一筆沒有紙的交付。**它沒有說謊**（只宣稱「T 時刻承諾的內容是 C」），可回復。 |
| 紙已到對方手上、交付沒記錄 | 紙上印著我們沒存過的號碼 —— **票券 07 整個論證的那個「事後補不回來」**。永久損壞。 |

順序因此是被迫的：**先提交交付，再渲染。** 但真正的答案比排序更強一句：

> **Delivery 是渲染的輸入，不是渲染的產物。**

渲染器讀的是那筆已提交的交付，不是 live doc。這一句同時買到四樣東西：atomicity 邊界縮成**只有一個交易**（建立交付），其餘全是它的純函式；重試＝用同一筆交付重新渲染、**不產生第二列**；「frozen link 的內容來源不得依賴 current screenplay state」**PDF 路徑免費也拿到**，不必各自保證一次；PDF 頁尾的時間戳必然是 `delivery` 的建立時間而非渲染當下的 now（否則重新渲染會印出不同的字）。

⚠️ 兩條作者加的限制：

- **「artifact 尚未成功產生」是交付的一個合法狀態**，不是待清理的異常。不為它設狀態機旗標（旗標會說謊），使用者重試即是重新渲染同一筆。
- **PDF 的 byte-for-byte determinism 不是 domain invariant** —— 它只是這個順序的良好後果。把它升格會直接撞上不變式 E：字型與渲染器本來就允許視覺漂移。

（frozen link 的 token 懶惰鑄造是**之後**一筆獨立寫入，只引用一筆已存在的交付，不在這個原子邊界內。）

### 6. 活連結的漂移線索

**無條件要做。** 活連結頁面頂端固定一行：「即時連結 · 最後更新於 X」。它的價值不在資訊量，而在**讓漂移變得可察覺** —— PDF 有實體差異可察覺，活連結什麼都沒有，這行字就是補回來的那個線索。這是本票券最便宜的一半。

⚠️ 作者的修正：**「內容是否變更」與「UI 顯示什麼」是兩件事** —— 前者以 canonical state（票券 04 的 `doc_seq`）定義，後者才用 timestamp 做 presentation。時間戳只是那個 canonical 事實的人類可讀投影，不是判準本身。

### 7. token 形式、撤銷、有效期

- **token**：規格要求的是 **opaque 且不可枚舉**。nanoid 是**實作選擇**，不寫進規格（作者的降級）。URL 形如 `/s/<token>`。
- **撤銷**：寫 `revoked_at`、**保留該列** —— 刪掉就查不出「這條連結曾經存在過」，而整個交付哲學是不說謊。被撤銷的連結對訪客顯示**中性頁面**（「這條連結已停用」），不透露劇本是否存在、不透露是誰撤的、不引導去要新連結。重新分享＝鑄新 token，與舊 token 互不牽連。
- **有效期：v1 不做。** (1) 它製造的失敗模式**專挑最糟的時機發作**（製片開拍前打開連結發現過期）；(2) 對「不小心被轉傳」這個真實威脅模型，過期是安全劇場，撤銷才是真正的控制；(3) 對 frozen link 它自相矛盾 —— 它是一筆**全部保留、不清理**的交付的把手，給它有效期等於讓把手比它指的東西先死。

### 8. frozen link 要不要說「作者後來又改了」—— 對讀者不說，對編劇說

這看似是第 6 點「讓漂移可察覺」的對稱套用，但**對稱在這裡不成立**。

不對讀者說的理由是**洩漏**：frozen link 的受眾是被刻意凍結的一方，告訴他「作者後來改了 40 次」是把 current state 洩漏給沒有資格知道的人 —— 投獎與交件情境下這是明確的害處，而那正是 frozen link 最主要的用途。且「我後來改了」是**編劇該主動說的話**，系統替他宣布等於替他做了一個他沒同意的溝通。

frozen link 不需要這個提示也不失守：它頁頂固定顯示「**這是 X 時交付的版本**」，收件人自己就能判斷新舊 —— 那是第 6 點在凍結側的等價物。

反過來，**在編劇自己的分享清單裡**顯示「這條連結凍結在 3 天前，之後 canonical state 已變更」有用且零洩漏。撤銷本來就需要一份分享清單，這一行搭便車。

### 對其他票券的影響

- **票券 07（已關閉）**：交付快照的觸發原則**被本票券的不變式 D 取代**（判準從「送出系統之外」改為「是否對外承諾在後續 canonical state 改變後仍保持不變」）；快照的內容要求從「`場次 id → 號碼`」擴充為「能獨立重建該次交付所承諾的語意」。它與 frozen link 是同一個實體的兩面。
- **票券 04（已關閉）**：`share_links` 是新的一張關聯式表（「本來就不在 doc 裡的東西」的又一個實例，不破壞 ADR-0007）。交付快照那張表獲得一個**新的公開消費者**，但它「唯一刻意不可變、無 `doc_seq`／`doc_schema_version`」的地位不變 —— 反而被本票券的不變式 E 加固。**與 append-only 自動備份表不共用**：備份是 before-image、無 UI、可被清理策略碰；交付刻意不可變。混用會讓票券 04「唯一刻意不可變」這條分野失效。
- **票券 05（已關閉）**：渲染器的輸入從 live doc 改成一筆已提交的交付。不影響技術選型。
