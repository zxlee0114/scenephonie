# 分享是一段關係，交付是一則承諾

唯讀分享連結**兩種都做**（活的與凍結的），但**沒有開關**。使用者表達意圖的方式是他本來就懂的那個區別 —— 「我在交稿」vs「我在給人看」。三根支柱：

> **① `share` 是一次具有獨立 identity 與生命週期的對外分享關係。** 劇本是它的欄位，不是它的身分。
> **② `delivery` 是一則承諾：「這份內容在你之後改稿時仍保持不變」。** 凍結連結與 PDF 是同一筆交付的兩個把手。
> **③ Delivery 是渲染的輸入，不是渲染的產物。**

## 這條決策要解的問題

製作端會回頭要求編劇改稿，**而需求有時候又會反悔**。劇組成員看劇本的時間不一致，打開同一條連結會看到不同的內容。

票券 07 原本主張「唯讀連結永遠是即時投影，所以沒有不同步問題」，並自行推翻了它。正確的拆法是兩個問題：

- **編號說謊**（製片手上寫 S12，系統裡 S12 已是別場戲）—— 投影模型確實消滅了這個（[ADR-0002](./0002-scene-id-and-derived-scene-numbers.md)）。
- **內容漂移**（兩人在不同時間看到不同的戲）—— 投影模型**不但沒消滅，還讓它更隱形**。PDF 至少有實體差異可察覺，活連結什麼線索都沒有。

而業界證據顯示這不是個別偏好：編劇圈的**顏色稿制度**（白稿鎖定場次號與頁碼，之後每輪換色、只發改動的頁）把「穩定版本」制度化了。本專案不採用該制度，但那個需求是真的。

## Considered Options

**只做活連結。** 否決 —— 就是上面那個內容漂移，且沒有任何主流工具只做一種。

**做一個「凍結此連結」開關。** 否決。**Figma 有凍結連結，但藏在版本歷史裡，社群抱怨了十年** —— 這是現成的失敗案例。凡是要使用者先理解「活 vs 凍結」這組詞才能正確分享的設計，都會退化成那個樣子。真正的洞見是：那組詞是**實作的詞彙**，不是編劇的詞彙；編劇腦子裡的區別是「交稿」與「給人看」，把凍結掛到交付動作上，開關就消失了。

**token 的 identity ＝ 劇本。** 否決，而且理由是結構性的：**frozen link 在這個 identity 下沒有位置可站** —— 它指的不是劇本的現在，而是劇本的某個過去。若 token 是劇本的別名，「同一個劇本的兩條 token 指向不同內容」就是矛盾。另兩處也會爆：撤銷一條 frozen link 會變成撤銷劇本的存取權；「第 3 稿的連結」與「第 5 稿的連結」其實是**兩次不同的分享事件**，不是同一個東西的兩個門牌。

**frozen ＝ 凍結一份 canonical doc state。** 否決。內容凍結了，但**推導值沒凍結**。票券 07 已對這件事下過判決：存推導的輸入，等於讓演算法一改就回頭改寫歷史（紙上印 `12A`，系統重算成 `12-1`）。

**frozen ＝ 凍結一份 rendered artifact。** 否決。像素凍結的代價是把樣式一起凍死 —— 排版 bug 修不了、字型換不了 —— 而且會開始需要保留舊渲染器，那正是本效力明確排除的版本管理坑。

**定案：frozen 的 identity 是一筆交付**，它凍結的是**該次交付所承諾的 canonical content 與 semantic derived values**。它承諾「這是那次交給你的那份稿」（內容一致、場次號一致），而不是像素一致 —— 像素一致由 PDF 檔本身提供，那才是真正的離線副本。

由此，票券 07 的**交付快照**與凍結連結是**同一個實體的兩面**：快照是它的內在，連結是它的公開把手。

## 兩條不變式

> **不變式 D（交付的判準）**：任何**對外承諾「在後續 canonical state 改變後仍保持不變」**的動作，都必須先建立一筆交付；該動作輸出的一切都指向那筆交付。

判準是**承諾**，不是**通道**。票券 07 的原句「凡是產生離線副本或凍結視圖的交付動作」是循環的（凍結視圖由快照定義），中途的改寫「把內容送出系統之外」則是拿通道當判準 —— 它會把純粹的線上唯讀誤判進來，也擋不住未來某個不出系統卻做出凍結承諾的功能。

v1 的實例是**衍生**的，不是定義：匯出 PDF ✅、凍結分享連結 ✅（同一次交付的另一個把手，不是第二個動作）、活分享連結 ❌、畫面內的場次表 ❌。

> **不變式 E（semantic freeze / visual drift）**：渲染器日後的純視覺變更**可以**影響已存在的交付；但**不得重新計算該次交付已承諾的 semantic derived values**。

這條劃出允許漂移的邊界：樣式變好看是可以的（它不說謊），場次號被重算則絕對不行 —— 後者正是票券 13（子場次是否攤平）翻案時會踩到的地雷。

配套的第三條，寫成能力而非欄位：**一筆交付必須能獨立重建該次交付所承諾的語意。** 這修掉了交付快照原本的弱點（只存 `場次 id → 號碼`，doc 一旦面目全非，`sc_abc → 12` 就無法單獨閱讀），但**不寫成「必須有 doc 欄位」** —— 那是 persistence concern，不該上升為 domain invariant。

## Atomicity boundary

PDF 的位元組送達對方硬碟，不可能與資料庫交易同一個原子操作。所以問題不是「怎麼讓它原子」，而是**失敗時往哪一邊倒**，而兩種失敗嚴重不對稱：

| 失敗 | 後果 |
|---|---|
| 交付已記錄、渲染失敗 | 一筆沒有紙的交付。**它沒有說謊**（只宣稱「T 時刻承諾的內容是 C」），可回復。 |
| 紙已到對方手上、交付沒記錄 | 紙上印著我們沒存過的號碼 —— 票券 07 整個論證的那個「事後補不回來」。永久損壞。 |

順序因此是被迫的：**先提交交付，再渲染。** 但真正的答案比排序更強一句 —— **Delivery 是渲染的輸入，不是渲染的產物。** 渲染器讀的是那筆已提交的交付，不是 live doc。

這一句買到四樣東西：atomicity 邊界縮成**只有一個交易**（建立交付），其餘全是它的純函式；重試＝用同一筆交付重新渲染，不產生第二列；「凍結連結的內容來源不得依賴 current screenplay state」**PDF 路徑免費也拿到**；PDF 頁尾的時間戳必然是交付的建立時間而非渲染當下的 now。

兩條限制：**「artifact 尚未成功產生」是交付的一個合法狀態**，不是待清理的異常（不設狀態機旗標 —— 旗標會說謊）；**PDF 的 byte-for-byte determinism 不是 domain invariant**，只是這個順序的良好後果 —— 把它升格會直接撞上不變式 E。

## 守住的紅線

- **identity 是 share ≠ 要做設定面板。** v1 的 share **零配置**：視圖組合固定（劇本＋場次表，頁內切換）、沒有標題、沒有密碼。選這個 identity 是為了讓 frozen 有地方站，不是為了長出開關。
- **不滑進版本管理。** 沒有版本列表、沒有比較、沒有還原。一次交付＝一條連結。
- **快照是必然的，連結是自願的。** 每次交付都建立（不變式 D 強制），但 token **懶惰鑄造** —— 直到使用者按「取得這次交付的連結」。否則「我只是想印一份 PDF」會在背後多出一條公開可讀的網址。
- **不對凍結連結的讀者說「作者後來又改了」。** 那是把 current state 洩漏給一個被刻意凍結的受眾（投獎與交件情境下是明確的害處），且「我後來改了」是編劇該主動說的話。同一則資訊**對編劇自己的分享清單顯示**則有用且零洩漏。

## 代價

- 渲染器演進後，舊的凍結連結會用新樣式顯示舊內容 —— 與當初那份 PDF 不會像素相同。這是刻意接受的（不變式 E），承諾從來就是語意層的。
- 「一次交付＝一條連結」使得同一天匯出五次會留下五筆交付。接受：交付是**事件**不是狀態，去重會製造「這次沒有新交付」的困惑，且票券 07 已定全部保留、不清理。
- 沒有有效期，所以一條被轉傳出去的連結在被撤銷前一直有效。接受：對這個威脅模型，過期是安全劇場，撤銷才是真正的控制。
