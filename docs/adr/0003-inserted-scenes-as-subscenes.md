# 插入戲以子場次表達，深度固定兩層

插入戲（在場次序列中插入一整場新戲）在 v1 範圍內，**以子場次表達**：主場次底下可以放子場次，子場次不能再有子場次；需要多個插入（蒙太奇）時水平展開，不遞迴。

階層是**結構**，不是屬性：在編輯器文件裡，子場次是父場次的子節點（父場次的內容規則從 `sceneBlock+` 放寬為 `(sceneBlock | subscene)+`），文件頂層仍然收成 `scene+`。子場次號（`5.1`）與場次號同一條規則 —— 從父子關係**推導**出來的顯示值，不進文件也不進資料庫。

子場次有完整的 metadata、自己的永久 id，並且**會進場次表**。決定性論證：場次 metadata 只有兩個消費者（場次表與 PDF 場次標題），子場次若不進場次表，它的 metadata 就沒有任何人看得到 —— 是白工，而且會讓編劇誤以為製片看得到。「有 metadata」與「進場次表」必須同進同退；製作面的理由是額外的場景需求必須讓製片知道。

## Considered Options

**使用者手打的字母尾綴（`S5A`）。** 已在 [ADR-0002](./0002-scene-id-and-derived-scene-numbers.md) 否決：一搬移就變成 `S2A`，是假保護。它在業界成立是因為底下有顏色稿的鎖定層，我們沒有那一層。**父子關係沒有這個毛病** —— 子場次跟著父場次一起搬，語意不會說謊，而編號是從關係推導的，不是人打的旗標。這正是同一個需求（反覆出現三次：`S5A` → 塞進插入鏡頭 → 子場次）能以更好的形狀回到 v1 的原因。

**塞進「插入畫面」這個區塊型別。** 已否決：插入的戲有自己的時空，而 metadata 正是場次的**身分判準**（時空變了，依定義就是另一個場次）。撐大區塊等於讓一個沒有 metadata 的東西承載必須被製片看到的資訊。插入畫面因此縮回「與本場次同一個時空的單一畫面」，並保留為區塊型別。

**平坦模型 + `depth` 屬性**（仍然只有一種場次節點，階層靠掃描序列推導）。否決有二：其一，「子場次跟著父場次一起搬」在巢狀是免費的（搬一棵子樹是編輯器的原生行為），在平坦則要在拖曳、刪除、剪下、貼上每一條路徑上手工維持 —— 那又是一個靠慣例維持的旗標，`S5A` 的毛病換個欄位名重演，而且平坦模型允許「`depth: 1` 的場次前面沒有父場次」這種文件狀態自己說謊。其二，平坦表達不了「插在場次中間」：父場次一旦被切開，後半段的區塊就沒有容器，除非把父場次拆成兩場 —— 而那正是插入戲要避免的事。

**深度不限的遞迴階層。** 否決：v1 的常設原則是一條路走通；固定兩層可由內容規則直接保證（子場次的內容規則不含子場次），不必寫執行期檢查，蒙太奇用水平展開已經夠。

## Consequences

**永久 id 不編碼階層。** 子場次用與場次相同的 `sc_` 前綴全域唯一 nanoid。把父 id 編進子 id 會在子場次被拖出來升級成主場次時說謊 —— 那是 `S5A` 的毛病換個地方重演。父子關係只由樹結構表達。

**交付快照不必改結構。** 它存的是 `場次 id → 那次印出的號碼`，號碼是字串，`"6"` 與 `"5.1"` 一樣裝得下。ADR-0002 選擇「存推導結果而非推導輸入」所要保護的情況（編號演算法日後改變、既有快照不得被重算改寫），在階層化引入時第一次真的發生了。

**PDF 上沒有範本可循。** 三份台灣格式範本完全沒有觸及插入場次，`5.1　內景 醫院走廊 日` 是本專案自己發明的寫法（省略尾點、不縮排、不加前綴）。投稿情境是否接受非連續編號**尚未查證**；若查出風險為真，補救是加一個「攤平成 1..N」的匯出選項 —— 一個推導函式，不動資料模型。

**拖曳成本增加。** 可拖的東西從兩種變三種，落點合法性從「同類型」變成依位置計算，且要拒絕會生出第三層的落點。編輯器選型票券記錄的那批拖放 bug 會部分重來。

**兩種「插入」在使用者眼前並存。** 插入畫面與子場次的界線是**時空是否改變**，這條線要靠選單文案與區塊上的逃生口去教，不能只寫在文件裡。
