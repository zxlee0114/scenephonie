# 場次號是推導的顯示值，永久 id 對使用者不可見

業界所有拍攝表單都以**會變動的場次號**互相參照，沒有任何永久識別碼機制；劇本一改版，下游表單就得「乾坤大挪移」。業界並非沒有處理這件事 —— 處理方式是**顏色稿制度**：正式開拍前發出的白稿把場次號與頁碼**鎖定**，之後每輪改稿依序換色（藍、粉、黃、綠、金黃）並只發改動的頁。廣為人知的字母尾綴編號（`12A`）正是這個制度的產物 —— 白稿一鎖，新插進來的戲只能靠尾綴。

我們選擇另一條路：**每個場次擁有永久 id，且該 id 對使用者完全不可見**（只存在於網址、API 與下游關聯）；**場次號是每次渲染時即時從序列推導出來的顯示值**，不進編輯器文件、也不進資料庫。所有下游文件因此不是與劇本脫鉤的副本，而是同一組場次的即時投影 —— 重排之後不需要同步，因為根本沒有第二份資料。

## Considered Options

**沿用顏色稿／鎖定制度。** 這是業界已驗證的解法，但它解的是**紙本流通**的問題：因為沒有共同的資料來源，只好靠凍結與換色讓人肉辨識版本。我們有共同的資料來源，套用鎖定等於自己製造出它要解決的那個問題。

**讓使用者手打字母尾綴（`S5A`）。** 已在原型中實作並否決：把 `S5A` 搬到 `S2` 後面，它就變成 `S2A`。從「場次號是推導值」的角度完全正確，但編劇寫 `S5A` 的**動機**正是不影響已發出去的表單 —— 一搬就失效。它在業界成立是因為底下有鎖定制度撐著；在我們這裡沒有那一層，它是沒有根的旗標，是假保護。（插入戲的需求本身仍在 v1，改以**子場次**表達 —— 父子關係不會說謊，因為子場次跟著父場次一起搬。）

## Consequences

**永久 id 在 v1 幾乎沒有消費者。** v1 只有編劇單人使用、沒有下游文件，這條約束的價值要到第二三層（分鏡、拍攝行程）才兌現。它現在是為未來鋪的路，不是可展示的賣點 —— 不該在 v1 對外宣稱。

**編劇與製片口頭溝通時，手上只有會變動的號碼。** 「你看第 12 場」這句話在重排後會失效，而使用者看不到 id，沒有備援的指稱方式。這是刻意付出的代價。

**離線副本仍然會過期。** 投影模型消滅了「編號說謊」，但消滅不了「有人手上拿著一份舊 PDF」。補償措施有兩層：匯出時存一份**交付快照**（記錄那次印出的 `場次 id → 號碼` 對照），以及 PDF 頁尾的匯出時間戳。

**活的分享連結有「內容漂移」問題，且比 PDF 更隱形。** 兩名組員在不同時間打開同一條唯讀連結會看到不同的戲，而紙本至少還有實體差異可察覺。投影模型不但沒解決這一項，還讓它更難被發現。此問題另案處理（唯讀分享連結票券）。

## 身分何時被建立、何時被保留

`CONTEXT.md` 的**場次**詞條列出了那條不變式（五個建立時刻，其餘一律保留既有身分）。這一節記它背後的理由與實作邊界。

**「保留」那一半就是永久 id 這條決策的可執行版本。** 上面說「重排之後不需要同步，因為根本沒有第二份資料」—— 那句話只有在**重排不會換掉 id** 時才成立。少了這條不變式，永久 id 只是一個欄位名稱，不是一個保證。

**「建立」那五條分成兩組，各有各的判準：**

**第 1～3 條（建立）沿用既有規則**：[ADR-0003](./0003-inserted-scenes-as-subscenes.md) 已定「**會產生永久錨點的動作，入口只有一個，而且那個入口的名字要說出它會建立東西**」。所以 `/next`、`/insert`、`/continue-to`、「對剪到…」的第二步都是具名入口 —— 編劇按下去時知道自己在建立一場戲。反過來說，**沒有任何隱含路徑可以生出場次**。

**第 4～5 條（剪貼簿）是同一條規則在剪貼簿上的延伸**：**貼上會不會建立新身分，由來源決定，不由使用者猜。**

- **剪下→貼上（搬移）id 必須保住**；**複製→貼上 id 必須換新**。不必猜測意圖，因為**碰撞本身就是判別器**：剪下時原節點已離開文件，貼上不碰撞；複製時原節點還在，貼上必碰撞。
- **跨劇本貼上一律建立新身分。** 理由是語意的：**一份劇本的場次，身分只在那份劇本裡有意義** —— 交付快照與下游文件都是「這一部片」的事。貼進另一部片，得到的不是同一場戲的另一個位置，而是另一部片裡的一場新戲。全域唯一是實作結果，不是要去維護的規則。

**實作邊界**（細節見票券 04 的 Q5）：

- **語意判斷住在剪貼簿邊界**（`transformCopied`／`transformPasted`）—— 只有它知道來源劇本與目的劇本。作法是在剪貼簿內容上蓋一個來源劇本的印記，**來源劇本 ≠ 目前劇本時一律重新產生 id**。
- **結構修復住在文件不變式**（`appendTransaction`）—— 它只認一條規則：同一份 doc 內不得有重複 id。**它永遠不必知道來源**，因此是最後一道防線，對任何來源都成立（剪貼簿、程式化插入、日後的匯入、我們自己的 bug）。修復時改的一律是本次 transaction 新插入的那個節點；無法判定時的後備規則是**文件順序在前者保留**。
- **修復的 transaction 標 `addToHistory: false`** —— 否則「複製貼上 → 去重改 id → ⌘Z」會退回到重複 id 的狀態。它不是使用者的動作，是模型的修復。
- **適用範圍**：場次與子場次完全相同處理。**群演**是場次限定實體、id 只在該場次內有意義，跟著場次被複製過去是**正確的**，不去重。
